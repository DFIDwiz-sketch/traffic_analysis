Which workstation read documents from the shared drive?

The publisher’s “First to Last” exercise asks the analyst to identify an infected workstation and scope its traffic. The setup page lists the DC as 172.16.8.2. In the original PCAP, SMB2 requests naming FIRSTTOLAST-DC receive replies from 172.16.8.8. Both investigated workstations read policy files from that server. The PCAP also records 172.16.8.49 reading two spreadsheets from its Shared share and sending HTTP POSTs to an external address.

어느 워크스테이션이 공유 문서를 읽었나

공개 실습 ‘First to Last’는 감염된 워크스테이션을 식별하고 트래픽 범위를 확인하는 과제입니다. 원문 환경 설명의 DC는 172.16.8.2입니다. 원본에서는 FIRSTTOLAST-DC를 대상으로 한 SMB2 요청에 172.16.8.8이 응답했습니다. 조사한 두 워크스테이션은 이 서버에서 정책 파일을 읽었습니다. 캡처에는 172.16.8.49의 Shared 문서 두 개 읽기와 외부 HTTP POST도 있습니다.

실습 시나리오와 문서의 DC 주소는 공개 원문에 근거합니다. 아래 응답자 주소, 작업, 상태 코드와 시각은 원본 패킷에서 확인했습니다. 검색 예제는 실습 환경에서 검증합니다.

1 · Baseline both clients before filtering the server

Use the case tag for <CASE>. Select the full capture interval and set Splunk to UTC. If the picker uses ingest time, widen it and read numeric Zeek ts for the actual timeline. The examples use flattened fields.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

Verify the available connection, SMB and HTTP sourcetypes. SMB log coverage can vary by analyzer and ingest settings.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp id_resp_p=445
    id_orig_h IN ("172.16.8.49","172.16.8.53")
| stats dc(uid) as connections values(id_orig_p) as client_ports values(conn_state) as states
    sum(orig_pkts) as client_packets sum(resp_pkts) as server_packets by id_orig_h id_resp_h
| sort 0 id_orig_h

Compare both client addresses and group by observed responder. Starting with the responder field open lets the capture resolve the address discrepancy. The original PCAP shows 593 bilateral TCP/445 packets for .49 and 319 for .53 to .8, including acknowledgement and control frames. Those packet totals differ in scope from Zeek’s connection count.

1단계 · 서버를 필터링하기 전에 두 클라이언트 비교

<CASE>에 수집 태그를 넣고 전체 캡처 구간을 포함합니다. Splunk는 UTC로 표시합니다. 시간 선택기가 수집 시각을 사용하면 범위를 넓히고 실제 사건 순서를 숫자형 Zeek ts로 확인합니다. 예제는 평탄화된 필드를 사용합니다.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

연결, SMB와 HTTP sourcetype 수집 여부를 확인합니다. SMB 로그의 가시성은 분석기와 수집 방식에 따라 다를 수 있습니다.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp id_resp_p=445
    id_orig_h IN ("172.16.8.49","172.16.8.53")
| stats dc(uid) as connections values(id_orig_p) as client_ports values(conn_state) as states
    sum(orig_pkts) as client_packets sum(resp_pkts) as server_packets by id_orig_h id_resp_h
| sort 0 id_orig_h

두 클라이언트를 실제 응답자 주소별로 비교합니다. 응답자를 먼저 제한하지 않으면 주소가 다른 이유를 원본에서 살필 수 있습니다. 원본 TCP/445에서 .8로 향한 연결에는 양방향 패킷이 .49에서 593개, .53에서 319개였습니다. ACK와 제어 패킷도 포함되며 Zeek의 연결 수와는 단위가 다릅니다.

2 · Trace reads from the share and compare outbound HTTP

SPL 
index=zeek pcap_case="<CASE>" id_resp_h=172.16.8.8 id_resp_p=445
    id_orig_h IN ("172.16.8.49","172.16.8.53") id_orig_p IN (49670,49671,49728)
    sourcetype IN ("zeek:conn","zeek:smb_mapping","zeek:smb_files","zeek:dce_rpc")
| sort 0 ts
| table ts sourcetype uid id_orig_h id_orig_p path name action endpoint operation

Take the UID from each TCP session and associate the SMB share and file records from the same Zeek processing run. If a case was imported repeatedly, select one run first. Use the successful tree mapping and file handle to link a read to its share and file in packets. A file-read row may be missing in Zeek, so check SMB2 replies before concluding about a specific file.

SPL 
index=zeek sourcetype=zeek:http pcap_case="<CASE>" id_orig_h IN ("172.16.8.49","172.16.8.53") method=POST
| search NOT id_resp_h="172.16.8.*"
| stats count as requests dc(uid) as connections min(ts) as first max(ts) as last
    values(status_code) as responses by id_orig_h id_resp_h

Use the external POST comparison to choose flows for follow-up. The HTTP rows have their own UIDs for joining to zeek:conn in the same run. Compare HTTP and SMB using the workstation, timestamps and endpoint telemetry when available.

The two reads represent separate requests on the selected share connection. Ordinary policy activity and authorized spreadsheet access are plausible explanations. Packet timing supports comparing the events. The captured HTTP status and SMB read replies leave process ownership, authorization and any outbound transfer of the documents unresolved.

2단계 · 공유 문서 읽기와 외부 HTTP 확인

SPL 
index=zeek pcap_case="<CASE>" id_resp_h=172.16.8.8 id_resp_p=445
    id_orig_h IN ("172.16.8.49","172.16.8.53") id_orig_p IN (49670,49671,49728)
    sourcetype IN ("zeek:conn","zeek:smb_mapping","zeek:smb_files","zeek:dce_rpc")
| sort 0 ts
| table ts sourcetype uid id_orig_h id_orig_p path name action endpoint operation

각 TCP 연결의 UID로 같은 Zeek 처리 실행의 SMB 공유 및 파일 기록을 연결합니다. 여러 번 가져온 케이스는 한 실행을 선택합니다. 패킷에서 성공한 트리 매핑과 파일 핸들로 작업을 해당 공유 및 파일에 연결합니다. Zeek에 읽기 행이 없으면 SMB2 응답을 패킷으로 확인합니다.

SPL 
index=zeek sourcetype=zeek:http pcap_case="<CASE>" id_orig_h IN ("172.16.8.49","172.16.8.53") method=POST
| search NOT id_resp_h="172.16.8.*"
| stats count as requests dc(uid) as connections min(ts) as first max(ts) as last
    values(status_code) as responses by id_orig_h id_resp_h

외부 POST 검색으로 추가 조사할 흐름을 고릅니다. HTTP 행의 각 UID는 같은 Zeek 실행의 zeek:conn과 대조합니다. HTTP와 SMB는 워크스테이션 IP, 시각, 확보 가능한 프로세스 기록으로 비교합니다.

표의 두 읽기는 선택한 공유 연결에서 별개의 요청입니다. 정상 정책 처리나 승인된 문서 접근도 가능한 설명입니다. 패킷 시각으로 사건을 비교할 수 있습니다. 프로세스, 접근 권한과 문서가 외부로 전송됐는지는 HTTP 상태와 SMB 읽기 응답만으로 확인하기 어렵습니다.

4 · Check the two read lengths offline if needed

TShark 
tshark -n -r "2026-08-09-traffic-analysis-exercise.pcap" \
  -Y 'frame.number == 10607 || frame.number == 10608 || frame.number == 11566 || frame.number == 11567' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e ip.src -e tcp.stream \
  -e smb2.msg_id -e smb2.read_length -e smb2.nt_status

If Arkime leaves a selected read unclear, compare the four original frames. Use the TCP stream, message ID and direction to pair each request and reply. Read the response status and length. This reports metadata for individual operations.

4단계 · 필요한 경우 읽기 길이 두 건을 오프라인 확인

TShark 
tshark -n -r "2026-08-09-traffic-analysis-exercise.pcap" \
  -Y 'frame.number == 10607 || frame.number == 10608 || frame.number == 11566 || frame.number == 11567' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e ip.src -e tcp.stream \
  -e smb2.msg_id -e smb2.read_length -e smb2.nt_status

Arkime에서 선택한 읽기가 분명하지 않으면 원본 프레임 네 개를 대조합니다. TCP 스트림, 메시지 ID와 방향으로 요청과 응답을 연결하고 각 응답의 상태와 길이를 확인합니다. 출력은 선택한 작업의 메타데이터입니다.

5 · Document the address discrepancy and follow up

Record the capture hash, observed and documented DC addresses, both client addresses, the confirmed read frames and the external POST. Verify the DC address against site inventory and check approved share access, process-network events, file access logs and proxy logs. Confirm process ownership or file transfer before attributing the document reads to the infection.

5단계 · 주소 차이를 기록하고 후속 증거 요청

티켓에 해시, 문서 및 원본에서 확인한 DC 주소, 두 클라이언트, 읽기 프레임과 외부 POST를 남깁니다. DC 주소는 환경 인벤토리와 대조합니다. 승인된 공유 접근, 프로세스 네트워크 기록, 파일 접근 및 프록시 로그를 확인합니다. 문서 읽기를 감염과 연결하기 전에 실행 프로세스와 외부 전송 근거를 확보합니다.
