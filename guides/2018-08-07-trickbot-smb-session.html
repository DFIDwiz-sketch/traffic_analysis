What the capture shows

The 7 August 2018 report describes Trickbot moving from a workstation at 172.16.10.191 to the domain controller at 172.16.10.2. It reports tot284 on the client and lib284 on the DC. A read-only review of the PCAP independently located successful SMB1 write exchanges for two executable filenames on the TCP connection from client port 49228 to DC port 445. The first workstation-to-DC SYN used a different client port. Finding the earliest SYN is useful for a timeline, but does not identify the file-write session.

패킷 번호와 시각은 원본에서 직접 확인했습니다. Splunk·Arkime·TShark 쿼리는 실습 예제입니다. 악성코드 계열과 변종 이름은 공개 원문에 근거합니다.

1 · Compare targets and sessions in Splunk

Use UTC and a search interval covering the file. Substitute your importer’s case tag for <CASE>. The SPL assumes flattened Zeek fields. If the capture was indexed more than once, select one Zeek processing run before using connection identifiers.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

Inventory sourcetypes before assuming that file or share records exist. The resulting time ranges describe indexed records. A missing sourcetype may reflect the Zeek analyzer or ingestion coverage.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp id_resp_p=445 id_orig_h=172.16.10.191
| stats count as connections dc(id_orig_p) as client_ports sum(orig_bytes) as sent
        sum(resp_bytes) as received min(ts) as first values(conn_state) as states by id_orig_h id_resp_h
| sort - connections
| eval first=strftime(first,"%H:%M:%S.%3N %Z")

Read the port and direction before ranking connections. Offline parsing counted 1,179 bilateral packets on flows from the workstation to DC TCP/445, including acknowledgements and other control packets. The same workstation also sent SYNs to .1 and .254. A TCP attempt to those addresses does not establish file transfer. Expand the DC pair by client port to see why the first connection differs from the write session.

1단계 · Splunk에서 대상과 세션 비교

UTC 표시를 사용하고 검색 범위에 캡처를 포함합니다. <CASE>를 수집기에서 실제로 붙인 값으로 바꾸세요. SPL은 평탄화된 Zeek 필드명을 가정합니다. 동일한 파일을 여러 번 수집했다면 연결 식별자를 사용하기 전에 처리 한 건만 선택합니다.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

로그 종류부터 확인합니다. 이 시각 범위는 색인된 기록에 해당합니다. 특정 로그가 없다면 Zeek 분석기와 수집 범위를 점검합니다.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp id_resp_p=445 id_orig_h=172.16.10.191
| stats count as connections dc(id_orig_p) as client_ports sum(orig_bytes) as sent
        sum(resp_bytes) as received min(ts) as first values(conn_state) as states by id_orig_h id_resp_h
| sort - connections
| eval first=strftime(first,"%H:%M:%S.%3N %Z")

연결 수를 해석하기 전에 포트와 방향을 확인합니다. 직접 확인한 원본에서는 워크스테이션이 DC의 TCP/445로 시작한 흐름에 ACK 등의 제어 패킷을 포함해 양방향 패킷 1,179개가 있었습니다. 같은 워크스테이션이 .1과 .254에도 SYN을 보냈지만, 연결 시도 자체는 파일 전송의 근거가 아닙니다. DC 쌍을 클라이언트 포트별로 살펴보면 최초 관측 연결과 쓰기 세션이 구분됩니다.

2 · Correlate file open, write and reply on one session

SPL 
index=zeek pcap_case="<CASE>" id_orig_h=172.16.10.191 id_resp_h=172.16.10.2 id_orig_p=49228 id_resp_p=445
    sourcetype IN ("zeek:conn","zeek:smb_mapping","zeek:smb_files","zeek:dce_rpc","zeek:ntlm")
| sort 0 ts
| eval time_utc=strftime(ts,"%Y-%m-%d %H:%M:%S.%3N %Z")
| table time_utc sourcetype uid id_orig_p path name action endpoint operation conn_state

Locate the connection using the verified client port. Keep its uid and inspect the same identifier in available share, file and RPC records from the same Zeek processing run. For each apparent file event, review the filename and action. The table matches file-handle metadata to a write and its reply. It does not treat file-open requests as completed writes.

SPL

확인한 클라이언트 포트로 연결을 찾고 uid를 기록합니다. 같은 Zeek 처리 실행에서 생성된 공유·파일·RPC 로그에 같은 값이 있는지 확인합니다. 파일명과 action을 함께 읽으세요. 아래 표는 파일 핸들 메타데이터와 대응하는 쓰기·응답을 연결한 결과이며, 파일을 열려는 요청만으로 쓰기 성공을 판단하지 않습니다.

3 · Cross-check one connection in Arkime

Arkime 
tags == "<CASE>" && ip.src == 172.16.10.191 && ip.dst == 172.16.10.2 && port.src == 49228 && port.dst == 445

Set the UTC picker around 21:30:20 and open the session for client port 49228. Check both directions, and compare packet times against Splunk. Keep the earlier port 65347 session separate when recording the transfer. If the indexed capture misses SMB operation details, inspect the original file.

21:30:20 UTC 전후로 좁혀 클라이언트 포트 49228의 세션을 열고, 양방향 패킷 시각을 Splunk 결과와 대조합니다. 앞서 본 포트 65347 세션과 쓰기 세션을 별도로 기록합니다. 색인된 패킷에서 작업이 잘 보이지 않으면 원본을 확인합니다.

4 · Use TShark if only the packet reply remains uncertain

TShark 
tshark -n -r "2018-08-07-Trickbot-moves-from-client-to-DC.pcap" \
  -Y 'ip.addr == 172.16.10.191 && ip.addr == 172.16.10.2 && tcp.port == 49228 && tcp.port == 445 && smb.cmd == 0x2f' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e ip.src -e ip.dst \
  -e tcp.stream -e smb.mid -e smb.nt_status

This offline query lists write metadata for just the observed pair and client port. Match requests and responses by TCP stream, SMB multiplex ID and direction. Confirm the zero reply status for the write under review. Reassembly or a filtered export can alter the frame reference, so record the connection tuple and time as well.

4단계 · 쓰기 응답만 확인할 때 TShark 사용

TShark 
tshark -n -r "2018-08-07-Trickbot-moves-from-client-to-DC.pcap" \
  -Y 'ip.addr == 172.16.10.191 && ip.addr == 172.16.10.2 && tcp.port == 49228 && tcp.port == 445 && smb.cmd == 0x2f' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e ip.src -e ip.dst \
  -e tcp.stream -e smb.mid -e smb.nt_status

해당 호스트 쌍과 클라이언트 포트의 쓰기 메타데이터만 오프라인으로 확인합니다. TCP 스트림, SMB Multiplex ID, 방향으로 요청과 응답을 연결하고 응답 상태값 0을 확인하세요. 재조립이나 재저장에 따라 프레임 번호가 달라질 수 있으므로 연결의 주소·포트와 시각도 기록합니다.

5 · Prepare a SOC ticket

Record the DC and workstation, exact TCP connection, two successful write exchanges and capture hash. Distinguish those observations from the publisher’s tot284 and lib284 labels. Ask for DC file-creation, process and service evidence. Compare any candidate host activity against authorized administration and software deployment before judging a similar event from a production network.
