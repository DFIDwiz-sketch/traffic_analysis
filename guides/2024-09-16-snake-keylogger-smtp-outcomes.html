Which SMTP submission did the server accept?

The publisher identifies Snake KeyLogger activity with SMTP exfiltration. The PCAP contains two message submissions from 10.9.16.101 to 208.91.199.223:587. In both sessions a server 354 reply preceded client message data. The first submission ended with 250, and the second ended with 550. This guide uses the reply after the message terminator to distinguish acceptance from rejection.

SMTP 서버가 어느 메시지를 수락했나

공개 원문은 Snake KeyLogger가 SMTP로 데이터를 유출한 사례를 소개합니다. 원본 PCAP에서 10.9.16.101은 208.91.199.223:587로 메시지를 두 번 제출했습니다. 두 세션 모두 서버의 354 응답 뒤에 클라이언트가 메시지 데이터를 보냈습니다. 첫 제출에 대한 최종 응답은 250, 두 번째는 550이었습니다. 메시지 종료 표시 뒤의 응답으로 서버 수락과 거부를 구분합니다.

1 · Baseline mail connections in Splunk

Replace <CASE> with the import label and display timestamps in UTC. Scope the search to the capture range. If _time is ingest time, include the ingest window and order events using numeric Zeek ts. The examples use flattened fields.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

Check that connection and SMTP logs arrived. A missing SMTP log can reflect analyzer or ingest coverage.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp id_orig_h=10.9.16.101
    id_resp_p IN (25,465,587,2525)
| stats count as connections values(service) as services values(conn_state) as states
        min(ts) as first max(ts) as last by id_resp_h id_resp_p
| sort 0 first

The query counts connections to common submission and mail ports by destination. This is a starting scope. Read the connection state and service fields, then verify the recorded SMTP exchange. The original capture contains two TCP/587 connections for the selected pair, with client ports 49887 and 49888.

1단계 · Splunk에서 메일 연결 베이스라인 확인

<CASE>에 수집 때 지정한 값을 넣고 UTC로 표시합니다. 검색 범위를 캡처 구간으로 설정합니다. _time이 수집 시각이면 수집 구간을 포함하고 숫자형 Zeek ts로 사건 순서를 읽습니다. 예제는 평탄화된 필드를 사용합니다.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

연결과 SMTP 로그가 조회되는지 확인합니다. SMTP 로그가 없으면 분석기와 수집 범위를 점검합니다.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp id_orig_h=10.9.16.101
    id_resp_p IN (25,465,587,2525)
| stats count as connections values(service) as services values(conn_state) as states
        min(ts) as first max(ts) as last by id_resp_h id_resp_p
| sort 0 first

일반적인 메일 및 메시지 제출 포트에 해당하는 연결을 목적지별로 집계합니다. 연결 상태와 서비스 분류로 범위를 좁힌 뒤 패킷에서 SMTP 교환을 확인합니다. 원본에서 선택한 두 호스트 사이에는 TCP/587 연결 두 개가 있으며, 클라이언트 포트는 49887과 49888입니다.

2 · Read the final SMTP outcome for each connection

SPL 
index=zeek sourcetype=zeek:smtp pcap_case="<CASE>"
    id_orig_h=10.9.16.101 id_resp_h=208.91.199.223 id_resp_p=587
| sort 0 ts
| table ts uid id_orig_p trans_depth tls last_reply

Use the selected SMTP rows to identify source port, TLS status and last_reply where present. A reply after another command can be the last reply recorded, so verify its position in the exchange. A 354 is permission to send message data. Evaluate acceptance only after the message terminator.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" uid="<SMTP_UID>"
| table ts uid id_orig_h id_orig_p id_resp_h id_resp_p conn_state orig_bytes resp_bytes missed_bytes

Use each SMTP UID with its zeek:conn data from the same Zeek processing run. If you loaded the capture twice, select one run. The two SMTP sessions have different UIDs. A TCP connection state describes transport. SMTP replies describe what the server said about the transaction.

UTC · 16 September Original frames Directly observed
20:08:50.690–20:08:50.785 136, 138 Source port 49887 sends DATA, and server replies 354
20:08:50.790–20:08:51.441 153, 155 Message terminator and server 250 acceptance
20:08:53.710–20:08:53.799 182, 184 Source port 49888 sends DATA, and server replies 354
20:08:54.365–20:08:55.247 1089, 1106 Message terminator and server 550 rejection

The second connection still carried client data before rejection. The first reply confirms acceptance by the observed server. Final mailbox delivery requires mail-side evidence. An approved application notification could produce accepted and rejected submissions. Use the source process, relay policy and case context to evaluate that explanation.

2단계 · 연결별 최종 SMTP 결과 읽기

SPL 
index=zeek sourcetype=zeek:smtp pcap_case="<CASE>"
    id_orig_h=10.9.16.101 id_resp_h=208.91.199.223 id_resp_p=587
| sort 0 ts
| table ts uid id_orig_p trans_depth tls last_reply

SMTP 행에서 출발지 포트, TLS 상태와 last_reply를 확인합니다. 다른 명령에 대한 응답이 마지막으로 기록될 수도 있으므로 교환 내 위치를 확인합니다. 354는 메시지 데이터를 보내도 된다는 뜻입니다. 서버의 수락 여부는 메시지 종료 표시 이후의 응답으로 판단합니다.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" uid="<SMTP_UID>"
| table ts uid id_orig_h id_orig_p id_resp_h id_resp_p conn_state orig_bytes resp_bytes missed_bytes

각 SMTP UID로 같은 Zeek 처리 실행의 zeek:conn 기록을 찾습니다. 두 번 가져온 캡처라면 한 실행으로 제한합니다. 두 SMTP 세션의 UID는 서로 다릅니다. TCP 연결 상태는 전송 계층을 설명하고 SMTP 응답은 서버의 처리 결과를 설명합니다.

9월 16일 UTC 원본 프레임 직접 확인한 근거
20:08:50.690–20:08:50.785 136, 138 출발지 포트 49887에서 DATA, 서버의 354 응답
20:08:50.790–20:08:51.441 153, 155 메시지 종료 표시와 서버의 250 수락 응답
20:08:53.710–20:08:53.799 182, 184 출발지 포트 49888에서 DATA, 서버의 354 응답
20:08:54.365–20:08:55.247 1089, 1106 메시지 종료 표시와 서버의 550 거부 응답

두 번째 연결도 거부 응답 전에 클라이언트 데이터를 전송했습니다. 첫 응답에서 확인한 범위는 관찰된 서버의 수락까지입니다. 수신함 배달은 메일 시스템의 추가 근거가 필요합니다. 승인된 애플리케이션 알림도 수락과 거부를 모두 겪을 수 있으므로 출발지 프로세스와 릴레이 정책을 대조합니다.

5 · Record acceptance, rejection and follow-up

Record the capture hash, the tuples and the two different outcomes. Ask the mail team for submission and relay logs and the endpoint team to identify the originating process. Verify approved service-account use and delivery records before assessing recipients or exposure. Keep message content and authentication data in the appropriate restricted evidence channel.
