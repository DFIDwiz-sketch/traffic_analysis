Which operations wrote to disk and which reached a control pipe?

The publisher’s ISC diary describes an IcedID-infected workstation and subsequent Trickbot activity on the DC. In the original capture, 10.3.4.101 opens two .exe objects beneath the DC’s C$ share and receives successful SMB write replies. The same TCP session later opens svcctl under IPC$. The DC 10.3.4.2 later makes a separate outbound HTTP request. Use the share and object evidence to distinguish these operations.

어떤 작업이 디스크에 쓰고 어떤 작업이 제어 파이프에 접근했는가?

저자의 ISC 보고서는 IcedID에 감염된 워크스테이션과 이후 DC에서 나타난 Trickbot 활동을 설명합니다. 원본에서 10.3.4.101은 DC의 C$ 아래 .exe 객체 두 개를 열고 SMB 쓰기 성공 응답을 받습니다. 이후 같은 TCP 연결에서 IPC$의 svcctl 파이프를 엽니다. DC 10.3.4.2는 뒤이어 별도 외부 HTTP 요청을 보냅니다. 각 작업의 공유와 대상 객체를 확인해 구분합니다.

1 · Find the SMB stream and the DC’s outbound connection

Set <CASE> to the case tag and display the full capture interval in UTC. Include the ingest window if Splunk filters on that timestamp. Use numeric Zeek ts for ordering. These examples assume flattened fields.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

Check which connection, SMB, DCE/RPC and HTTP logs the import produced.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp
    id_orig_h IN ("10.3.4.101","10.3.4.2") id_resp_p IN (445,8082)
| sort 0 ts
| table ts uid id_orig_h id_orig_p id_resp_h id_resp_p conn_state orig_pkts resp_pkts orig_bytes resp_bytes

Start with the two internal IPs and ports 445 and 8082. Around 15:47:41 UTC, select the connection to the DC from client port 49218. The original TCP tuple contains 1,422 packets in both directions. Compare it with the separate DC-originated port 8082 flow around 15:51 UTC.

1 · SMB 스트림과 DC의 외부 연결 찾기

<CASE>에 사례 태그를 입력하고 전체 캡처 구간을 UTC로 표시합니다. Splunk가 수집 시각으로 필터링하면 가져온 구간도 포함합니다. 정렬에는 숫자형 Zeek ts를 쓰며 예시는 평탄화된 필드명을 사용합니다.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

연결, SMB, DCE/RPC, HTTP 로그가 수집됐는지 확인합니다.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp
    id_orig_h IN ("10.3.4.101","10.3.4.2") id_resp_p IN (445,8082)
| sort 0 ts
| table ts uid id_orig_h id_orig_p id_resp_h id_resp_p conn_state orig_pkts resp_pkts orig_bytes resp_bytes

내부 IP 두 개와 포트 445, 8082에서 시작합니다. 15:47:41 UTC 전후에 클라이언트 포트 49218에서 DC로 향한 연결을 확인합니다. 원본의 해당 TCP 연결은 양방향 1,422패킷입니다. 15:51 UTC 전후 DC가 시작한 별도 TCP/8082 흐름과 비교합니다.

2 · Separate disk-share writes from pipe access

SPL 
index=zeek pcap_case="<CASE>" uid="<SMB_UID>"
    sourcetype IN ("zeek:conn","zeek:smb_mapping","zeek:smb_files","zeek:dce_rpc")
| sort 0 ts
| table ts sourcetype uid id_orig_p path share_type name action endpoint operation

Use the UID from client port 49218 in the same Zeek processing run to correlate connection, mapping, file and RPC records. One TCP UID spans multiple SMB trees. Use the server-side tree identifier, file-open reply and resulting handle to associate selected writes with their .exe objects. Use each transaction’s SMB multiplex ID to verify the response.

SPL 
index=zeek pcap_case="<CASE>" id_orig_h=10.3.4.2 id_resp_h=103.119.144.250 id_orig_p=49302 id_resp_p=8082
    sourcetype IN ("zeek:conn","zeek:http")
| sort 0 ts
| table ts sourcetype uid id_orig_h id_resp_h method trans_depth status_code

Compare the DC’s HTTP request and response within their own UID. Use trans_depth within that connection, and use host and time to compare HTTP with the SMB evidence. A missing HTTP row on an unusual port warrants a packet check.

Authorized deployment can produce administrative-share writes followed by service-manager traffic. The packet evidence establishes selected writes and a pipe open. The pipe open leaves service creation and process execution unresolved. The later POST raises the priority of DC follow-up without establishing that the same process caused both activities.

2 · 디스크 공유 쓰기와 파이프 접근 구분하기

SPL 
index=zeek pcap_case="<CASE>" uid="<SMB_UID>"
    sourcetype IN ("zeek:conn","zeek:smb_mapping","zeek:smb_files","zeek:dce_rpc")
| sort 0 ts
| table ts sourcetype uid id_orig_p path share_type name action endpoint operation

클라이언트 포트 49218의 UID를 동일한 Zeek 처리 실행에서 찾아 연결, 공유 매핑, 파일, RPC 로그를 연계합니다. TCP UID 하나에 여러 SMB 트리가 포함될 수 있습니다. 서버 트리 ID, 파일 열기 응답의 핸들로 선택한 쓰기를 각 .exe 객체에 연결합니다. SMB 멀티플렉스 ID로 요청과 응답을 짝짓습니다.

SPL 
index=zeek pcap_case="<CASE>" id_orig_h=10.3.4.2 id_resp_h=103.119.144.250 id_orig_p=49302 id_resp_p=8082
    sourcetype IN ("zeek:conn","zeek:http")
| sort 0 ts
| table ts sourcetype uid id_orig_h id_resp_h method trans_depth status_code

DC의 HTTP 요청과 응답은 해당 연결의 UID로 확인합니다. 같은 연결 안에서는 trans_depth를 쓰고, SMB와 비교할 때는 호스트와 시각을 대조합니다. 비표준 포트에서 HTTP 로그가 비어 있으면 패킷을 확인합니다.

승인된 소프트웨어 배포에서도 관리 공유 쓰기와 서비스 관리자 통신이 이어질 수 있습니다. 패킷에서 확인한 범위는 선택한 쓰기와 파이프 열기까지입니다. 서비스 생성과 프로세스 실행 여부는 추가 확인이 필요합니다. 이후 POST는 DC 후속 조사의 우선순위를 높이지만, 두 활동을 같은 프로세스가 일으켰는지는 확인되지 않았습니다.
