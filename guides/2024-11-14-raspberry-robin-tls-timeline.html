What can the encrypted capture establish?

The publisher attributes the case to Raspberry Robin and describes a WebDAV download using evidence from a separate Fiddler capture. The original PCAP analyzed here shows TLS ClientHello messages from 10.0.0.101. An early group requests the same visible server name over TCP/443, while later ClientHello messages reach additional hosts and ports. Use this timeline to decide which connection details are confirmed and which claims require the separate application or endpoint records.

암호화된 캡처에서 어디까지 확인할 수 있나

공개 원문은 Raspberry Robin 사례를 소개하고 별도의 Fiddler 캡처를 근거로 WebDAV 다운로드를 설명합니다. 여기서 분석한 원본 PCAP에는 10.0.0.101이 보낸 TLS ClientHello가 있습니다. 초기에는 TCP/443 연결 여러 개에서 같은 서버 이름을 요청했고, 이후 다른 호스트와 포트에서도 ClientHello가 관찰됩니다. 타임라인으로 확인된 연결 근거와 별도 응용 계층 또는 엔드포인트 기록이 필요한 항목을 정리합니다.

1 · Baseline connections by minute in Splunk

Use the case label assigned at import for <CASE>. Display UTC and search the full capture interval. If _time is set from ingest time, widen the picker and use numeric Zeek ts for the timeline. The examples use flattened fields.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

Confirm that Zeek connection and TLS logs arrived. Zeek's TLS log is commonly imported as zeek:ssl. Check the field mapping and analyzer coverage before interpreting sparse results.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" id_orig_h=10.0.0.101 proto=tcp
| bin ts span=1m
| stats count as connections dc(id_resp_h) as destinations values(id_resp_p) as responder_ports
        values(service) as services by ts
| sort 0 ts

Read each minute's destination count and responder ports. Compare the early traffic around 21:13–21:16 UTC with the new addresses and ports around 21:28–21:34 UTC. Use the Zeek service label as a starting point, then validate selected connections in packets. Standard port assignments are only one clue to the protocol observed.

1단계 · Splunk에서 분 단위 연결 베이스라인 확인

<CASE>에 가져올 때 지정한 케이스 값을 넣습니다. UTC로 표시하고 전체 캡처 구간을 선택합니다. _time이 수집 시각이면 검색 범위를 넓히고 숫자형 Zeek ts로 사건 시각을 읽습니다. 예제는 평탄화된 필드를 사용합니다.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

Zeek 연결과 TLS 로그가 수집됐는지 확인합니다. Zeek TLS 로그의 sourcetype은 보통 zeek:ssl입니다. 결과가 적으면 필드 매핑과 분석기 범위를 점검합니다.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" id_orig_h=10.0.0.101 proto=tcp
| bin ts span=1m
| stats count as connections dc(id_resp_h) as destinations values(id_resp_p) as responder_ports
        values(service) as services by ts
| sort 0 ts

분마다 목적지 수와 응답자 포트를 봅니다. 21:13~21:16 UTC의 초기 연결과 21:28~21:34 UTC 전후에 나타난 새 주소 및 포트를 비교합니다. Zeek 서비스 분류로 후보를 좁힌 뒤 선택한 연결을 패킷에서 확인합니다. 포트는 프로토콜을 판단하는 단서 중 하나입니다.

2 · Isolate the TLS phases and keep the evidence at connection level

SPL 
index=zeek sourcetype=zeek:ssl pcap_case="<CASE>" id_orig_h=10.0.0.101
| eval visible_name=coalesce(server_name,"<absent in log>")
| stats dc(uid) as connections min(ts) as first max(ts) as last
    by id_resp_h id_resp_p visible_name
| sort 0 first

Read responder IP, port, visible server name and time span together. In the original capture 19 distinct client ports carried ClientHello messages to 194.165.16.82:443 with the same SNI, between the first one at 21:13:51.409 and the last one at 21:16:04.119 UTC. A missing server name can reflect the handshake or parser coverage. Check selected packets before interpreting it.

SPL 
index=zeek pcap_case="<CASE>" uid="<TLS_UID>" sourcetype IN ("zeek:ssl","zeek:conn")
| sort 0 ts
| table ts sourcetype uid id_orig_p id_resp_h id_resp_p server_name established conn_state orig_bytes resp_bytes missed_bytes

Copy one TLS uid and use it for the corresponding connection record from the same Zeek processing run. If the case was imported twice, select one run first. A different TCP connection has its own UID even when the workstation and SNI recur.

2단계 · TLS 시기별 흐름을 찾고 연결 근거 확인

SPL 
index=zeek sourcetype=zeek:ssl pcap_case="<CASE>" id_orig_h=10.0.0.101
| eval visible_name=coalesce(server_name,"<absent in log>")
| stats dc(uid) as connections min(ts) as first max(ts) as last
    by id_resp_h id_resp_p visible_name
| sort 0 first

응답자 IP, 포트, 관찰 가능한 서버 이름과 시간 범위를 함께 읽습니다. 원본에서 21:13:51.409부터 21:16:04.119 UTC까지 194.165.16.82:443을 향해 서로 다른 클라이언트 포트 19개에서 같은 SNI의 ClientHello가 관찰됐습니다. 서버 이름이 비어 있다면 실제 핸드셰이크와 수집 범위를 확인합니다.

SPL 
index=zeek pcap_case="<CASE>" uid="<TLS_UID>" sourcetype IN ("zeek:ssl","zeek:conn")
| sort 0 ts
| table ts sourcetype uid id_orig_p id_resp_h id_resp_p server_name established conn_state orig_bytes resp_bytes missed_bytes

TLS uid 하나를 가져와 같은 Zeek 처리 실행의 연결 기록을 찾습니다. 캡처를 여러 번 가져왔으면 먼저 한 실행으로 범위를 좁힙니다. 워크스테이션과 SNI가 같아도 TCP 연결마다 UID가 다릅니다.

시각이 가까운 흐름은 호스트에서 추가 확인할 범위를 좁혀 줍니다. 브라우저나 업데이트 도구, 프록시도 연결을 반복하거나 여러 목적지를 사용할 수 있습니다. ClientHello는 TLS 협상 시도를 보여줍니다. HTTP 메서드, 다운로드 파일의 정체와 실행 여부는 별도 근거가 필요합니다.

4 · Read two original ClientHello frames if needed

TShark 
tshark -n -r "2024-11-14-Raspberry-Robin-infection-traffic.pcap" -d tcp.port==9001,tls \
  -Y '(frame.number == 7167 || frame.number == 57882)' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e ip.dst -e tcp.dstport \
  -e tls.handshake.type -e tls.handshake.extensions_server_name

Use this metadata-only check if Arkime leaves the handshake on TCP/9001 unresolved. The decode hint tells the offline analyzer to try TLS on that port. Compare handshake type and server name for the two known frames and verify their tuples. The hint applies to the local read of the existing capture.

4단계 · 필요한 경우 원본 ClientHello 두 건 확인

TShark 
tshark -n -r "2024-11-14-Raspberry-Robin-infection-traffic.pcap" -d tcp.port==9001,tls \
  -Y '(frame.number == 7167 || frame.number == 57882)' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e ip.dst -e tcp.dstport \
  -e tls.handshake.type -e tls.handshake.extensions_server_name

Arkime에서 TCP/9001의 핸드셰이크가 분명하지 않으면 메타데이터만 확인합니다. 디코드 옵션은 해당 포트를 TLS로 분석하도록 지정합니다. 원본 프레임 두 개에서 핸드셰이크 유형, 서버 이름, 주소·포트를 비교합니다. 이 옵션은 기존 캡처의 오프라인 조회에 적용됩니다.

5 · Record the timeline and collect the application evidence

Record the capture hash, workstation, early TLS destination and time span, and later destinations with the supporting frames. Keep the publisher's WebDAV characterization linked to its separate Fiddler evidence. Request proxy or WebDAV logs and endpoint process-network, file-creation and execution telemetry. Verify approved browser, updater or proxy behavior before assigning impact to any destination in a production incident.

5단계 · 타임라인을 기록하고 응용 계층 증거 요청

캡처 해시, 워크스테이션, 초기 TLS의 목적지와 시각 범위, 후속 목적지와 근거 프레임을 기록합니다. 원문의 WebDAV 설명은 별도 Fiddler 근거에 연결합니다. 프록시 또는 WebDAV 로그와 엔드포인트의 프로세스 네트워크·파일 생성·실행 기록을 요청합니다. 운영 환경에서는 승인된 브라우저, 업데이트 또는 프록시 사용과 일치하는지 확인한 뒤 영향을 판단합니다.
