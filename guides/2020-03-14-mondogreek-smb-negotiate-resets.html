How far did each SMB connection get?

Mondogreek provides a capture from an Active Directory network and asks for an incident report. In the original PCAP, 10.3.11.194 reads a policy file from DC 10.3.11.3, then later contacts multiple internal systems on TCP/445. Two peer workstations complete TCP handshakes and reset their connections directly after SMB1 Negotiate requests. Compare those peer attempts with the working policy session.

각 연결은 SMB의 어느 단계까지 진행됐는가?

Mondogreek 실습은 Active Directory 네트워크 캡처를 바탕으로 사고 보고서를 작성하는 사례입니다. 원본에서 10.3.11.194는 DC 10.3.11.3의 정책 파일을 읽고, 이후 내부 시스템 여러 곳의 TCP/445에 접속합니다. 동료 워크스테이션 두 곳은 TCP 핸드셰이크 뒤 SMB1 Negotiate 요청을 받고 곧바로 리셋을 보냅니다. 이 시도들을 정상적으로 진행된 정책 세션과 비교합니다.

1 · Compare the three workstations’ SMB reach

Set <CASE> to the capture tag. Cover the full UTC capture interval. If Splunk filters on ingest time, include that interval and order results by numeric Zeek ts. The examples assume flattened fields.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

Check connection, SMB mapping and SMB file log coverage before comparing the workstations.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp id_resp_p=445
    id_orig_h IN ("10.3.11.194","10.3.11.218","10.3.11.119")
| eval second=floor(ts)
| stats dc(uid) as flows dc(id_resp_h) as peers values(id_resp_h) as responders by second id_orig_h
| sort 0 second

Find the increase in destinations for .194 at 21:36:47 UTC. The original packets show 12 distinct outbound SYN tuples across six internal IPs from 21:36:47.303 through 21:36:47.355. Counts from conn.log group flows by Zeek connection start and can differ from counts of SYN frames. Compare with .218 and .119 as initiators to place the burst in context.

1 · 워크스테이션 세 대의 SMB 접속 범위 비교하기

<CASE>에 캡처 태그를 넣고 UTC로 전체 캡처 구간을 선택합니다. 수집 시각 기준이라면 가져온 구간을 포함하고 숫자형 Zeek ts로 정렬합니다. 예시는 평탄화된 필드명을 사용합니다.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

비교 전 연결, SMB 공유 매핑, 파일 로그의 수집 범위를 확인합니다.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp id_resp_p=445
    id_orig_h IN ("10.3.11.194","10.3.11.218","10.3.11.119")
| eval second=floor(ts)
| stats dc(uid) as flows dc(id_resp_h) as peers values(id_resp_h) as responders by second id_orig_h
| sort 0 second

21:36:47 UTC에 .194의 목적지 수가 늘어나는 구간을 찾습니다. 원본 패킷에서 21:36:47.303부터 21:36:47.355까지 내부 IP 여섯 곳으로 고유한 주소·포트 조합의 SYN 12건이 관찰됩니다. conn.log는 Zeek가 기록한 연결 시작 시각으로 집계하므로 SYN 프레임 수와 다를 수 있습니다. .218, .119가 시작한 세션도 비교해 변화의 범위를 확인합니다.

2 · Identify the last stage reached by each flow

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp id_resp_p=445 id_orig_h=10.3.11.194
| sort 0 ts
| table ts uid id_resp_h id_orig_p conn_state history service duration orig_pkts resp_pkts orig_bytes resp_bytes

Check the state and packet history for the DC, gateway and peer destinations. Look for activity on ports 49921 and 49927. A SYN-ACK confirms a TCP response. Inspect the packets after the handshake to evaluate SMB negotiation separately.

SPL 
index=zeek pcap_case="<CASE>" uid="<SELECTED_UID>"
    sourcetype IN ("zeek:conn","zeek:smb_mapping","zeek:smb_files")
| sort 0 ts
| table ts sourcetype uid id_resp_h id_orig_p id_resp_p conn_state path name action

Query each selected connection with its own UID from the same Zeek processing run. First compare a peer tuple, then the policy session on client port 49683. If application rows are missing, use the packet evidence to determine whether the server sent an SMB reply. TCP reset flags and SMB status codes describe different layers.

For the two peer tuples shown, the capture ends the exchange at a transport reset. It leaves the responding device’s enforcement policy and the initiating process unresolved.

2 · 흐름별로 마지막으로 확인된 단계 찾기

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp id_resp_p=445 id_orig_h=10.3.11.194
| sort 0 ts
| table ts uid id_resp_h id_orig_p conn_state history service duration orig_pkts resp_pkts orig_bytes resp_bytes

DC, 게이트웨이, 피어별 연결 상태와 패킷 이력을 봅니다. 클라이언트 포트 49921과 49927을 확인합니다. SYN-ACK은 TCP 응답을 확인하는 근거입니다. 핸드셰이크 이후 패킷에서 SMB 협상 결과를 별도로 판단합니다.

SPL 
index=zeek pcap_case="<CASE>" uid="<SELECTED_UID>"
    sourcetype IN ("zeek:conn","zeek:smb_mapping","zeek:smb_files")
| sort 0 ts
| table ts sourcetype uid id_resp_h id_orig_p id_resp_p conn_state path name action

선택한 연결마다 동일한 Zeek 처리 실행에서 생성된 해당 UID로 조회합니다. 피어 연결을 조회한 뒤 포트 49683의 정책 연결과 비교합니다. 애플리케이션 로그가 비어 있으면 서버가 SMB 응답을 보냈는지 패킷에서 확인합니다. TCP 리셋 플래그와 SMB 상태 코드는 서로 다른 계층의 결과입니다.

자동화된 SMB 탐색과 부합할 수 있는 패턴입니다. 승인된 스캐너, 구형 소프트웨어 또는 프로토콜 정책을 적용하는 장비에서도 비슷한 현상이 나타날 수 있습니다. 선택한 피어 연결 두 건에서 캡처가 보여 주는 마지막 결과는 TCP 리셋입니다. 어떤 정책이 적용됐는지와 연결을 시작한 프로세스는 추가 확인이 필요합니다.

4 · Confirm the request and reset offline if needed

TShark 
tshark -n -r "2020-03-14-traffic-analysis-exercise.pcap" \
  -Y 'frame.number == 18961 || frame.number == 18962 || frame.number == 18977 || frame.number == 18978' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e tcp.stream \
  -e ip.src -e ip.dst -e smb.cmd -e tcp.flags.reset

If Arkime does not show the SMB command or reset flag clearly, inspect the four original frames. Pair each request and reset by TCP stream, then check direction. This view returns header metadata without accessing SMB contents.
