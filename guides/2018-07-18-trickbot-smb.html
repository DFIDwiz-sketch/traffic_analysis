Findings at a glance

The publication identifies Trickbot moving from 172.16.1.205 to the AD domain controller at 172.16.1.8. Its screenshots also report Tor traffic and a new module. The SMB activity is a separate line of evidence: offline inspection of the original capture found two executable filenames written over SMB1 on the same client-initiated TCP connection. Treat outbound sessions and the internal transfer as separate scopes unless other evidence ties them together.

Evidence Observed value
Original capture 20,761 packets, 17:41:53.165–18:00:37.816 UTC on 18 July 2018
Host pair using TCP/445 1,124 packets in both directions, including control and ACK-only packets
File-write connection 172.16.1.205:49552 → 172.16.1.8:445
Source attribution Trickbot and Tor observations are described by the publisher. SMB frame numbers, file metadata, capture times and hash were independently checked in the original PCAP

The Splunk and Arkime steps below are lab queries and verification steps. The packet observations are from an offline read of the capture.

한눈에 보는 결과

공개 원문은 Trickbot이 172.16.1.205에서 AD 도메인 컨트롤러 172.16.1.8로 이동했다고 보고합니다. 원문에는 Tor 통신과 새 모듈도 나옵니다. 내부 SMB 통신은 별도로 살펴봤습니다. 원본 PCAP에서 클라이언트가 시작한 같은 TCP 연결을 타고 실행 파일 이름 두 개에 대한 SMB1 쓰기가 이뤄졌습니다. 내부 파일 전송과 외부 통신을 연결할 별도 근거가 생기기 전까지는 각각 조사합니다.

근거 관찰값

출처 구분 Trickbot과 Tor는 공개 원문에 근거합니다. SMB 프레임, 파일 메타데이터, 캡처 시각·해시는 원본 PCAP에서 직접 확인했습니다.

아래 Splunk와 Arkime 절차는 실습 환경에서 돌려 볼 쿼리입니다. 표에 나오는 패킷은 원본 캡처를 오프라인에서 읽어 확인했습니다.

1 · Establish scope in Splunk

Ingest only the original PCAP. Use UTC and a time range that includes the capture. Replace <CASE> with your importer’s pcap_case value. The examples use the flattened Zeek address and port fields described in the site's PCAP Baselining Guide.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

Review each sourcetype and its time range. ts from a Zeek connection record is the connection’s start time. The packet-level capture boundaries in the findings table refer to the entire PCAP.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp id_resp_p=445
| stats count as connections sum(orig_bytes) as sent sum(resp_bytes) as received
    values(conn_state) as states by id_orig_h id_resp_h
| sort - connections

The direction filter highlights initiators of TCP/445. Compare this host pair against other destinations before drawing a conclusion, then open the connections for 172.16.1.205 and 172.16.1.8. The first matching client SYN in the raw capture is frame 5218 at 17:49:57.734 UTC. The executable-file evidence appears a few seconds later.

1단계 · Splunk에서 케이스 범위 좁히기

원본 PCAP을 수집하고 시간대를 UTC로 맞춘 뒤 캡처 시각을 포함해 검색합니다. <CASE>는 수집기가 붙인 pcap_case 값으로 바꾸세요. 쿼리는 이 사이트의 PCAP 베이스라이닝 가이드와 같은 Zeek 필드 이름을 사용합니다.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

로그 종류와 각 시간 범위를 봅니다. Zeek 연결 로그의 ts는 연결이 시작한 시각입니다. 앞의 표에 나온 캡처 경계는 전체 PCAP의 패킷을 기준으로 합니다.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp id_resp_p=445
| stats count as connections sum(orig_bytes) as sent sum(resp_bytes) as received
    values(conn_state) as states by id_orig_h id_resp_h
| sort - connections

목적지 포트가 445인 연결을 보고 누가 시작했는지 파악합니다. 다른 목적지와 비교한 뒤 172.16.1.205와 172.16.1.8 두 주소 사이를 확인합니다. 원본에서 첫 클라이언트 SYN은 17:49:57.734 UTC의 5218번 프레임이며, 몇 초 뒤 실행 파일과 관련된 쓰기가 관찰됩니다.

2 · Link shares, files and RPC

SPL 
index=zeek pcap_case="<CASE>" id_orig_h=172.16.1.205 id_resp_h=172.16.1.8
    id_orig_p=49552 id_resp_p=445
    sourcetype IN ("zeek:conn","zeek:smb_mapping","zeek:smb_files","zeek:dce_rpc","zeek:ntlm")
| sort 0 ts
| eval time_utc=strftime(ts,"%Y-%m-%d %H:%M:%S.%3N %Z")
| table time_utc sourcetype uid conn_state path name action endpoint operation

Correlate the zeek:conn record for client port 49552 by its uid with available SMB mapping, file and RPC records from the same Zeek run. Inspect action with path and name so a share or file open is not mistaken for a data write. If the Zeek SMB analyzer gives little detail, narrow the raw packets in Arkime.

2단계 · 공유, 파일 작업, RPC를 연결하기

SPL 
index=zeek pcap_case="<CASE>" id_orig_h=172.16.1.205 id_resp_h=172.16.1.8
    id_orig_p=49552 id_resp_p=445
    sourcetype IN ("zeek:conn","zeek:smb_mapping","zeek:smb_files","zeek:dce_rpc","zeek:ntlm")
| sort 0 ts
| eval time_utc=strftime(ts,"%Y-%m-%d %H:%M:%S.%3N %Z")
| table time_utc sourcetype uid conn_state path name action endpoint operation

클라이언트 포트 49552의 zeek:conn 기록을 찾아 같은 Zeek 처리 실행에서 생성된 공유·파일·RPC 로그를 uid로 연결합니다. action을 path, name과 함께 봐야 공유나 파일을 연 것과 데이터를 쓴 것을 구분할 수 있습니다. Zeek SMB 로그에 필요한 정보가 적으면 Arkime에서 원본 패킷을 좁혀 봅니다.

파일명은 줄여 적었습니다. 파일 열기와 쓰기 메타데이터를 연결해 확인했습니다. svcctl이 보이면 엔드포인트에서 서비스 관련 기록을 확인할 근거가 됩니다. 이름 파이프에 쓰기가 관찰됐다는 사실만으로 어떤 서비스가 설치되거나 실행됐는지 판단할 수 없습니다.

3 · Corroborate the timeline in Arkime

Arkime 
tags == "<CASE>" &&
ip.src == 172.16.1.205 && ip.dst == 172.16.1.8 &&
port.src == 49552 && port.dst == 445

Set the time picker around 17:50:08 UTC. The filter narrows the session to the verified client port and DC. Compare the endpoints and packet activity with the Splunk results. Keep any Tor or other outbound-traffic investigation in its own pivot so it does not get counted as part of this SMB transfer.

3단계 · Arkime에서 타임라인 교차 확인

Arkime 
tags == "<CASE>" &&
ip.src == 172.16.1.205 && ip.dst == 172.16.1.8 &&
port.src == 49552 && port.dst == 445

17:50:08 UTC 전후를 선택합니다. 필터는 확인된 클라이언트 포트와 DC로 세션을 좁혀 줍니다. 양 끝 주소와 패킷 흐름을 Splunk 결과와 대조하세요. Tor 등 외부 통신은 별도의 검색으로 조사해 이 SMB 전송의 패킷이나 세션 수에 섞이지 않도록 합니다.

4 · Resolve the SMB1 write response with TShark if needed

TShark 
tshark -n -r "2018-07-18-Trickbot-infection-in-AD-environment.pcap" \
  -Y 'ip.addr == 172.16.1.205 && ip.addr == 172.16.1.8 && tcp.port == 49552 && smb.cmd == 0x2f' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e ip.src \
  -e ip.dst -e tcp.stream -e smb.cmd -e smb.mid -e smb.nt_status

Focus on the request-reply pair for the first executable filename. A zero response status supports a successful write operation. Compare the SMB Multiplex ID within the same connection rather than treating nearby packets as a match. Frame references are for the SHA-256 listed below. Reassembly may change where a dissector displays a message.

4단계 · 필요할 때 TShark로 SMB1 쓰기 응답 확인

TShark 
tshark -n -r "2018-07-18-Trickbot-infection-in-AD-environment.pcap" \
  -Y 'ip.addr == 172.16.1.205 && ip.addr == 172.16.1.8 && tcp.port == 49552 && smb.cmd == 0x2f' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e ip.src \
  -e ip.dst -e tcp.stream -e smb.cmd -e smb.mid -e smb.nt_status

첫 실행 파일의 요청·응답을 확인합니다. 응답 상태값 0은 성공한 쓰기의 근거입니다. 프레임이 가까운 것만으로 짝을 정하지 말고 같은 연결의 SMB Multiplex ID를 비교합니다. 프레임 번호는 아래 SHA-256의 파일을 기준으로 하며, 재조립에 따라 디섹터가 메시지를 표시하는 프레임이 달라질 수 있습니다.

5 · Write the incident note

Record the client and DC, the file-write connection, the two write times, and the named-pipe observation. Report the publisher’s Trickbot attribution separately and use DC process, file and service telemetry to assess execution. Compare with approved software deployment activity before treating administrative share traffic as malicious in a new case.
