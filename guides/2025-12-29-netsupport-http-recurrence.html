Which destination shows recurring HTTP activity?

The publisher describes a ClickFix infection leading to NetSupport RAT, with an initial HTTP POST to a shared edge address followed by recurring POSTs to a different destination. In the original capture, 10.12.29.101 sends one observed POST to 104.21.96.46:443 and receives HTTP 400. It also sends recurring plaintext HTTP POSTs to 185.39.19.96:443 on a separate TCP connection. The publisher's role attribution and the packet-visible behavior are separate pieces of evidence.

어느 목적지에서 HTTP 요청이 반복됐나

공개 원문은 ClickFix로 시작해 NetSupport RAT으로 이어진 사례를 소개합니다. 처음에는 공유 인프라 주소로 HTTP POST를 한 차례 보내고, 이후 다른 목적지로 POST가 반복됐다고 설명합니다. 원본 PCAP에서 10.12.29.101이 104.21.96.46:443으로 보낸 POST 한 건에는 HTTP 400이 돌아왔습니다. 별도 TCP 연결의 185.39.19.96:443에서는 평문 HTTP POST가 반복됐습니다. 각 목적지의 역할에 대한 원문의 해석과 패킷에서 확인한 동작을 각각 기록합니다.

악성코드 계열과 캠페인 설명은 공개 원문에 근거합니다. 요청 시각, 연결 주소·포트, 선택한 응답과 반복 여부는 원본 PCAP에서 확인했습니다. 검색 예제는 자신의 수집 환경에서 검증합니다.

1 · Set the workstation baseline in Splunk

Set UTC in Splunk and replace <CASE> with the tag applied during import. Search the full capture interval. If _time is stored as ingest time, adjust the picker and use numeric Zeek ts for packet-era timestamps. The searches use flattened fields.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

Check for connection and HTTP logs. A missing HTTP row can result from protocol recognition or input settings. TCP/443 can carry plaintext HTTP, as confirmed in the packet view for these connections.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" id_orig_h=10.12.29.101 proto=tcp
| eval minute=floor(ts/60)*60
| stats count as connections dc(id_resp_h) as destinations values(id_resp_p) as ports by minute
| sort 0 minute

Review destination counts and ports per minute. The query counts connection records by their start time. A long-lived connection can continue sending requests after its initial minute, so use HTTP transaction times to measure recurrence.

1단계 · Splunk에서 워크스테이션 베이스라인 확인

Splunk 표시 시간대를 UTC로 설정하고 <CASE>에 가져올 때 붙인 태그를 넣습니다. 전체 캡처 구간을 검색합니다. _time이 수집 시각이면 범위를 조정하고 사건 시각은 숫자형 Zeek ts로 읽습니다. 예제는 평탄화된 필드를 사용합니다.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

연결과 HTTP 로그가 조회되는지 확인합니다. HTTP 행이 없으면 분석기의 프로토콜 인식과 수집 설정을 점검합니다. 이 사례에서는 TCP/443에서 평문 HTTP를 패킷으로 확인했습니다.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" id_orig_h=10.12.29.101 proto=tcp
| eval minute=floor(ts/60)*60
| stats count as connections dc(id_resp_h) as destinations values(id_resp_p) as ports by minute
| sort 0 minute

분마다 목적지 수와 포트를 봅니다. 이 검색은 연결 시작 시각으로 연결 행을 집계합니다. 오래 열린 연결은 시작한 분 이후에도 요청을 보낼 수 있으므로 반복 여부는 HTTP 트랜잭션 시각으로 확인합니다.

2 · Rank HTTP destinations and check the recurring stream

SPL 
index=zeek sourcetype=zeek:http pcap_case="<CASE>" id_orig_h=10.12.29.101 id_resp_p=443 method=POST
    id_resp_h IN ("104.21.96.46","185.39.19.96")
| stats count as posts dc(uid) as connections values(status_code) as response_codes
        min(ts) as first max(ts) as last by id_resp_h
| sort 0 - posts

Compare POST count, distinct UIDs, first and last timestamps, and available reply codes. The original PCAP contains 85 distinct packet-start POST request headers to the recurring endpoint on source port 57735, counted once per TCP sequence position on that connection. This is a measurement from packet headers. Zeek's transaction count can differ because it uses its own stream parsing.

SPL 
index=zeek pcap_case="<CASE>" uid="<HTTP_UID>" sourcetype IN ("zeek:conn","zeek:http")
| sort 0 ts
| table ts sourcetype uid id_orig_p id_resp_h id_resp_p trans_depth method status_code request_body_len

Use one HTTP UID to look up its connection in the same Zeek processing run. Use trans_depth where present to distinguish requests on one connection. The earlier edge attempt and recurring session each have their own UID. Compare them by workstation address and time.

2단계 · HTTP 목적지를 비교하고 반복 연결 확인

SPL 
index=zeek sourcetype=zeek:http pcap_case="<CASE>" id_orig_h=10.12.29.101 id_resp_p=443 method=POST
    id_resp_h IN ("104.21.96.46","185.39.19.96")
| stats count as posts dc(uid) as connections values(status_code) as response_codes
        min(ts) as first max(ts) as last by id_resp_h
| sort 0 - posts

POST 수, 고유 UID 수, 최초와 최종 시각, 수집된 응답 코드를 확인합니다. 원본에서는 출발지 포트 57735의 연결에서 패킷 시작부에 보이는 POST 요청 헤더가 85개였습니다. 같은 TCP 시퀀스 위치는 한 번만 셌습니다. 이 값은 패킷 헤더 기준이고, Zeek의 트랜잭션 집계는 스트림 파싱 방식에 따라 다를 수 있습니다.

SPL 
index=zeek pcap_case="<CASE>" uid="<HTTP_UID>" sourcetype IN ("zeek:conn","zeek:http")
| sort 0 ts
| table ts sourcetype uid id_orig_p id_resp_h id_resp_p trans_depth method status_code request_body_len

HTTP UID 하나를 선택해 같은 Zeek 처리 실행의 연결 기록을 찾습니다. trans_depth가 있으면 연결 하나의 여러 요청을 구분합니다. 처음 공유 인프라로 향한 TCP 연결과 반복 요청을 보낸 연결은 UID가 서로 다릅니다. 두 흐름은 워크스테이션 IP와 시각으로 대조합니다.

단발 HTTP 400과 반복 트래픽을 구분하면 후속 조사 우선순위를 정할 수 있습니다. HTTP 오류는 그 교환의 응답을 설명합니다. 승인된 원격 지원이나 애플리케이션 폴링도 주기적으로 발생할 수 있습니다. 실행 여부, 운영 주체와 POST 데이터의 의미는 별도 근거로 확인합니다.

4 · Confirm two HTTP exchanges offline if needed

TShark 
tshark -n -r "2025-12-29-ClickFix-page-sends-NetSupportRAT.pcap" -d tcp.port==57734,http -d tcp.port==57735,http \
  -Y '(frame.number == 24779 || frame.number == 24781 || frame.number == 24789 || frame.number == 24790)' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e ip.src -e ip.dst \
  -e tcp.stream -e http.request.method -e http.response.code

If Arkime labels TCP/443 ambiguously, this offline example applies the HTTP decoder only to the two confirmed client port numbers and displays metadata for four original frames. Compare TCP stream, direction, method and status. The filter leaves message bodies out of the output.

4단계 · 필요한 경우 두 HTTP 교환을 오프라인 확인

TShark 
tshark -n -r "2025-12-29-ClickFix-page-sends-NetSupportRAT.pcap" -d tcp.port==57734,http -d tcp.port==57735,http \
  -Y '(frame.number == 24779 || frame.number == 24781 || frame.number == 24789 || frame.number == 24790)' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e ip.src -e ip.dst \
  -e tcp.stream -e http.request.method -e http.response.code

Arkime에서 TCP/443의 프로토콜이 불분명하면 확인된 클라이언트 포트 두 개에만 HTTP 디코더를 적용하고 원본 프레임 네 개의 메타데이터를 읽습니다. TCP 스트림, 방향, 메서드와 응답 상태를 대조합니다. 출력은 이 메타데이터로 제한됩니다.

5 · Record priority and collect corroboration

Record the capture hash, both endpoints and tuples, request counts, time range and example responses. Keep shared infrastructure separate from the recurring destination in the ticket. Ask for process-network telemetry, approved remote-support inventory, proxy records and file-creation or execution evidence. Confirm scope and business ownership before drawing conclusions about the operator or taking action against a shared address.

5단계 · 우선순위를 기록하고 추가 근거 요청

캡처 해시, 두 목적지와 연결 주소·포트, 요청 건수, 시각, 대표 응답을 기록합니다. 공유 인프라 주소와 반복 요청의 목적지를 티켓에서 별도로 적습니다. 프로세스 네트워크 기록, 승인된 원격지원 목록, 프록시 기록, 파일 생성·실행 증거를 요청합니다. 운영 주체를 지목하거나 공유 주소에 조치하기 전에 범위와 업무 소유자를 확인합니다.
