Overview

Baselining means getting to know a capture before investigating suspicious activity. Establish when it was collected, which logs are available, which internal hosts appear, what their traffic looks like, and how to identify them. This makes unusual behavior easier to spot and gives you evidence for the affected-host details in an incident ticket.

For each step, start with the purpose, read the Splunk query line by line, then interpret its results. Use Arkime for a packet-level cross-check where helpful.

  1. Confirm the case is searchable.
  2. List the Zeek log types.
  3. Establish the observed connection window.
  4. Count connections and destinations by originating IP.
  5. Cross-check with Arkime.
  6. Identify the host, account, and domain.

Two principles

  • Work in UTC. Set Splunk’s user time zone to UTC in Preferences and Arkime’s time zone to UTC under Settings. Formatting a timestamp in Adelaide time gives a different displayed time, with the offset depending on the date.
  • Use Zeek’s ts to order events. Zeek records event time as seconds since the Unix epoch. Splunk’s _time is the event timestamp assigned during indexing. A missing or unrecognized source timestamp can cause ingestion time to be used. Use ts for this workflow, and check the Splunk time picker if older capture events are missing. Use eval t=strftime(ts,"%H:%M:%S") to format a time for display.

Field names used throughout the guide

Field Meaning
id_orig_h / id_orig_p Originator IP address and port
id_resp_h / id_resp_p Responder IP address and port
orig_bytes / resp_bytes Payload bytes sent by the originator and responder, respectively
ts Event time in epoch seconds
pcap_case Lab-specific case field assigned by pcapbox from the PCAP filename without its extension

개요

베이스라이닝은 악성 행위를 찾기 전에 PCAP의 평소 모습(시간 범위, 로그 종류, 내부 PC, 통신량, PC 정체)을 먼저 파악하는 단계예요. 이걸 알아야 이상한 것이 눈에 띄고, 티켓의 호스트 정보(IP, 호스트 이름, 사용자)를 채울 수 있어요.

순서는 아래와 같아요. 단계마다 목적 → Splunk 쿼리 → 한 줄씩 설명 → 결과 읽기 → (필요하면) Arkime 확인 순서로 진행해요.

  1. 0단계 — 케이스 확인: 이번 PCAP의 로그만 골라 볼 수 있는지
  2. 1-1 — 로그 종류: Zeek가 어떤 프로토콜을 알아봤는지
  3. 1-2 — 캡처 시간 범위: 언제부터 언제까지인지
  4. 1-3 — 내부 IP: PC가 몇 대이고 각각 얼마나 통신하는지
  5. 1-4 — Arkime 교차 확인: 같은 그림인지, 눈에 띄는 줄이 있는지
  6. 1-5 — 호스트 정체: 호스트 이름, 사용자, 도메인

두 가지 원칙

  • 시간대는 UTC. Splunk는 Preferences → Time zone = UTC, Arkime는 Settings → General → Timezone = UTC로 맞춰요. strftime()은 Splunk 사용자 시간대를 따르기 때문에, 애들레이드처럼 UTC와 다른 시간대를 사용하면 날짜에 따라 표시 시간이 달라져요.
  • 이벤트 시간은 ts로 봐요. ts는 Zeek가 기록한 이벤트 시간(1970-01-01부터 센 초, epoch)이에요. Splunk의 _time은 인덱싱할 때 정해지는 이벤트 시간이에요. 원본 타임스탬프를 인식하지 못하면 수집 시각이 쓰일 수 있어요. 실습에서는 정렬과 출력에 ts를 사용하고, 검색 결과가 비어 있으면 Splunk 시간 선택기에서 해당 이벤트를 포함하는지 확인해요. 읽을 때는 eval t=strftime(ts,"%H:%M:%S")로 바꿔요.

Zeek 필드 이름 규칙 — 모든 쿼리에 나오니 먼저 외워 두면 편해요.

필드 뜻
id_orig_h / id_orig_p 연결을 시작한 쪽의 IP / 포트 (orig = originator)
id_resp_h / id_resp_p 연결을 받은 쪽의 IP / 포트 (resp = responder)
orig_bytes / resp_bytes 시작한 쪽 / 응답한 쪽이 보낸 페이로드 바이트
ts 이벤트 시간 (epoch 초)
pcap_case pcapbox가 붙인 케이스 이름 (= PCAP 파일 이름에서 .pcap을 뺀 것)

Step 0 · Confirm the case

In this lab, name the capture after the case before ingesting it into pcapbox. For example, use 20180630_SORTING_THROUGH_THE_ALERTS.pcap. Each log gets the same pcap_case value so you can isolate the capture even when multiple exercises share one index.

  1. Place the file in your lab’s capture intake folder, such as incoming.
  2. On the lab’s pcapbox, watch tail -f /data/logs/ingest.log until DONE case=<case> appears. The sha256= value on the START line records the evidence hash.
  3. Check that the case appears in Splunk. Select a search time range wide enough to include older practice captures.
SPL 
index=zeek sourcetype=zeek:conn
| stats count by pcap_case
  • index=zeek limits the search to the index holding Zeek logs.
  • sourcetype=zeek:conn selects connection records, the starting point for this baseline.
  • A pipe, |, passes the current results to the next SPL command.
  • stats count by pcap_case counts records in each case, similar to grouping rows in a pivot table.

If the case appears, continue. You can use a search such as pcap_case=20180630_SORTING* when the prefix uniquely identifies the case. In Arkime, use the exact case tag with tags ==.

0단계 — 케이스 확인

PCAP을 pcapbox에 넣기 전에 파일 이름을 케이스 이름으로 바꿔요(예: 20180630_SORTING_THROUGH_THE_ALERTS.pcap). 그러면 모든 로그에 같은 pcap_case 값이 붙어서, 여러 실습 로그가 한 인덱스에 섞여 있어도 나눌 수 있어요.

  1. 파일을 실습 환경의 PCAP 수집 폴더(예: incoming)에 넣어요.
  2. pcapbox에서 tail -f /data/logs/ingest.log를 보다가 DONE case=<케이스>가 나오면 끝이에요. START 줄의 sha256= 값이 증거 해시예요.
  3. Splunk에 들어왔는지 확인해요. 오래된 실습 캡처라면 검색 시간 범위를 먼저 넓혀요.
SPL 
index=zeek sourcetype=zeek:conn
| stats count by pcap_case
  • index=zeek — Zeek 로그가 들어 있는 인덱스(Splunk의 "서랍")만 봐요.
  • sourcetype=zeek:conn — conn 로그만 봐요. 연결 하나가 한 줄이라서 가장 기본이 되는 로그예요.
  • | (파이프) — 왼쪽 결과를 오른쪽 명령으로 넘겨요.
  • stats count by pcap_case — pcap_case 값마다 줄 수를 세요. 엑셀의 피벗 테이블과 비슷해요.

목록에 케이스 이름이 보이면 준비 끝이에요. 케이스 이름이 길어서 오타가 나기 쉽다면 Splunk에서는 pcap_case=20180630_SORTING*처럼 와일드카드(* = 아무 글자)를 써도 돼요. 다른 케이스와 겹치지 않을 때만 쓰세요. Arkime의 tags ==에는 전체 이름을 써요.

1-1 · Inventory Zeek logs

Purpose. Find out which protocols and types of activity Zeek recognized. That tells you where to look next.

SPL 
index=zeek pcap_case=<CASE>
| stats count by sourcetype
| sort - count
  • The first line searches the case across all sourcetypes.
  • stats count by sourcetype counts the records of each kind.
  • sort - count puts the highest counts first. An explicit + sorts in ascending order.
Log What it records Where it helps
zeek:conn Endpoints, ports, byte counts, and connection state Establish the starting baseline
zeek:dns DNS questions and answers Link observed addresses and names
zeek:http Visible HTTP fields such as Host, URI, User-Agent, Referer, and lengths Trace web activity or candidate C2
zeek:ssl / zeek:x509 TLS metadata, including available server names and certificates Identify possible peers for encrypted traffic
zeek:files Observed files and their available size, MIME type, and hashes Inspect file transfers
zeek:ocsp Certificate status checks Recognize routine certificate-validation traffic
zeek:dhcp Lease traffic that may contain hostnames and MAC addresses Identify hosts
zeek:kerberos / zeek:ntlm Windows domain authentication activity Identify accounts and computers
zeek:ldap, zeek:ldap_search, zeek:dce_rpc, zeek:smb_mapping, zeek:smb_files Directory queries, group policy, file shares, and other internal activity Establish a baseline for investigating possible lateral movement
zeek:software Detected applications and version information Compare software observed in the capture
zeek:ntp Time synchronization Identify common infrastructure traffic
zeek:weird Unexpected protocol behavior detected by Zeek Check the protocol context before drawing a conclusion

Read the results

  • Missing DHCP can mean the host already had a lease or that the exchange was outside the capture. Use the other host-identification sources in step 1-5.
  • High HTTP or TLS counts can reflect browsing or other applications. Visible HTTP fields can help trace what requested a resource.
  • Kerberos, LDAP, and SMB together can indicate an Active Directory environment. Use them as leads for account attribution and for later investigation of internal activity.

1-1. 어떤 로그가 있나

목적: Zeek가 이 PCAP에서 어떤 프로토콜을 알아봤는지 봐요. 어떤 로그가 있느냐에 따라 다음 단계에서 어디를 볼지 정해져요.

SPL 
index=zeek pcap_case=<케이스>
| stats count by sourcetype
| sort - count
  • 1줄: sourcetype을 지정하지 않아서 이 케이스의 모든 종류의 로그를 가져와요.
  • 2줄: 로그 종류(sourcetype)마다 줄 수를 세요.
  • 3줄: sort - count — 많은 순서로 정렬해요. -는 내림차순, +(또는 생략)는 오름차순이에요.

로그별 뜻과 쓰는 곳

로그 알려 주는 것 쓰는 곳
zeek:conn 모든 연결(누가, 누구에게, 몇 번 포트, 얼마나, 어떻게 끝났는지) 모든 단계의 기본
zeek:dns 이름 조회와 답(IP) IP 뒤의 도메인 이름 찾기
zeek:http 암호화 안 된 웹 요청: URL, Host, User-Agent, Referer, 크기 감염 경로, C2 찾기
zeek:ssl / zeek:x509 HTTPS 연결의 서버 이름(SNI)과 인증서 암호화된 통신의 상대 확인
zeek:files 오간 파일의 크기, 형식(MIME), 해시 다운로드된 파일 확인
zeek:ocsp 인증서가 취소됐는지 확인하는 요청 보통 정상(브라우징하면 자동으로 생김)
zeek:dhcp PC가 IP를 받을 때 보낸 호스트 이름과 MAC 호스트 이름 찾기
zeek:kerberos / zeek:ntlm 윈도우 도메인 로그온 사용자와 컴퓨터 이름 찾기
zeek:ldap / zeek:ldap_search / zeek:dce_rpc / zeek:smb_mapping / zeek:smb_files PC와 DC의 평소 대화(그룹 정책, 디렉터리 조회, 공유 폴더) 내부 확산 확인
zeek:software 트래픽에서 알아낸 프로그램 이름과 버전(브라우저 등) 평소와 다른 프로그램 찾기
zeek:ntp 시간 맞추기 보통 정상
zeek:weird Zeek가 보기에 프로토콜 규칙에 안 맞는 패킷 대부분 별일 아님

결과 읽기

  • 없는 로그도 정보예요. 예를 들어 zeek:dhcp가 없으면 캡처가 시작되기 전에 PC가 이미 IP를 받았거나, 캡처 범위에서 DHCP 교환을 관찰하지 못했을 수 있어요. 그러면 호스트 이름은 1-5의 다른 방법으로 찾아요.
  • 웹 로그(http, ssl)가 많으면 브라우징이나 웹을 사용하는 프로그램이 있었을 수 있어요. http는 내용까지 볼 수 있어서 가장 중요한 재료예요.
  • 도메인 로그(kerberos, ldap, smb_*)가 있으면 AD 환경이에요. 사용자 이름을 찾을 수 있고, 나중에 내부 확산도 확인해야 해요.

1-2 · Establish the time window

Purpose. Find the times of the earliest and latest observed connection starts. In conn.log, ts is the time of the first packet of each connection. Use the timestamps on the first and last packets of the capture for the exact PCAP boundaries.

SPL 
index=zeek sourcetype=zeek:conn pcap_case=<CASE>
| stats min(ts) as first max(ts) as last count as sessions
| eval duration_min=round((last-first)/60,1)
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S"), last=strftime(last,"%Y-%m-%d %H:%M:%S")
  • The first line selects connection logs for this case.
  • min(ts), max(ts), and count produce one summary row with the earliest start, latest start, and number of connection records. as gives each result a useful name.
  • (last-first)/60 converts the elapsed seconds to minutes. round(...,1) rounds to one decimal place.
  • strftime() formats the numeric timestamps for reading. For example, %Y-%m-%d produces 2018-06-30, and %H:%M:%S produces 20:27:15.

Calculate the duration before formatting the timestamps. The formatted values are strings.

Read the results

  • A short capture might cover the whole incident or start after the first suspicious activity. Preserve that uncertainty in the report.
  • If the times differ from Arkime by a fixed offset, check that both tools are displaying UTC.
  • Zeek’s connection count may differ from Arkime’s session count because the tools can group traffic differently or use different filters. This exercise reports the Splunk count and records the Arkime count separately.

1-2. 캡처 시간 범위

목적: Zeek 연결이 관찰된 시간대를 파악해요. conn 로그의 ts는 각 연결의 첫 패킷 시각이므로 아래 쿼리는 첫 연결과 마지막으로 시작된 연결의 범위를 구해요. PCAP 자체의 정확한 시작과 끝은 첫 패킷과 마지막 패킷의 타임스탬프로 확인해요.

SPL 
index=zeek sourcetype=zeek:conn pcap_case=<케이스>
| stats min(ts) as first max(ts) as last count as sessions
| eval duration_min=round((last-first)/60,1)
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S"), last=strftime(last,"%Y-%m-%d %H:%M:%S")
  • 1줄: 이 케이스의 conn 로그만 가져와요.
  • 2줄: 전체를 한 줄로 요약해요. min(ts) as first는 가장 이른 시간, max(ts) as last는 가장 늦은 시간, count as sessions는 연결 수예요. as는 결과에 새 이름을 붙여요.
  • 3줄: eval은 새 필드를 계산해요. (last-first)/60은 초를 분으로 바꾸고, round(…, 1)은 소수점 한 자리로 반올림해요.
  • 4줄: strftime(숫자, "형식")은 epoch 숫자를 읽을 수 있는 날짜로 바꿔요. %Y-%m-%d = 2018-06-30, %H:%M:%S = 20:27:15.

순서가 중요해요. 3줄(계산)을 4줄(글자로 바꾸기)보다 먼저 둬야 해요. 4줄을 지나면 first와 last가 글자가 되어서 뺄셈을 할 수 없어요.

결과 읽기

  • 캡처 길이가 짧으면(수십 분) 악성 행위의 시작부터 끝까지가 다 들어 있을 수도 있고, 감염이 캡처 전에 일어났을 수도 있어요. 둘 다 염두에 둬요.
  • 시간에 일정한 차이가 나면 먼저 Splunk 시간대가 UTC인지 확인해요.
  • Zeek의 연결 수는 다른 도구(Arkime 등)의 세션 수와 다를 수 있어요. 세션을 나누는 방식이나 필터 범위가 다를 수 있어요. 이 실습에서는 Splunk 숫자를 기준으로 기록해요.

1-3 · Identify internal connection originators

Purpose. See which hosts initiated traffic, how many destinations they reached, and how much data flowed in each direction. The query groups all originators. Compare the returned addresses with the capture’s internal network range.

SPL 
index=zeek sourcetype=zeek:conn pcap_case=<CASE>
| stats count as sessions dc(id_resp_h) as destinations sum(orig_bytes) as sent sum(resp_bytes) as received min(ts) as first max(ts) as last by id_orig_h
| eval first=strftime(first,"%H:%M:%S"), last=strftime(last,"%H:%M:%S")
| sort - sessions
  • count as sessions counts connections associated with each originator.
  • dc(id_resp_h) as destinations counts distinct responder IP addresses.
  • sum(orig_bytes) and sum(resp_bytes) total sent and received payload bytes for the originator.
  • min(ts) and max(ts) provide the first and last recorded connection start for each IP.
  • by id_orig_h makes a row per originator. The final sort brings the busiest originators to the top.
Observation How to interpret it
One internal IP initiates traffic Prioritize the observed host, while considering what the capture covers
The DC is absent from the list or rarely initiates traffic A server often responds to requests. Its replies can appear under the client that initiated the flow
A few destinations recur at regular intervals A possible beacon. Check timing, protocol, and the expected purpose of the traffic
Dozens or hundreds of destinations Browsing can load many third-party services and CDNs. Use context alongside volume
Received bytes far exceed sent bytes Common during browsing and downloads
Sent bytes far exceed received bytes Examine legitimate uploads, backups, and possible exfiltration. Volume by itself is insufficient

1-3. 어떤 내부 IP가 연결을 시작하나

목적: 네트워크에 PC가 몇 대인지, 각 PC가 얼마나 바쁜지 봐요. 조사할 호스트를 고르는 첫걸음이에요. 아래 쿼리는 내부·외부 구분 없이 모든 연결 시작 IP를 모으므로, 결과를 실습의 내부 네트워크 범위와 대조해요.

SPL 
index=zeek sourcetype=zeek:conn pcap_case=<케이스>
| stats count as sessions dc(id_resp_h) as destinations sum(orig_bytes) as sent sum(resp_bytes) as received min(ts) as first max(ts) as last by id_orig_h
| eval first=strftime(first,"%H:%M:%S"), last=strftime(last,"%H:%M:%S")
| sort - sessions
  • count as sessions — 그 IP가 시작한 연결 수
  • dc(id_resp_h) as destinations — 서로 다른 목적지 IP 수. dc = distinct count(중복 빼고 세기)
  • sum(orig_bytes) as sent / sum(resp_bytes) as received — 보낸 / 받은 데이터 바이트 합계
  • min(ts) / max(ts) — 그 IP의 첫 연결과 마지막 연결 시간
  • by id_orig_h — 위 계산을 시작한 IP마다 따로 해요.
  • sort - sessions — 연결이 많은 IP를 맨 위로 올려요.

결과 읽기 — 이렇게 판단해요

보이는 모습 뜻
내부 IP가 한 개뿐 이 캡처에서 한 대의 내부 PC가 연결을 시작했어요. 그 PC를 우선 조사해요.
DC가 목록에 없거나 연결이 아주 적음 정상. 서버는 보통 요청을 받는 쪽이라서. Zeek는 UDP도 먼저 보낸 쪽을 orig로 정해서, DC의 응답은 PC가 시작한 연결에 들어가요
목적지가 1–3곳, 일정한 간격 비콘(C2) 후보. 반복 간격과 통신 목적을 더 확인해요.
목적지가 수십~수백 곳 사람이 웹을 본 모습. 뉴스 사이트 하나가 광고·CDN을 수십 곳 불러요. 이때는 "많이 통신한 곳 = 악성"이 통하지 않아요. 정상을 하나씩 지워서 찾아요
받은 양 ≫ 보낸 양 브라우징이나 다운로드에서 볼 수 있어요.
보낸 양 ≫ 받은 양 업로드, 백업, 데이터 유출 등을 검토해요. 전송량만으로 판단할 수는 없어요.

1-5 · Identify hosts and accounts

Determine the host name, user and domain for Impacted Internal Machines. Compare at least two relevant sources where possible. Tie the evidence to the same IP and time window before calling a match confirmed.

DHCP

SPL 
index=zeek sourcetype=zeek:dhcp pcap_case=<CASE>
| eval t=strftime(ts,"%H:%M:%S")
| table t client_addr assigned_addr mac host_name domain msg_types
  • host_name is the name supplied by the client. domain is the domain supplied by DHCP.
  • table shows selected fields for individual events. Aggregation commands such as stats group events.
  • If there is no DHCP record, the host may already have had an address or the exchange may be outside the capture. Continue with the sources below.

Kerberos

SPL 
index=zeek sourcetype=zeek:kerberos pcap_case=<CASE>
| stats min(ts) as first count values(request_type) as types values(success) as success values(error_msg) as errors by client
| sort first
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S")
  • client identifies the requesting principal. Its representation can include an account and realm.
  • values() lists distinct observations for the grouped principal. Sorting uses the numeric ts result before it is formatted.
  • AS requests the initial ticket-granting ticket. TGS requests a service ticket. AP presents a ticket to a service.
Observed value Interpretation
Name ending in $ such as NAME$ Typically a computer account. Use it as a hostname lead
A name without $, such as first.last Often a user account. Verify against the other logs
A blank client name in an AP record The name can be inside encrypted data and unavailable to Zeek
Differences in case or realm Case can be a naming variation. Verify differences in realm before merging accounts
KDC_ERR_PREAUTH_REQUIRED followed by success Can be a normal pre-authentication exchange
KDC_ERR_PREAUTH_FAILED Pre-authentication failed. Investigate repeated failures in context

NTLM

SPL 
index=zeek sourcetype=zeek:ntlm pcap_case=<CASE>
| eval t=strftime(ts,"%H:%M:%S")
| table t id_orig_h id_resp_h id_resp_p username hostname domainname server_nb_computer_name success
  • username, hostname, and domainname can identify the account, originating system, and domain.
  • server_nb_computer_name is the responder’s NetBIOS name. It can help confirm the DC in this exercise.
  • If the account ends in $, check Kerberos for an associated user account.

DNS SOA and dynamic registration

SPL 
index=zeek sourcetype=zeek:dns pcap_case=<CASE> qtype_name=SOA
| eval t=strftime(ts,"%H:%M:%S")
| table t id_orig_h id_resp_h query qtype_name rcode_name
  • Domain-joined Windows clients can register their DNS names dynamically. An SOA question can help identify the DNS zone and server involved.
  • A query such as <host>.<domain> can corroborate a hostname. id_resp_h identifies the DNS responder.
  • SOA alone is a clue. Inspect packets for a DNS UPDATE request to verify actual registration.

Observed software

SPL 
index=zeek sourcetype=zeek:software pcap_case=<CASE>
| eval t=strftime(ts,"%H:%M:%S")
| table t host software_type name unparsed_version
  • Zeek can infer software and versions from fields such as an HTTP User-Agent. Availability depends on the traffic and Zeek configuration.
  • software_type indicates the reported type. For example, HTTP::BROWSER identifies software reported in an HTTP client context, and OS::WINDOWS denotes a reported Windows OS.
  • Windows NT 6.1 is consistent with Windows 7 in this workstation example, and Win64; x64 indicates a 64-bit user-agent environment.
  • Note familiar browser and Windows service traffic, then record timestamps for software that differs from the baseline.

1-5. 호스트 정체 찾기

티켓의 IMPACTED INTERNAL MACHINES에 들어갈 호스트 이름, 사용자, 도메인을 찾아요. 윈도우는 자기 이름을 여러 곳에서 말하니, 두 곳 이상에서 같은 값이 나오면 확인된 걸로 봐요.

① DHCP — 있으면 가장 먼저

SPL 
index=zeek sourcetype=zeek:dhcp pcap_case=<케이스>
| eval t=strftime(ts,"%H:%M:%S")
| table t client_addr assigned_addr mac host_name domain msg_types
  • host_name — PC가 IP를 요청할 때 보낸 컴퓨터 이름
  • domain — DHCP 서버가 알려 준 도메인
  • table — 지정한 필드만 표로 보여 줘요(stats처럼 묶지 않아요).
  • 결과가 없으면 캡처 전에 IP를 받았거나 DHCP 교환이 수집되지 않았을 수 있어요. ②–⑤로 찾아요.

② Kerberos — 컴퓨터 계정과 사용자 계정

SPL 
index=zeek sourcetype=zeek:kerberos pcap_case=<케이스>
| stats min(ts) as first count values(request_type) as types values(success) as success values(error_msg) as errors by client
| sort first
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S")
  • client — 티켓을 요청한 계정, 계정/영역(REALM) 모양
  • values(…) — 그 계정에서 나온 서로 다른 값을 모두 보여 줘요.
  • request_type — AS = 로그온할 때 받는 첫 티켓(TGT), TGS = 특정 서비스용 티켓, AP = 받은 티켓을 서비스에 내미는 단계
보이는 값 뜻
이름이 $로 끝남 (NAME$) 컴퓨터 계정 → 호스트 이름
$ 없음 (first.last) 사용자 계정
계정 이름이 빈 줄 (/REALM, 종류 AP) AP 요청은 계정 이름이 암호화된 부분 안에 있어서 Zeek가 못 보여 줘요. 정상
같은 계정이 대소문자·REALM만 다르게 여러 줄 대소문자 차이는 표기 차이일 수 있어요. REALM이 다르면 같은 계정으로 묶기 전에 확인해요.
KDC_ERR_PREAUTH_REQUIRED 다음 성공 정상적인 사전 인증. 비밀번호 오류 아님
KDC_ERR_PREAUTH_FAILED 사전 인증 실패. 반복되면 비밀번호 오류나 추측 시도를 조사해요.

③ NTLM — 한 줄에 이름 세 개

SPL 
index=zeek sourcetype=zeek:ntlm pcap_case=<케이스>
| eval t=strftime(ts,"%H:%M:%S")
| table t id_orig_h id_resp_h id_resp_p username hostname domainname server_nb_computer_name success
  • username / hostname / domainname — 누가, 어느 PC에서, 어느 도메인으로 로그온했는지
  • server_nb_computer_name — 상대 서버(보통 DC)의 NetBIOS 이름
  • username이 $로 끝나면 사람이 아니라 컴퓨터 계정이 로그온한 거예요. 이때 사용자는 Kerberos에서 찾아요.

④ DNS 동적 업데이트 — PC가 자기 이름을 DC에 등록

SPL 
index=zeek sourcetype=zeek:dns pcap_case=<케이스> qtype_name=SOA
| eval t=strftime(ts,"%H:%M:%S")
| table t id_orig_h id_resp_h query qtype_name rcode_name
  • 도메인에 가입된 윈도우 PC는 자기 이름과 IP를 DNS에 동적으로 등록할 수 있어요. 등록 전에 "이 영역의 주인 서버가 누구야?"라는 SOA 질의를 먼저 보내요.
  • query = <PC 이름>.<도메인>, id_resp_h = DNS 서버(보통 DC)
  • SOA 질의는 이름 확인의 단서예요. 실제 동적 업데이트가 있었는지 확인하려면 DNS 패킷의 UPDATE 요청도 확인해요.

⑤ software — 이 PC가 쓰는 프로그램

SPL

티켓에 넣는 것과 넣지 않는 것

  • 넣음: IMPACTED INTERNAL MACHINES의 한 줄 — <IP> <호스트 이름> – user <도메인>\<사용자>
  • 이 실습의 티켓 양식에서는 상세 쿼리와 작업 로그를 작업 노트에 남겨요. MAC 주소가 필요한지는 보고서 양식에 따라 달라요. 아래 공개 실습의 DETAILS 양식은 MAC 주소도 요구해요.
  • 예: 172.16.2.169 CONSERVATOR-PC – user FABULOUSDUKES\lloyd.maxwell
