What did the domain controller acknowledge?

The source post identifies a Trickbot case that spread from a workstation to a domain controller (DC). The original PCAP shows that 172.16.2.101 directed SMB1 writes for two executable filenames to 172.16.2.2 and received successful replies. Both files appear on one connection in a busy host pair. That makes the case useful for testing a volume-based starting point against evidence of actual writes.

도메인 컨트롤러는 어떤 쓰기를 수락했나

공개 원문은 워크스테이션에서 도메인 컨트롤러(DC)로 확산된 Trickbot 사례를 소개합니다. 원본 PCAP에서는 172.16.2.101이 172.16.2.2로 실행 파일 이름 두 개에 대한 SMB1 쓰기를 보냈고 성공 응답을 받았습니다. 두 파일 모두 트래픽이 많은 호스트 쌍의 연결 하나에서 확인됐습니다. 이 사례에서는 트래픽 양으로 조사 대상을 좁힌 뒤 실제 쓰기 근거를 확인합니다.

캡처 시각, 프레임 번호, 패킷 수, 쓰기 성공 응답은 원본 PCAP을 직접 확인했습니다. 악성코드 계열과 호스트 역할은 공개 원문에 근거합니다. Splunk, Arkime, TShark 검색은 실습 예제입니다.

1 · Build a connection baseline in Splunk

Use the case label attached during import for <CASE>. Set the display timezone to UTC and use the original capture interval. If Splunk indexes by ingestion time, widen the picker and use the numeric Zeek ts field in search results. Map the examples to your ingestion's index, sourcetypes and flattened fields.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

Check which logs arrived and when. Before treating missing SMB rows as an investigative result, verify the decoder and index inputs.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp id_resp_p=445 id_orig_h=172.16.2.101 id_resp_h=172.16.2.2
| table ts uid id_orig_p duration conn_state orig_pkts resp_pkts orig_bytes resp_bytes missed_bytes
| sort 0 ts

Compare session age, client port, connection state and bytes, then sort on the client payload byte count to prioritize review. A packet count includes ACKs and retransmissions and can be high without file activity. The original PCAP has 4,396 bidirectional packets for workstation-initiated TCP/445 to the DC. The selected write connection on client port 49619 contributes 1,663 of those packets. Zeek connection rows and packet counts are separate measures.

1단계 · Splunk에서 연결 베이스라인 확인

가져올 때 지정한 케이스 값을 <CASE>에 넣습니다. 표시 시간대를 UTC로 설정하고 원본 캡처 구간을 선택합니다. Splunk의 시간 필드가 수집 시각이면 시간 범위를 넓히고 숫자형 Zeek ts를 기준으로 결과를 읽습니다. 예제의 인덱스, sourcetype과 평탄화된 필드는 실제 수집 환경에 맞춥니다.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

어떤 로그가 언제 수집됐는지 봅니다. SMB 행이 조회되지 않으면 그 결과를 근거로 삼기 전에 분석기와 인덱스의 입력 범위를 확인합니다.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp id_resp_p=445 id_orig_h=172.16.2.101 id_resp_h=172.16.2.2
| table ts uid id_orig_p duration conn_state orig_pkts resp_pkts orig_bytes resp_bytes missed_bytes
| sort 0 ts

연결 시작 시각, 출발지 포트, 연결 상태와 바이트를 비교합니다. 워크스테이션이 보낸 바이트가 많은 연결을 먼저 검토하려면 orig_bytes를 내림차순으로 정렬합니다. 패킷 수는 ACK와 재전송도 포함하므로 파일 쓰기 없이도 많아질 수 있습니다. 원본 PCAP에서 워크스테이션이 시작한 DC 방향 TCP/445 흐름은 양방향 4,396개 패킷이고, 파일 쓰기가 있었던 출발지 포트 49619의 연결이 그중 1,663개를 차지합니다. 패킷 수와 Zeek 연결 행 수는 각각 집계합니다.

2 · Follow the UID to the file activity

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" id_orig_h=172.16.2.101 id_resp_h=172.16.2.2 id_resp_p=445 id_orig_p=49619
| table ts uid id_orig_h id_orig_p id_resp_h id_resp_p duration conn_state missed_bytes

Take the UID for the TCP/445 connection on client port 49619. Use it only with logs from the same Zeek processing run and narrow to one import if the case was loaded multiple times.

SPL 
index=zeek pcap_case="<CASE>" uid="<SMB_UID>"
    sourcetype IN ("zeek:conn","zeek:smb_mapping","zeek:smb_files","zeek:dce_rpc","zeek:ntlm")
| sort 0 ts
| table ts sourcetype uid path name action endpoint operation

Read the smb_mapping share path, the SMB file name and action, and any nearby RPC operation. Multiple writes can target the same file handle. Count distinct target objects separately from write operations. Use the packet pane to confirm the server's replies.

The table abbreviates filenames and timestamps the requests. File-handle context ties each write to an earlier open. The first write's response status supports acceptance of that write, while execution and any changes to services need their own evidence. These filename patterns also appear in earlier public cases. A filename alone cannot establish identical content or a shared incident.

SPL 
index=zeek sourcetype=zeek:http pcap_case="<CASE>" id_orig_h=172.16.2.2
    id_resp_h=203.176.135.102 id_resp_p=8082 method=POST
| sort 0 ts
| eval log_time=strftime(ts,"%Y-%m-%d %H:%M:%S.%3N %Z")
| table log_time uid id_orig_p host uri status_code request_body_len response_body_len

Use this optional pivot to scope the later POST by DC IP and destination. Compare the HTTP UID with zeek:conn in the same run. To relate the HTTP and SMB rows, use the DC IP and time window. The network ordering alone leaves the process and purpose of the POST unresolved.

2단계 · 연결 UID로 파일 활동 확인

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" id_orig_h=172.16.2.101 id_resp_h=172.16.2.2 id_resp_p=445 id_orig_p=49619
| table ts uid id_orig_h id_orig_p id_resp_h id_resp_p duration conn_state missed_bytes

출발지 포트 49619의 TCP/445 연결에서 UID를 가져옵니다. 같은 Zeek 처리 실행의 로그에서 이 값을 사용합니다. 케이스를 여러 번 가져왔다면 먼저 수집 범위를 하나의 실행으로 제한합니다.

SPL 
index=zeek pcap_case="<CASE>" uid="<SMB_UID>"
    sourcetype IN ("zeek:conn","zeek:smb_mapping","zeek:smb_files","zeek:dce_rpc","zeek:ntlm")
| sort 0 ts
| table ts sourcetype uid path name action endpoint operation

smb_mapping의 공유 경로, SMB 파일 name과 action, 인접한 RPC 작업을 살핍니다. 쓰기 여러 건이 같은 파일 핸들을 사용할 수 있습니다. 작업 건수와 파일 수를 별도로 집계하고 서버 응답은 패킷 화면에서 확인합니다.

표의 파일 이름은 줄여 표시했으며 시각은 요청 기준입니다. 파일 핸들로 앞선 열기 요청과 쓰기를 연결했습니다. 첫 쓰기의 성공 응답은 해당 쓰기를 수락했다는 근거입니다. 실행과 서비스 변경에는 별도 증거가 필요합니다. 이전 공개 사례에도 이 파일 이름 패턴이 있으므로, 동일 바이너리나 동일 사건으로 판단하려면 추가 근거가 필요합니다.

SPL 
index=zeek sourcetype=zeek:http pcap_case="<CASE>" id_orig_h=172.16.2.2
    id_resp_h=203.176.135.102 id_resp_p=8082 method=POST
| sort 0 ts
| eval log_time=strftime(ts,"%Y-%m-%d %H:%M:%S.%3N %Z")
| table log_time uid id_orig_p host uri status_code request_body_len response_body_len

후속 POST는 DC IP와 목적지로 범위를 좁혀 확인합니다. HTTP UID를 사용해 같은 Zeek 실행의 zeek:conn을 살핍니다. HTTP와 SMB 기록의 관계는 DC IP와 시간대를 기준으로 조사합니다. 패킷의 순서만으로는 POST를 생성한 프로세스나 목적을 확인하기 어렵습니다.

3 · Verify the selected connection in Arkime

Arkime 
tags == "<CASE>" && ip.src == 172.16.2.101 && ip.dst == 172.16.2.2 && port.src == 49619 && port.dst == 445

Use the case tag, time around 17:56:46 UTC and source port 49619. Locate the requests and server responses, checking the packet direction and timestamps against the original capture. Identify which two writes target files and which exchange targets the named pipe before recording the result.

3단계 · Arkime에서 선택한 연결 확인

Arkime 
tags == "<CASE>" && ip.src == 172.16.2.101 && ip.dst == 172.16.2.2 && port.src == 49619 && port.dst == 445

케이스 태그와 17:56:46 UTC 전후, 출발지 포트 49619를 기준으로 확인합니다. 요청과 서버 응답을 찾고 방향과 시각을 원본 캡처와 대조합니다. 어떤 쓰기가 두 파일을 대상으로 하고 어떤 교환이 명명된 파이프를 대상으로 하는지 구분해 기록합니다.

4 · Check the server status with TShark if needed

TShark 
tshark -n -r "2020-03-04-Trickbot-spreads-from-client-to-DC.pcap" \
  -Y 'ip.addr == 172.16.2.101 && ip.addr == 172.16.2.2 && tcp.port == 49619 && tcp.port == 445 && smb.cmd == 0x2f' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e ip.src -e ip.dst \
  -e tcp.stream -e smb.mid -e smb.nt_status

If Arkime leaves a write reply unclear, list SMB1 write metadata for the selected stream offline. Compare the request and reply using the TCP stream, SMB multiplex ID and packet direction. Read the server's status for the matched transaction. Use the earlier open and handle context to identify the object.

4단계 · 필요한 경우 TShark로 서버 응답 상태 확인

TShark 
tshark -n -r "2020-03-04-Trickbot-spreads-from-client-to-DC.pcap" \
  -Y 'ip.addr == 172.16.2.101 && ip.addr == 172.16.2.2 && tcp.port == 49619 && tcp.port == 445 && smb.cmd == 0x2f' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e ip.src -e ip.dst \
  -e tcp.stream -e smb.mid -e smb.nt_status

Arkime에서 쓰기 응답이 불분명하다면 선택한 스트림의 SMB1 쓰기 메타데이터를 오프라인에서 조회합니다. TCP 스트림, SMB multiplex ID, 패킷 방향으로 요청과 응답을 짝짓고 서버 응답 상태를 읽습니다. 앞선 열기 요청과 파일 핸들로 작업 대상을 확인합니다.

5 · Record what the network confirms and follow up on the host

Record the PCAP hash, two host addresses, the five-tuple and the packet references for the confirmed writes. Attach the POST as a separate observation. Check whether one software deployment or administration window could explain the file and pipe activity. Ask the DC owner for file creation, execution and service telemetry, and look up the process associated with the later POST in proxy and endpoint network logs. Escalate the file-write evidence with any unverified execution or outbound activity marked as open.

5단계 · 네트워크 근거를 티켓에 남기고 호스트를 후속 조사

PCAP 해시, 두 호스트 IP, 연결의 주소·포트·프로토콜, 확인된 쓰기의 프레임을 기록합니다. POST는 별도 관찰 항목으로 첨부합니다. 승인된 배포나 관리 작업이 파일과 파이프 활동을 설명할 수 있는지 확인합니다. DC 담당자에게 파일 생성, 실행과 서비스 기록을 요청하고, 프록시와 엔드포인트 네트워크 로그에서 POST를 보낸 프로세스를 조사합니다. 쓰기 근거를 전달할 때 미확인 실행과 외부 통신은 후속 조사 항목으로 남깁니다.
