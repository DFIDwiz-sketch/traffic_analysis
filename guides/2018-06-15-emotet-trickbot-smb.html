Findings at a glance

The publisher reports that an Emotet infection on a Windows workstation preceded Trickbot spreading to the Oyster domain controller (DC). In the public capture, 192.168.200.95 (Linwood-Win-PC) sends SMB1 writes to 192.168.200.4 (Oyster-DC). The independently checked packet evidence includes successful replies for writes to two executable filenames. The publisher supplies the malware identification: del9 on the client and lib247 on the DC.

Evidence Observed value How to use it

TCP/445 between the two hosts 3,246 packets in both directions, including ACK-only and control packets Packet count, distinct from Zeek connections or Arkime sessions
File evidence Two \WINDOWS\…exe paths, first matched successful writes at 15:38:41.633 and 15:38:41.763 UTC Pivot from a port number to an operation and filename

Verification scope. Packet numbers, timestamps, file operation metadata and the capture hash were checked directly from the downloaded PCAP. The Splunk and Arkime steps are reproducible searches for your lab. Their result counts were not measured here.

1 · Set the case scope and baseline TCP/445

Ingest only the PCAP from the source page. Use the same tag in Splunk and Arkime if your importer supports it. In this guide, <CASE> means your actual pcap_case value. Example sourcetypes assume the flattened Zeek field names used in the site's PCAP Baselining Guide. Set time display to UTC and choose a time range that includes this historical capture.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

This returns the number of log events and their first and last ts values per sourcetype. Check that zeek:conn exists, then check for SMB, DCE-RPC and authentication logs. A missing analyzer log is a visibility gap. A conn timestamp marks the start of an observed connection and can differ from the full packet capture bounds.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp id_resp_p=445
| stats count as connections sum(orig_bytes) as sent sum(resp_bytes) as received
    values(conn_state) as states by id_orig_h id_resp_h
| sort - connections

The filter uses destination port 445 to find the connection initiator. Grouping by source and destination shows which pairs to prioritize. Use conn_state and both byte directions to decide which connections deserve deeper review. In this capture, the pair already had TCP/445 traffic at 15:14:38 UTC, over 24 minutes before the strong file-write evidence.

1단계 · 케이스 범위와 TCP/445 베이스라인

원문에서 PCAP을 가져와 수집하세요. 수집기가 지원하면 Splunk와 Arkime에 같은 케이스 태그를 사용하세요. 아래의 <CASE>는 실제 pcap_case 값으로 바꿉니다. 쿼리는 이 사이트의 PCAP 베이스라이닝 가이드와 같은 Zeek 필드 이름을 가정합니다. 시간을 UTC로 표시하고 검색 범위에 과거 캡처를 포함하세요.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

로그 종류마다 건수와 첫 번째·마지막 ts가 나옵니다. 먼저 zeek:conn이 있는지 보고, SMB·DCE-RPC·인증 로그도 확인하세요. 로그 종류가 빠져 있다면 해당 분석기의 가시성에 한계가 있을 수 있습니다. conn의 ts는 연결 시작 시각이고 전체 PCAP의 패킷 범위와 다를 수 있습니다.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp id_resp_p=445
| stats count as connections sum(orig_bytes) as sent sum(resp_bytes) as received
    values(conn_state) as states by id_orig_h id_resp_h
| sort - connections

목적지 포트 445를 조건으로 사용하면 누가 연결을 시작했는지 알 수 있습니다. 출발지·목적지별로 묶고 conn_state와 양방향 바이트를 비교해 다음 조사 대상을 고르세요. 이 캡처에서는 실행 파일에 대한 쓰기 근거가 나오기 24분 이상 전인 15:14:38 UTC부터 두 호스트 간 TCP/445가 보였습니다.

2 · Pivot from connections to SMB evidence

SPL 
index=zeek pcap_case="<CASE>" id_orig_h=192.168.200.95 id_resp_h=192.168.200.4
    id_orig_p=49562 id_resp_p=445
    sourcetype IN ("zeek:conn","zeek:smb_mapping","zeek:smb_files","zeek:dce_rpc","zeek:ntlm")
| sort 0 ts
| eval time_utc=strftime(ts,"%Y-%m-%d %H:%M:%S.%3N %Z")
| table time_utc sourcetype uid conn_state path name action endpoint operation

Keep the Zeek uid from the connection and use it to correlate share mapping, file actions and available RPC or authentication records generated in the same Zeek processing run. Compare path, name and action. Record whether a path came from Zeek's share mapping or is only the name carried in an SMB request. SMB1 parsing or file-action visibility may vary by Zeek version and configuration.

2단계 · 연결을 SMB 작업과 연결하기

SPL 
index=zeek pcap_case="<CASE>" id_orig_h=192.168.200.95 id_resp_h=192.168.200.4
    id_orig_p=49562 id_resp_p=445
    sourcetype IN ("zeek:conn","zeek:smb_mapping","zeek:smb_files","zeek:dce_rpc","zeek:ntlm")
| sort 0 ts
| eval time_utc=strftime(ts,"%Y-%m-%d %H:%M:%S.%3N %Z")
| table time_utc sourcetype uid conn_state path name action endpoint operation

연결 로그에서 가져온 Zeek uid를 같은 Zeek 처리 실행의 공유 매핑·파일 작업·RPC·인증 로그와 대조하세요. path, name, action을 비교하고, 공유 이름이 Zeek 공유 매핑에서 나온 값인지 SMB 요청에 실린 이름인지 구분합니다. SMB1 파일 작업이 로그에 얼마나 남는지는 Zeek 버전과 설정에 따라 다를 수 있습니다.

15:38:41.763 12454, 12458 같은 연결에서 두 번째 실행 파일명 \WINDOWS\lgwgf4lr…exe에 대응하는 쓰기와 성공 응답

표의 파일명은 줄여 적었습니다. SMB 쓰기 성공은 해당 대상에 데이터가 전달됐다는 근거입니다. 실행 여부는 별도 증거로 확인해야 합니다. 이름 파이프 쓰기와 실행 파일 쓰기는 같은 명령 코드가 보여도 의미가 다릅니다.

3 · Cross-check in Arkime

Arkime 
tags == "<CASE>" &&
ip.src == 192.168.200.95 && ip.dst == 192.168.200.4 &&
port.src == 49562 && port.dst == 445

Start with the UTC interval around 15:38:25–15:38:43. In Sessions, locate client port 49562 and inspect the packet metadata for request and reply. Compare the endpoints, ports and time with the Splunk record. Reset direction carefully if you search for a DC-initiated flow, since its source and destination are reversed.

4 · Use TShark to verify SMB1 status if needed

TShark 
tshark -n -r "2018-06-15-Emotet-infection-with-Trickbot-and-DC-infection.pcap" \
  -Y 'ip.addr == 192.168.200.95 && ip.addr == 192.168.200.4 && tcp.port == 49562 && smb.cmd == 0x2f' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e ip.src \
  -e ip.dst -e tcp.stream -e smb.cmd -e smb.mid -e smb.nt_status

Read the original capture offline with name resolution off. On the same TCP connection, compare the SMB Multiplex ID of the write request with the reply, and inspect the reply status. Frame numbers are from the original PCAP and can change in a filtered export. If a dissector reports an SMB message on the frame where it finished reassembly, use the time, endpoints and ID to match it.

4단계 · 필요할 때 TShark로 SMB1 응답 확인

TShark 
tshark -n -r "2018-06-15-Emotet-infection-with-Trickbot-and-DC-infection.pcap" \
  -Y 'ip.addr == 192.168.200.95 && ip.addr == 192.168.200.4 && tcp.port == 49562 && smb.cmd == 0x2f' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e ip.src \
  -e ip.dst -e tcp.stream -e smb.cmd -e smb.mid -e smb.nt_status

이름 해석을 끄고 원본 파일을 오프라인에서 읽습니다. 같은 TCP 연결에서 쓰기 요청과 응답의 SMB Multiplex ID를 맞춰 보고 응답 상태를 확인하세요. 프레임 번호는 원본 PCAP 기준이라 일부만 내보낸 파일에서는 달라질 수 있습니다. 재조립이 끝난 프레임에 SMB가 표시되면 시각·양 끝 주소·ID를 함께 대조하세요.

5 · Write the incident note

Record the workstation and DC, TCP/445 direction, the two file-write timestamps and the packet references. Attribute the family and DC infection to the publisher's report. Ask for DC file-creation and process or service telemetry to corroborate execution. If available, check Windows Security 5145 for share access and System 7045 or EDR service records for service installation. Treat early SMB sessions as context and investigate them separately if other evidence indicates abuse.

5단계 · 사고 티켓 작성

워크스테이션과 DC, TCP/445 방향, 두 파일의 쓰기 시각과 프레임 번호를 기록하세요. 악성코드 계열과 DC 감염은 원문 보고로 출처를 표시합니다. 실행을 확인하려면 DC의 파일 생성, 프로세스 또는 서비스 기록을 요청하세요. 수집돼 있다면 Windows Security 5145의 공유 접근 기록과 System 7045 또는 EDR의 서비스 설치 기록을 비교합니다. 앞서 보인 SMB 세션은 배경 정보로 두고 다른 증거가 있을 때 별도로 조사합니다.
