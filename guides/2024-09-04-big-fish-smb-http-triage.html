What connects the share activity and the external POSTs?

The publisher’s exercise asks for an incident report in an Active Directory lab. The original PCAP shows 172.17.0.99 using the DC at 172.17.0.17. It opens a named pipe on IPC$, connects separately to Storage, and later sends recurring HTTP POSTs to an external address. Investigate each flow and compare the time windows before assigning cause.

공유 접근과 외부 POST 사이에 어떤 근거가 있나

공개 실습은 Active Directory 환경의 사고 보고서 작성을 요청합니다. 원본 PCAP에서 172.17.0.99는 DC 172.17.0.17의 IPC$ 파이프를 열고, 별도 연결에서 Storage 공유에 접속했습니다. 이후 외부 주소로 HTTP POST를 반복했습니다. 각 흐름의 결과와 시각부터 비교한 뒤 원인을 조사합니다.

DC 역할은 공개 원문에 근거합니다. 아래 작업, 응답 코드, 주소와 시각은 원본 PCAP에서 직접 확인했습니다. Splunk, Arkime, TShark는 실습 환경에서 검증할 검색입니다.

1 · Baseline the workstation

Use the import tag for <CASE>, display UTC and include the capture interval in Splunk. Widen the picker if _time stores ingestion time and use numeric Zeek ts for event ordering. The examples use flattened fields.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

Check which connection, SMB, RPC and HTTP sourcetypes arrived before interpreting gaps.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" id_orig_h=172.17.0.99 proto=tcp
| stats count as connections values(service) as services values(conn_state) as states
    sum(orig_bytes) as client_bytes by id_resp_h id_resp_p
| sort 0 - connections

Group the workstation’s connections by responder and port. Ports and byte totals tell you where to look first. This capture contains 313 bilateral TCP/445 packets for workstation-initiated flows to the DC, including acknowledgements and control traffic. That packet count and the Splunk connection count measure different things.

1단계 · 워크스테이션 베이스라인 확인

<CASE>에 수집 태그를 넣고 Splunk 시간을 UTC로 표시합니다. 캡처 구간을 포함합니다. _time이 수집 시각이라면 시간 범위를 넓히고 사건 순서는 숫자형 Zeek ts로 확인합니다. 예제는 평탄화된 필드를 사용합니다.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

연결, SMB, RPC와 HTTP sourcetype의 수집 여부를 먼저 확인합니다.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" id_orig_h=172.17.0.99 proto=tcp
| stats count as connections values(service) as services values(conn_state) as states
    sum(orig_bytes) as client_bytes by id_resp_h id_resp_p
| sort 0 - connections

응답자 주소와 포트로 워크스테이션의 연결을 묶습니다. 포트와 바이트 집계로 확인할 대상을 고릅니다. 원본에서 워크스테이션이 시작한 DC 방향 TCP/445에는 ACK와 제어 패킷을 포함해 양방향 313개 패킷이 있었습니다. 패킷 수와 Splunk의 연결 행 수는 단위가 다릅니다.

2 · Verify SMB actions and scope the external requests

SPL 
index=zeek pcap_case="<CASE>" id_orig_h=172.17.0.99 id_resp_h=172.17.0.17
    id_resp_p=445 id_orig_p IN (49778,49785)
    sourcetype IN ("zeek:conn","zeek:smb_mapping","zeek:smb_files","zeek:dce_rpc")
| sort 0 ts
| table ts sourcetype uid id_orig_p path name action endpoint operation

Use the uid from each connection row to associate the share and application rows from the same Zeek processing run. The two client ports identify distinct TCP connections. Read the share path and use packet-level message IDs and the direction to check the result of each operation.

SPL 
index=zeek sourcetype=zeek:http pcap_case="<CASE>" id_orig_h=172.17.0.99
    id_resp_h=79.124.78.197 id_resp_p=80
| eval request_path=mvindex(split(uri,"?"),0)
| stats count as requests dc(uid) as connections values(status_code) as status
    min(ts) as first max(ts) as last by method request_path
| sort 0 first

Compare method, request path and available status for the external endpoint. dc(uid) counts connections while count counts HTTP rows. Join HTTP and connection logs for a specific HTTP UID within the same Zeek run. To compare the HTTP and SMB activity, use the workstation, time and endpoint process evidence where available.

Attribution to one process, DC modification and the meaning of the POST data require separate evidence.

2단계 · SMB 작업과 외부 요청의 범위 확인

SPL 
index=zeek pcap_case="<CASE>" id_orig_h=172.17.0.99 id_resp_h=172.17.0.17
    id_resp_p=445 id_orig_p IN (49778,49785)
    sourcetype IN ("zeek:conn","zeek:smb_mapping","zeek:smb_files","zeek:dce_rpc")
| sort 0 ts
| table ts sourcetype uid id_orig_p path name action endpoint operation

연결 행의 uid로 같은 Zeek 처리 실행의 공유 및 응용 프로토콜 행을 연결합니다. 두 출발지 포트는 별도 TCP 연결입니다. 공유 경로를 읽고 패킷의 메시지 ID와 방향으로 각 작업의 결과를 확인합니다.

SPL 
index=zeek sourcetype=zeek:http pcap_case="<CASE>" id_orig_h=172.17.0.99
    id_resp_h=79.124.78.197 id_resp_p=80
| eval request_path=mvindex(split(uri,"?"),0)
| stats count as requests dc(uid) as connections values(status_code) as status
    min(ts) as first max(ts) as last by method request_path
| sort 0 first

외부 목적지의 메서드, 요청 경로와 수집된 응답 상태를 비교합니다. dc(uid)는 연결 수, count는 HTTP 행 수를 집계합니다. 특정 HTTP UID의 연결과 HTTP 기록은 같은 Zeek 실행에서 대조합니다. SMB와 HTTP를 비교할 때는 워크스테이션 IP, 시각과 확보 가능한 프로세스 증거를 사용합니다.

같은 TCP 시퀀스 위치를 한 번만 세었을 때 반복 경로의 POST는 서로 다른 출발지 포트 43개에서 48건이었습니다. Zeek의 집계는 스트림 파싱 방식에 따라 달라질 수 있습니다. 파이프 쓰기 성공은 프로세스 간 데이터 교환의 근거입니다. 정상적인 공유 탐색이나 도메인 작업도 이런 SMB 활동을 보일 수 있습니다. PCAP은 작업 순서와 결과를 보여 줍니다. 실행 프로세스, DC 변경과 POST 내용의 의미는 별도 증거가 필요합니다.

3 · Cross-check both directions in Arkime

Arkime 
tags == "<CASE>" && ip.src == 172.17.0.99 && ip.dst == 172.17.0.17 && port.dst == 445 && (port.src == 49778 || port.src == 49785)

Apply the import tag and compare the two source ports around 17:34:35 UTC. Find the successful tree responses and the selected file-open failures. Keep the transport tuple with the packet times.

Arkime 
tags == "<CASE>" && ip.src == 172.17.0.99 && ip.dst == 79.124.78.197 && port.dst == 80

Check the separate outbound exchange around 17:35:07 UTC. Verify request and response direction and compare the time and port with later requests.

4 · Confirm the Storage replies offline if needed

TShark 
tshark -n -r "2024-09-04-traffic-analysis-exercise.pcap" \
  -Y 'frame.number == 493 || frame.number == 494 || frame.number == 608 || frame.number == 609 || frame.number == 610 || frame.number == 611' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e ip.src -e tcp.stream \
  -e smb2.msg_id -e smb2.cmd -e smb2.nt_status

If Arkime leaves the two file statuses unclear, read the selected SMB2 frames from the original file. Match request and reply by TCP stream, message ID and direction. The status of a successful tree connect and the statuses of later file-open requests describe separate operations.

Arkime에서 파일 상태가 분명하지 않으면 원본의 선택한 SMB2 프레임을 읽습니다. TCP 스트림, 메시지 ID와 방향으로 요청과 응답을 짝짓습니다. 공유 연결 성공과 이후 파일 열기는 별도 작업으로 확인합니다.

5 · Write the SOC ticket

Record the PCAP hash, workstation and DC, confirmed share activity, file-open outcomes and external HTTP timing. Check the share owner, workstation process-network events, DC share and RPC logs, and proxy records. Compare with approved administration and record any unresolved file access or data exposure.
