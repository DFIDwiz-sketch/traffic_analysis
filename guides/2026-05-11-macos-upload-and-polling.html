What separates the large upload from the later polling?

The publisher describes a macOS infection following a misleading software ad and download page. In the original PCAP, 10.5.11.101 sends small JSON POSTs and larger multipart POSTs to 165.245.215.18:80. It later makes recurring GETs to 94.232.249.129:80. This guide checks the upload’s size and final response separately from the frequency of the later requests.

대용량 업로드와 이후 폴링은 어떻게 구분하나

공개 원문은 오인하기 쉬운 소프트웨어 광고와 다운로드 페이지에 이은 macOS 감염을 설명합니다. 원본 PCAP에서 10.5.11.101은 165.245.215.18:80으로 작은 JSON POST와 더 큰 멀티파트 POST를 보냈습니다. 이후 94.232.249.129:80으로 GET을 반복했습니다. 업로드의 크기와 최종 응답, 이후 요청의 반복 주기를 각각 확인합니다.

감염 시나리오는 공개 원문에 근거합니다. 아래 HTTP 헤더, TCP에서 확인한 본문 범위와 시각은 원본 파일에서 직접 확인했습니다. 검색은 각자의 실습 환경에서 검증합니다.

1 · Baseline the workstation in Splunk

Use the import tag for <CASE>, set UTC and include the full capture interval. If _time uses ingest time, widen the picker and use numeric Zeek ts to order the case. The examples use flattened fields.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

Confirm that zeek:conn and zeek:http are available before comparing destinations.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" id_orig_h=10.5.11.101 proto=tcp
| stats count as connections sum(orig_bytes) as client_payload_bytes min(ts) as first max(ts) as last
    by id_resp_h id_resp_p
| sort 0 - client_payload_bytes

Compare client payload bytes, connection counts and time per responder and port. orig_bytes is connection-level payload. A single large transaction can dominate that total. Use HTTP logs and the capture to identify the specific request.

1단계 · Splunk에서 워크스테이션 베이스라인 확인

<CASE>에 수집 태그를 넣고 UTC로 표시합니다. 전체 캡처 범위를 포함합니다. _time이 수집 시각이면 범위를 넓히고 숫자형 Zeek ts로 사건 순서를 읽습니다. 예제는 평탄화된 필드를 사용합니다.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

목적지를 비교하기 전에 zeek:conn과 zeek:http 수집 여부를 확인합니다.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" id_orig_h=10.5.11.101 proto=tcp
| stats count as connections sum(orig_bytes) as client_payload_bytes min(ts) as first max(ts) as last
    by id_resp_h id_resp_p
| sort 0 - client_payload_bytes

응답자와 포트마다 클라이언트 바이트, 연결 수와 시각을 비교합니다. orig_bytes는 연결 전체의 페이로드를 집계합니다. 큰 트랜잭션 하나가 대부분의 바이트를 차지할 수 있으므로 HTTP 로그와 캡처에서 해당 요청을 찾습니다.

2 · Compare methods, request sizes and responses

SPL 
index=zeek sourcetype=zeek:http pcap_case="<CASE>" id_orig_h=10.5.11.101 id_resp_p=80
    id_resp_h IN ("165.245.215.18","94.232.249.129")
| eval path=mvindex(split(uri,"?"),0)
| eval route=case(like(path,"/api/tasks/%"),"/api/tasks/<id>",path="/contact","/contact",
    path="/api/metrics/run","/api/metrics/run",true(),"other")
| stats count as requests dc(uid) as connections min(request_body_len) as smallest
    max(request_body_len) as largest values(status_code) as responses by id_resp_h method route

Read counts, distinct UIDs, request-body sizes and status by route and destination. The query strips query strings and groups task paths without showing their identifiers. The packet review found 19 GETs in the later task path on 19 source ports. This count uses distinct packet-start requests, after removing repeated TCP sequence positions. Zeek can count differently after stream parsing.

SPL 
index=zeek pcap_case="<CASE>" uid="<HTTP_UID>" sourcetype IN ("zeek:conn","zeek:http")
| sort 0 ts
| table ts sourcetype uid id_orig_p id_resp_h id_resp_p missed_bytes method status_code request_body_len

Use a selected HTTP UID to get its connection row from the same Zeek processing run. Select one run if you imported the file twice. For the large upload, compare request_body_len and missed_bytes with packet-level coverage. The later polling connections each have a separate UID. Compare across endpoints using the workstation and time.

2단계 · 메서드, 요청 크기와 응답 비교

SPL 
index=zeek sourcetype=zeek:http pcap_case="<CASE>" id_orig_h=10.5.11.101 id_resp_p=80
    id_resp_h IN ("165.245.215.18","94.232.249.129")
| eval path=mvindex(split(uri,"?"),0)
| eval route=case(like(path,"/api/tasks/%"),"/api/tasks/<id>",path="/contact","/contact",
    path="/api/metrics/run","/api/metrics/run",true(),"other")
| stats count as requests dc(uid) as connections min(request_body_len) as smallest
    max(request_body_len) as largest values(status_code) as responses by id_resp_h method route

경로와 목적지별로 요청 수, 고유 UID, 본문 크기와 응답 코드를 비교합니다. 이 검색은 쿼리 문자열을 잘라내고 작업 경로의 식별자를 표시하지 않도록 묶습니다. 원본에서 이후 작업 경로의 GET이 출발지 포트 19개에서 19건 관찰됐습니다. 패킷 시작부에서 확인된 요청 중 같은 TCP 시퀀스를 한 번만 셌습니다. Zeek의 스트림 파싱 결과는 다를 수 있습니다.

SPL 
index=zeek pcap_case="<CASE>" uid="<HTTP_UID>" sourcetype IN ("zeek:conn","zeek:http")
| sort 0 ts
| table ts sourcetype uid id_orig_p id_resp_h id_resp_p missed_bytes method status_code request_body_len

HTTP UID 하나로 같은 Zeek 처리 실행의 연결 행을 확인합니다. 캡처를 여러 번 가져왔으면 한 실행으로 좁힙니다. 대용량 업로드는 request_body_len 및 missed_bytes를 실제 패킷 범위와 대조합니다. 이후의 폴링 연결에는 각각 UID가 있습니다. 목적지가 다른 흐름은 워크스테이션과 시각으로 비교합니다.

대용량 POST의 HTTP 헤더 뒤 연속 TCP 시퀀스를 세고 겹친 구간은 한 번만 계산했습니다. 본문 11,008,735바이트가 캡처됐습니다. HTTP 100은 중간 응답이며 뒤이은 200은 서버의 최종 HTTP 상태입니다. 정상 텔레메트리, 대량 업로드와 폴링에서도 비슷한 특징이 있을 수 있습니다. 파일 정체, 서버 보존 및 호출 프로세스에는 별도 근거가 필요합니다.

4 · Verify declared length and reply order offline if needed

TShark 
tshark -n -r "2026-05-11-macOS-malware-infection-traffic.pcap" \
  -Y 'frame.number == 5595 || frame.number == 5599 || frame.number == 18872 || frame.number == 18980' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e tcp.stream -e ip.src \
  -e http.request.method -e http.content_length -e http.response.code

If Arkime leaves the reply order or declared length unclear, compare these four original frames. Use the TCP stream and direction to distinguish the request, HTTP 100 and HTTP 200. Reassembly can move the displayed request fields to a later frame. This query shows headers. Verify body coverage independently before treating a declared length as an observed transfer size.

4단계 · 필요한 경우 선언 길이와 응답 순서 확인

TShark 
tshark -n -r "2026-05-11-macOS-malware-infection-traffic.pcap" \
  -Y 'frame.number == 5595 || frame.number == 5599 || frame.number == 18872 || frame.number == 18980' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e tcp.stream -e ip.src \
  -e http.request.method -e http.content_length -e http.response.code

Arkime에서 선언 길이나 응답 순서가 분명하지 않으면 원본 프레임 네 개를 읽습니다. TCP 스트림과 방향으로 요청, HTTP 100과 HTTP 200을 구분합니다. 재조립 시 요청 필드가 뒤쪽 프레임에 표시될 수 있습니다. 이 검색은 헤더를 보여 줍니다. 실제 전송 크기는 본문 바이트 범위를 따로 확인한 뒤 판단합니다.

5 · Record the transfer and check which process sent it

Include the hash, destination tuples, final response, body coverage and later GET cadence in the ticket. Compare both endpoints with approved software and telemetry. Ask for process-network events, browser and proxy history, and file-access evidence to confirm the initiating process and scope any exposure.

5단계 · 전송을 기록하고 요청 프로세스 확인
