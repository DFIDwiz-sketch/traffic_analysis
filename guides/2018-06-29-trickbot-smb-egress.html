What the capture shows

The 29 June 2018 report attributes the workstation infection to Trickbot ser0629 and the domain-controller infection to lib257. A read-only review of the original PCAP found successful SMB1 write replies for two executable filenames on the connection from 172.16.1.102:49476 to 172.16.1.8:445. A later HTTP POST to TCP/8082 originated from the workstation. Keep that outbound traffic separate from the internal file transfer and attribute any assessment of its content to the publisher.

아래 프레임 번호와 시각은 원본 PCAP에서 직접 확인했습니다. 쿼리는 실습용이며, 실제 결과 건수는 여기서 측정하지 않았습니다.

1 · Establish the case in Splunk

Select the capture window in UTC and replace <CASE> with your import tag. The queries use the site’s flattened Zeek field names. Check which logs were produced and isolate one processing run if the same capture was imported more than once.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

The first search counts log records by sourcetype and shows each log’s event range. These ranges can differ from the first and last packet times above. Check for zeek:conn, zeek:smb_mapping and zeek:smb_files before narrowing.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp id_resp_p=445 id_orig_h=172.16.1.102
| stats count as connections dc(id_orig_p) as client_ports sum(orig_bytes) as sent
        sum(resp_bytes) as received min(ts) as first values(conn_state) as states by id_orig_h id_resp_h
| sort - connections
| eval first=strftime(first,"%H:%M:%S.%3N %Z")

Grouping by source and destination shows which pairs use TCP/445. Read originator and responder byte counts together with connection state. The original capture had 1,518 packets in both directions on flows from the workstation toward DC TCP/445, including control packets. This count is neither a Zeek connection count nor a count of SMB requests.

1단계 · Splunk에서 케이스 범위 설정

UTC로 표시하고 캡처 시간대를 선택합니다. <CASE>는 실제 수집 태그로 바꿉니다. 예제는 사이트에서 쓰는 평탄화된 Zeek 필드명을 가정합니다. 같은 PCAP을 여러 번 가져왔다면 처리 한 건으로 범위를 좁힙니다.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

로그 종류별 건수와 이벤트 시각 범위를 봅니다. 이 범위는 위의 첫·마지막 패킷 시각과 다를 수 있습니다. zeek:conn, zeek:smb_mapping, zeek:smb_files의 수집 여부를 먼저 확인하세요.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp id_resp_p=445 id_orig_h=172.16.1.102
| stats count as connections dc(id_orig_p) as client_ports sum(orig_bytes) as sent
        sum(resp_bytes) as received min(ts) as first values(conn_state) as states by id_orig_h id_resp_h
| sort - connections
| eval first=strftime(first,"%H:%M:%S.%3N %Z")

출발지·목적지별 TCP/445 연결을 묶습니다. 클라이언트와 서버 쪽 바이트를 연결 상태와 함께 읽으세요. 원본에서 워크스테이션이 DC의 TCP/445로 향한 흐름에는 응답과 제어 패킷을 포함해 양방향 1,518개 패킷이 있었습니다. 이는 Zeek 연결 수나 SMB 요청 수와 집계 단위가 다릅니다.

2 · Follow the file-write session

SPL 
index=zeek pcap_case="<CASE>" id_orig_h=172.16.1.102 id_resp_h=172.16.1.8 id_orig_p=49476 id_resp_p=445
    sourcetype IN ("zeek:conn","zeek:smb_mapping","zeek:smb_files","zeek:dce_rpc","zeek:ntlm")
| sort 0 ts
| eval time_utc=strftime(ts,"%Y-%m-%d %H:%M:%S.%3N %Z")
| table time_utc sourcetype uid id_orig_p path name action endpoint operation conn_state

Find the zeek:conn record for client port 49476. Use its uid to match share and file logs from the same Zeek processing run. Inspect action, path and name together. A file open, a named-pipe write and a write to a disk file provide different evidence.

16:58:04.012 4773, 4774 Write and success reply for the svcctl named pipe

Filenames are abbreviated. The write table uses file-handle and request/reply metadata. It records transfer of data to the target objects. Ask for endpoint evidence before recording execution or task creation.

SPL 
index=zeek sourcetype=zeek:http pcap_case="<CASE>" method=POST id_resp_p=8082
| sort 0 ts
| eval time_utc=strftime(ts,"%Y-%m-%d %H:%M:%S.%3N %Z")
| table time_utc id_orig_h id_resp_h id_resp_p uid method status_code request_body_len

Run the HTTP query independently. id_orig_h identifies the originator of each HTTP connection. Compare the POST event time and source with the SMB timeline using the endpoint and UTC window. The HTTP and SMB records belong to different connections and do not share a UID. A POST header establishes the request method. Its purpose or the data involved requires separate evidence.

2단계 · 파일 쓰기 세션 추적

SPL 
index=zeek pcap_case="<CASE>" id_orig_h=172.16.1.102 id_resp_h=172.16.1.8 id_orig_p=49476 id_resp_p=445
    sourcetype IN ("zeek:conn","zeek:smb_mapping","zeek:smb_files","zeek:dce_rpc","zeek:ntlm")
| sort 0 ts
| eval time_utc=strftime(ts,"%Y-%m-%d %H:%M:%S.%3N %Z")
| table time_utc sourcetype uid id_orig_p path name action endpoint operation conn_state

클라이언트 포트 49476의 zeek:conn을 찾고 같은 Zeek 처리 실행의 공유·파일 로그를 uid로 연결합니다. action, path, name을 함께 보면 일반 파일 열기, 이름 파이프 쓰기, 디스크 파일 쓰기를 구분할 수 있습니다.

표의 파일명은 축약했습니다. 파일 핸들과 요청·응답 메타데이터를 연결해 쓰기를 확인했습니다. 실행이나 예약 작업 생성 여부는 엔드포인트 기록으로 확인합니다.

SPL 
index=zeek sourcetype=zeek:http pcap_case="<CASE>" method=POST id_resp_p=8082
| sort 0 ts
| eval time_utc=strftime(ts,"%Y-%m-%d %H:%M:%S.%3N %Z")
| table time_utc id_orig_h id_resp_h id_resp_p uid method status_code request_body_len

HTTP 쿼리는 따로 실행합니다. id_orig_h는 연결 시작 호스트입니다. POST의 출발지와 UTC 시각을 SMB 타임라인과 비교하세요. 서로 다른 연결이므로 같은 uid로 조인하지 않습니다. POST 헤더는 요청 방식을 보여 주며, 전송 목적이나 데이터의 성격에는 별도 근거가 필요합니다.

3 · Cross-check in Arkime

Arkime 
tags == "<CASE>" && ip.src == 172.16.1.102 && ip.dst == 172.16.1.8 && port.src == 49476 && port.dst == 445

Set Sessions to 16:57:58–16:58:05 UTC. Verify both endpoints and the client port, then inspect the packet sequence. Verify the HTTP connection separately if it matters to your incident scope.

3단계 · Arkime에서 교차 확인

Arkime 
tags == "<CASE>" && ip.src == 172.16.1.102 && ip.dst == 172.16.1.8 && port.src == 49476 && port.dst == 445

16:57:58–16:58:05 UTC 범위에서 세션을 열고 양 끝 주소와 클라이언트 포트를 확인합니다. 패킷 순서를 Splunk와 대조하세요. 외부 통신이 조사 범위에 들어가면 HTTP 연결은 별도로 확인합니다.

4 · Use TShark only if the reply status is unclear

TShark 
tshark -n -r "2018-06-29-Trickbot-infects-client-then-moves-to-DC.pcap" \
  -Y 'ip.addr == 172.16.1.102 && ip.addr == 172.16.1.8 && tcp.port == 49476 && tcp.port == 445 && smb.cmd == 0x2f' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e ip.src -e ip.dst \
  -e tcp.stream -e smb.mid -e smb.nt_status

Read the original PCAP offline and print only SMB1 write metadata for this pair and port. Compare the TCP stream, SMB multiplex ID and response direction. The successful reply has status zero. Filtered copies can have different frame numbers, and reassembly can move the displayed protocol detail to a later frame.

4단계 · 응답 상태가 불명확할 때 TShark로 확인

TShark 
tshark -n -r "2018-06-29-Trickbot-infects-client-then-moves-to-DC.pcap" \
  -Y 'ip.addr == 172.16.1.102 && ip.addr == 172.16.1.8 && tcp.port == 49476 && tcp.port == 445 && smb.cmd == 0x2f' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e ip.src -e ip.dst \
  -e tcp.stream -e smb.mid -e smb.nt_status

원본 파일을 오프라인으로 읽어 해당 연결의 SMB1 쓰기 메타데이터만 출력합니다. TCP 스트림, SMB Multiplex ID와 응답 방향을 비교하세요. 성공 응답의 상태값은 0입니다. 필터링해 다시 저장하면 프레임 번호가 달라질 수 있으며, 재조립이 끝난 프레임에 프로토콜 내용이 표시될 수 있습니다.

5 · Prepare a SOC ticket

Record the two endpoints, TCP connection, file-write times, frame references and capture hash. Mark the scheduled task and Trickbot labels as findings from the original report. Ask for DC process, file creation and scheduled-task records. Compare against approved software deployment and maintenance windows. Check workstation egress separately before assigning scope to the DC.

5단계 · SOC 티켓 작성

두 호스트, TCP 연결, 쓰기 시각, 프레임 번호, 캡처 해시를 기록합니다. 예약 작업과 Trickbot 식별은 공개 원문의 보고로 표시합니다. DC에서 프로세스·파일 생성·예약 작업 기록을 요청하고, 승인된 배포나 유지보수 일정과 대조하세요. 워크스테이션의 외부 전송 범위는 따로 조사합니다.
