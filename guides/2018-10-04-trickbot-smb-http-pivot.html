What connects the internal and outbound traffic?

The publisher describes Trickbot moving from a workstation to a domain controller (DC) and attributes this case to URL-based propagation over SMB. In the original PCAP, a client-to-DC TCP/445 packet from 172.16.4.119 contains a UTF-16LE URL. The DC at 172.16.4.4 then sends an HTTP GET whose Host and request path match, and the server responds with HTTP 200. The byte match and timing link the network observations. The publisher supplies the Trickbot attribution and the interpretation of how it spread.

내부 트래픽과 외부 요청을 연결하는 근거

공개 원문은 Trickbot이 워크스테이션에서 도메인 컨트롤러(DC)로 확산됐으며 이 사례에서 SMB로 URL을 전달했다고 설명합니다. 원본 PCAP에서 워크스테이션 172.16.4.119이 DC로 보낸 TCP/445 패킷에 UTF-16LE URL이 들어 있었습니다. 직후 DC 172.16.4.4가 해당 URL의 Host와 경로가 일치하는 HTTP GET을 보냈고 서버는 HTTP 200을 반환했습니다. 이 두 네트워크 관찰은 값과 시각이 일치합니다. 악성코드 계열과 확산 방식의 해석은 공개 원문에 근거합니다.

1 · Set the case scope and baseline the host pair

Replace <CASE> with the tag assigned during import. Set the Splunk display timezone to UTC and cover the full capture. If _time is ingestion time, widen the picker and use the Zeek ts field for the incident timeline. The examples assume flattened Zeek fields and numeric ts.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

Check that connection and HTTP logs arrived. Look for SMB and RPC logs as well, keeping analyzer coverage in mind. Compare the log extent to the capture range before interpreting missing events.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp id_resp_p=445 id_orig_h=172.16.4.119 id_resp_h=172.16.4.4
| table ts uid id_orig_p duration conn_state orig_pkts resp_pkts orig_bytes resp_bytes missed_bytes
| sort 0 ts

Read the sessions in time order for this directional pair. Search the 20:34:06 UTC burst, then look at id_orig_p to separate parallel connections. orig_pkts and resp_pkts count packets, while orig_bytes and resp_bytes describe payload bytes as reported by Zeek. Check missed_bytes before drawing conclusions from a thin session. The original capture contains 1,265 packets in both directions for workstation-originated TCP/445 to the DC, including ACKs and control traffic.

1단계 · 케이스 범위와 두 호스트 간 TCP 베이스라인

<CASE>를 가져올 때 지정한 케이스 값으로 바꿉니다. Splunk 표시 시간대를 UTC로 설정하고 전체 캡처 구간을 포함합니다. _time이 수집 시각인 경우 검색 범위를 넓히고 타임라인에는 Zeek ts를 사용합니다. 예제는 평탄화된 Zeek 필드와 숫자형 ts를 기준으로 합니다.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

연결과 HTTP 로그가 조회되는지 확인합니다. SMB와 RPC 로그도 살피되 분석기의 수집 범위를 고려합니다. 이벤트가 빠졌다고 해석하기 전에 로그 시간 범위를 캡처 시간과 비교합니다.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp id_resp_p=445 id_orig_h=172.16.4.119 id_resp_h=172.16.4.4
| table ts uid id_orig_p duration conn_state orig_pkts resp_pkts orig_bytes resp_bytes missed_bytes
| sort 0 ts

워크스테이션→DC 연결을 시간순으로 살핍니다. 20:34:06 UTC 전후에 여러 연결이 몰린 구간을 찾고 id_orig_p로 각각을 구분합니다. orig_pkts와 resp_pkts는 패킷 수, orig_bytes와 resp_bytes는 Zeek가 집계한 페이로드 바이트입니다. 데이터량이 적은 세션은 missed_bytes도 확인합니다. 원본 PCAP에서 워크스테이션이 시작한 DC 방향 TCP/445 흐름에는 ACK와 제어 패킷을 포함해 양방향 1,265개 패킷이 있었습니다.

2 · Pivot from the TCP session to the DC’s HTTP request

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" id_orig_h=172.16.4.119 id_resp_h=172.16.4.4 id_resp_p=445 id_orig_p=49422
| table ts uid id_orig_h id_orig_p id_resp_h id_resp_p duration conn_state missed_bytes

Take the connection’s uid and restrict subsequent SMB and RPC searches to the same Zeek processing run. A capture imported twice may contain separate UID sets.

SPL 
index=zeek pcap_case="<CASE>" uid="<SMB_UID>"
    sourcetype IN ("zeek:conn","zeek:smb_mapping","zeek:smb_files","zeek:dce_rpc","zeek:ntlm")
| sort 0 ts
| table ts sourcetype uid path name action endpoint operation

Use the UID search to look for share, file or RPC context if the analyzer logged it. A TCP/445 burst can still provide packet evidence when application logs are absent.

SPL 
index=zeek sourcetype=zeek:http pcap_case="<CASE>" id_orig_h=172.16.4.4
    id_resp_h=185.17.123.2 id_resp_p=80 method=GET
| sort 0 ts
| eval log_time=strftime(ts,"%Y-%m-%d %H:%M:%S.%3N %Z")
| table log_time uid id_orig_p host uri status_code request_body_len response_body_len

Read host and uri together for the DC’s GET around 20:34:06 UTC. Compare them with the URL in the captured TCP/445 data. The HTTP connection has a separate UID. Correlate it to the internal connection using the DC IP, request timing and matching Host plus path. Record its HTTP UID for pivots to zeek:conn from the same run.

4 · Check direction and status offline if needed

TShark 
tshark -n -r "2018-10-04-Trickbot-spreads-from-client-to-DC.pcap" \
  -Y '(frame.number == 15364 || frame.number == 15508 || frame.number == 15514)' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e ip.src -e ip.dst \
  -e tcp.srcport -e tcp.dstport -e tcp.len -e http.request.method -e http.response.code

Use this read-only view if Arkime leaves the packet order or the HTTP response status unclear. It reports only metadata from three original frames. Use the source and destination ports to distinguish the two separate TCP sessions. The output provides a timing and status check. The URL comparison comes from the existing packet data.

4단계 · 필요한 경우 오프라인에서 방향과 HTTP 상태 확인

TShark 
tshark -n -r "2018-10-04-Trickbot-spreads-from-client-to-DC.pcap" \
  -Y '(frame.number == 15364 || frame.number == 15508 || frame.number == 15514)' \

Arkime에서 패킷 순서나 HTTP 응답 상태가 불분명하면 이 오프라인 조회로 원본 프레임 세 개의 메타데이터를 확인합니다. 출발지와 목적지 포트로 별개인 TCP 세션을 구분합니다. 이 출력은 시각과 상태 확인에 사용하고, URL 일치 여부는 패킷의 기존 데이터에서 확인합니다.

5 · Record the evidence and what remains open

Record the workstation, DC, both TCP tuples, capture hash, frame references, URL match and HTTP status in the ticket. An approved software download or simultaneous administration could account for HTTP activity in a different incident, so check the change record and identify the process responsible for the request. HTTP 200 records the server’s response. File identity and execution on the DC require endpoint or additional evidence. Request proxy records, process network telemetry and file or service events around 20:34:06 UTC.

5단계 · 사고 티켓과 DC 후속 점검

워크스테이션과 DC, 두 TCP 연결의 주소·포트, 해시, 프레임, URL 일치와 HTTP 상태를 남깁니다. 운영 환경에서는 승인된 소프트웨어 다운로드나 같은 시간대의 관리 작업도 가능한 설명이므로 변경 기록과 요청을 보낸 프로세스를 확인합니다. HTTP 200은 서버의 응답 상태입니다. DC에 저장된 파일의 정체나 실행 여부는 별도의 증거가 필요합니다. 20:34:06 UTC 전후 프록시 로그, 프로세스 네트워크 기록, 파일 및 서비스 이벤트를 요청합니다.
