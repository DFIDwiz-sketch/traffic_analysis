Which direction did the transfer take?

The source post dated 24 May 2018 describes two Trickbot runs, on a standalone host and in an Active Directory (AD) network. The AD capture is the scope of this guide. It begins on 25 May UTC. In that file, the workstation 10.0.100.223 received success replies from the DC at 10.0.100.5 for writes to two executable filenames. Later, the DC sent SYNs in the opposite direction. These are two separate observations.

파일은 어느 쪽으로 전송됐나

5월 24일자 공개 원문은 Trickbot을 단독 호스트와 Active Directory(AD) 환경에서 각각 관찰했습니다. 이 가이드의 조사 범위는 UTC 5월 25일에 시작하는 AD 캡처입니다. 워크스테이션 10.0.100.223이 실행 파일 이름 두 개에 쓰기를 요청했고, 도메인 컨트롤러(DC) 10.0.100.5가 성공 응답을 보냈습니다. 이후 DC가 반대 방향으로 SYN을 보낸 활동도 별도로 관찰됐습니다.

호스트 역할과 악성코드 계열은 공개 원문에 근거합니다. UTC 날짜, 연결 방향, 파일 쓰기와 프레임 위치는 AD PCAP에서 직접 확인했습니다. 아래 검색은 각 도구에서 해당 근거를 검증하는 데 사용합니다.

1 · Compare both TCP/445 directions in Splunk

Set the time picker to cover the 25 May UTC capture interval and substitute the AD import's <CASE> value. Search using UTC in your profile. Use a dedicated case label for the standalone capture if you import it separately. The SPL uses numeric Zeek ts and flattened fields such as id_orig_h.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

Check the bounds against the metadata and confirm the connection and SMB sourcetypes. If _time stores ingestion time, find the indexed events first and use ts for the packet-era timeline.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp id_resp_p=445 ((id_orig_h=10.0.100.223 id_resp_h=10.0.100.5) OR (id_orig_h=10.0.100.5 id_resp_h=10.0.100.223))
| stats count as connections dc(id_orig_p) as client_ports sum(orig_pkts) as origin_packets
        sum(resp_pkts) as response_packets values(conn_state) as states by id_orig_h id_resp_h
| sort id_orig_h

Read each row as the originator and responder of the connection. origin_packets and response_packets describe the two sides of that directional row. The raw PCAP has 1,122 bidirectional packets on workstation-initiated TCP/445 flows to the DC, including ACKs and control packets. In the opposite direction, only three SYN packets are visible. The second and third use the same source port and TCP sequence number. Use Zeek connection states and Arkime to check how your ingest groups those packets.

1단계 · Splunk에서 양방향 TCP/445 비교

시간 범위를 UTC 5월 25일 AD 캡처 구간에 맞추고, <CASE>에 AD 캡처를 가져올 때 지정한 값을 넣습니다. Splunk 프로필 시간대를 UTC로 설정합니다. 단독 호스트 캡처도 가져온다면 별도 케이스 값을 지정합니다. 예제는 숫자형 Zeek ts와 id_orig_h처럼 평탄화된 필드를 사용합니다.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

시간 범위를 캡처 메타데이터와 비교하고 연결 및 SMB sourcetype을 확인합니다. _time이 수집 시각이면 먼저 이벤트가 조회되도록 검색 범위를 맞춘 뒤, 타임라인은 ts로 정렬합니다.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp id_resp_p=445 ((id_orig_h=10.0.100.223 id_resp_h=10.0.100.5) OR (id_orig_h=10.0.100.5 id_resp_h=10.0.100.223))
| stats count as connections dc(id_orig_p) as client_ports sum(orig_pkts) as origin_packets
        sum(resp_pkts) as response_packets values(conn_state) as states by id_orig_h id_resp_h
| sort id_orig_h

각 행을 연결 시작자와 응답자로 읽습니다. origin_packets와 response_packets는 그 방향에서 각각 송신·응답 측에 해당하는 패킷 수입니다. 원본 PCAP에서 워크스테이션이 시작한 DC 방향 TCP/445 흐름에는 양방향 1,122개 패킷이 있으며 ACK와 제어 패킷도 포함됩니다. DC가 반대 방향으로 시작한 흐름에서는 SYN 패킷 세 개가 보입니다. 두 번째와 세 번째 SYN은 출발지 포트와 TCP 시퀀스 번호가 같습니다. Zeek 연결 상태와 Arkime에서 수집 결과가 해당 패킷들을 어떻게 묶는지 확인합니다.

2 · Link the forward connection to its SMB file writes

SPL 
index=zeek pcap_case="<CASE>" id_orig_h=10.0.100.223 id_resp_h=10.0.100.5 id_orig_p=60879 id_resp_p=445
    sourcetype IN ("zeek:conn","zeek:smb_mapping","zeek:smb_files","zeek:dce_rpc","zeek:ntlm")
| sort 0 ts
| eval log_time=strftime(ts,"%Y-%m-%d %H:%M:%S.%3N %Z")
| table log_time sourcetype uid id_orig_p path name action endpoint operation conn_state

Take the uid from the verified workstation-to-DC connection. Use it for the share, file and RPC logs from the same Zeek processing run. If you indexed multiple runs, filter to one before making the pivot. Look for file write actions and filenames in zeek:smb_files and keep any share mappings attached to that UID. A missing file log may reflect parser or ingestion coverage. Confirm individual write replies in packets.

The following search takes the connection UID as <UID>. The output orders the available share, file and RPC records by Zeek event time.

SPL 
index=zeek pcap_case="<CASE>" uid="<UID>"

2단계 · 워크스테이션이 시작한 연결을 SMB 파일 쓰기와 연결

SPL 
index=zeek pcap_case="<CASE>" id_orig_h=10.0.100.223 id_resp_h=10.0.100.5 id_orig_p=60879 id_resp_p=445
    sourcetype IN ("zeek:conn","zeek:smb_mapping","zeek:smb_files","zeek:dce_rpc","zeek:ntlm")
| sort 0 ts
| eval log_time=strftime(ts,"%Y-%m-%d %H:%M:%S.%3N %Z")
| table log_time sourcetype uid id_orig_p path name action endpoint operation conn_state

확인된 워크스테이션→DC 연결 행에서 uid를 가져옵니다. 같은 Zeek 처리 실행에서 나온 SMB 공유·파일·RPC 로그를 이 값으로 찾아갑니다. 여러 실행을 인덱싱했다면 먼저 한 실행으로 제한합니다. zeek:smb_files에서 쓰기 작업과 파일 이름을 찾고 해당 UID에 연결된 공유 매핑도 확인합니다. 파일 로그가 조회되지 않으면 분석기와 수집 범위를 점검합니다. 개별 쓰기 응답은 패킷에서 확인합니다.

표의 쓰기 시각은 요청 시각이며 파일 이름은 줄여 표시했습니다. 성공 응답은 워크스테이션에서 DC로 파일 쓰기가 이뤄졌다는 근거입니다. 이 캡처의 역방향 SYN에는 응답이나 SMB 데이터가 관찰되지 않습니다. 호스트 탐색, 관리 점검 또는 현재 캡처 지점에서 응답이 누락된 연결일 수 있습니다. 역방향 파일 쓰기나 감염을 판단하려면 추가 트래픽 또는 엔드포인트 증거가 필요합니다.

3 · Inspect the two directions in Arkime

Arkime 
tags == "<CASE>" && ip.src == 10.0.100.223 && ip.dst == 10.0.100.5 && port.src == 60879 && port.dst == 445

Use the case tag applied during import. Inspect the packet pane around 01:27:31 UTC for the two forward write exchanges. Record the endpoints and ports alongside the times.

Arkime 
tags == "<CASE>" && ip.src == 10.0.100.5 && ip.dst == 10.0.100.223 && port.dst == 445

Then inspect DC-originated traffic around 01:34:18–01:34:27 UTC. Session collection can omit or group short attempts. If Arkime leaves the return traffic uncertain, check the original capture offline.

3단계 · Arkime에서 양방향 세션 확인

Arkime 
tags == "<CASE>" && ip.src == 10.0.100.223 && ip.dst == 10.0.100.5 && port.src == 60879 && port.dst == 445

가져오기 단계에서 붙인 케이스 태그를 사용합니다. 01:27:31 UTC 전후 패킷에서 워크스테이션이 보낸 두 쓰기와 DC의 응답을 확인합니다. 시각과 함께 출발지·목적지 주소와 포트를 기록합니다.

Arkime 
tags == "<CASE>" && ip.src == 10.0.100.5 && ip.dst == 10.0.100.223 && port.dst == 445

이어서 01:34:18–01:34:27 UTC에 DC가 시작한 트래픽을 살핍니다. 세션 수집 과정에서 짧은 연결 시도가 빠지거나 한 세션으로 묶일 수 있습니다. Arkime에서 응답 유무가 불분명하면 원본 캡처를 오프라인으로 조회합니다.

4 · Confirm the reverse TCP flags if needed

TShark 
tshark -n -r "2018-05-24-Trickbot-infection-in-AD-environment.pcap" \
  -Y '((ip.src == 10.0.100.5 && ip.dst == 10.0.100.223 && tcp.dstport == 445) || (ip.src == 10.0.100.223 && ip.dst == 10.0.100.5 && tcp.srcport == 445))' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e ip.src -e ip.dst \
  -e tcp.srcport -e tcp.dstport -e tcp.flags.syn -e tcp.flags.ack -e tcp.flags.reset -e tcp.len

This filter reads both packet directions of DC-initiated TCP/445 and reports flags and TCP payload length. Look for any reverse-flow SYN/ACK, reset or data from the answering host. Match the ports and UTC time before interpreting the flags. The filter excludes the separate workstation-initiated file-write stream.

4단계 · 필요한 경우 역방향 TCP 플래그를 확인

TShark 
tshark -n -r "2018-05-24-Trickbot-infection-in-AD-environment.pcap" \
  -Y '((ip.src == 10.0.100.5 && ip.dst == 10.0.100.223 && tcp.dstport == 445) || (ip.src == 10.0.100.223 && ip.dst == 10.0.100.5 && tcp.srcport == 445))' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e ip.src -e ip.dst \
  -e tcp.srcport -e tcp.dstport -e tcp.flags.syn -e tcp.flags.ack -e tcp.flags.reset -e tcp.len

DC가 시작한 TCP/445 흐름에서 요청과 응답 방향의 TCP 플래그 및 페이로드 길이를 확인합니다. 워크스테이션이 SYN/ACK, RST 또는 데이터를 반환했는지 살핍니다. 플래그를 해석하기 전에 포트와 UTC 시각을 확인합니다. 이 필터의 범위는 DC가 시작한 연결입니다.

5 · Document the transfer and assign separate follow-up

Attach the AD capture hash and UTC scope to the ticket. Record the confirmed direction, source port 60879, write request and response frames, and filename prefixes. Ask the DC owner for file creation, process and service records around the write window and check approved deployment activity. Put the reverse SYNs in a separate observation and ask for firewall and workstation telemetry if their cause matters to incident scope. Record the standalone run as outside this ticket's capture scope.

5단계 · 전송 증거와 역방향 후속 점검 기록

티켓에 AD 캡처의 해시와 UTC 범위를 남깁니다. 확인한 전송 방향, 출발지 포트 60879, 쓰기 요청·응답 프레임, 파일 이름의 앞부분을 기록합니다. DC 담당자에게 해당 시간의 파일 생성·프로세스·서비스 기록을 요청하고 승인된 배포 작업이 있었는지 확인합니다. 역방향 SYN은 별도 관찰 항목으로 남기고, 사고 범위 판단에 필요하면 방화벽 및 워크스테이션 로그를 요청합니다. 단독 호스트 캡처는 이 티켓의 조사 범위에서 제외합니다.
