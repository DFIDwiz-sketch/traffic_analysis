Which connections actually upgraded to WebSocket?

The publisher describes traffic from an Android malware infection, including an app-generated WebSocket session. In the PCAP, 10.10.2.101 sends HTTP requests with Upgrade: websocket and receives 101 Switching Protocols on matching TCP connections. Another TCP connection to one of the same servers receives HTTP 408. The connection tuple and the request-reply pair determine which outcome applies.

어느 연결에서 WebSocket으로 전환됐나

공개 원문은 Android 악성코드 감염과 앱이 생성한 WebSocket 트래픽을 설명합니다. 원본 PCAP에서 10.10.2.101은 Upgrade: websocket 요청을 보내고 같은 TCP 연결에서 101 Switching Protocols를 받았습니다. 같은 서버의 다른 TCP 연결에서는 HTTP 408이 돌아왔습니다. 각 결과는 연결의 주소·포트와 요청·응답 쌍으로 확인합니다.

감염 맥락과 앱 관련 설명은 공개 원문에 근거합니다. 연결의 주소·포트와 HTTP 헤더, 시각은 원본 PCAP에서 확인했습니다. 검색 예제는 각자의 실습 환경에서 검증합니다.

1 · Baseline the mobile host in Splunk

Set the display timezone to UTC, include the capture interval and use the import tag for <CASE>. If _time is ingestion time, widen the time picker and use numeric Zeek ts for the timeline. The examples use flattened fields.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

Confirm the presence of connection and HTTP records. An incomplete or unrecognized HTTP exchange can lack an application row.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" id_orig_h=10.10.2.101 proto=tcp id_resp_p=8080
| stats count as connections values(conn_state) as states sum(orig_pkts) as outbound_packets
    sum(resp_pkts) as inbound_packets by id_resp_h
| sort 0 - connections

Compare TCP/8080 destinations, packet direction and connection states. A TCP state confirms transport behavior. Determine protocol changes from the HTTP exchange within the selected flow.

1단계 · Splunk에서 모바일 호스트 베이스라인 확인

UTC로 표시하고 전체 캡처 시간 범위를 포함합니다. <CASE>에 가져올 때 지정한 태그를 넣습니다. Splunk _time이 수집 시각이면 시간 범위를 넓히고 숫자형 Zeek ts로 사건 시각을 읽습니다. 예제는 평탄화된 필드를 사용합니다.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

연결 및 HTTP 로그가 조회되는지 확인합니다. 불완전하거나 분석기가 인식하지 못한 교환은 응용 계층 행이 빠질 수 있습니다.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" id_orig_h=10.10.2.101 proto=tcp id_resp_p=8080
| stats count as connections values(conn_state) as states sum(orig_pkts) as outbound_packets
    sum(resp_pkts) as inbound_packets by id_resp_h
| sort 0 - connections

TCP/8080의 목적지, 양방향 패킷 수와 연결 상태를 비교합니다. TCP 상태는 전송 계층을 설명합니다. 프로토콜 전환 여부는 각 흐름의 HTTP 교환에서 확인합니다.

2 · Match the upgrade request to its reply

SPL 
index=zeek sourcetype=zeek:http pcap_case="<CASE>" id_orig_h=10.10.2.101 id_resp_p=8080
    id_resp_h IN ("101.32.207.8","43.159.143.39") status_code IN (101,408)
| stats count as rows dc(uid) as distinct_connections min(ts) as first max(ts) as last by id_resp_h status_code

Use this search to group logged 101 or 408 statuses by responder and count distinct UIDs. A server reply without a visible request may lack a paired HTTP record in Zeek. Inspect the original packets where a row is missing.

SPL 
index=zeek pcap_case="<CASE>" uid="<TCP_UID>" sourcetype IN ("zeek:conn","zeek:http")
| sort 0 ts
| table ts sourcetype uid id_orig_p id_resp_h id_resp_p service conn_state method status_code trans_depth

Use the UID from the TCP tuple to look up application and connection logs from the same Zeek processing run. Limit a re-imported case to one run before using the UID. Read the response code and flow tuple. Check the request and response for the WebSocket upgrade header. The original PCAP shows seven distinct request/101 pairs to 101.32.207.8 and one to 43.159.143.39, identified by source port on TCP/8080.

A successful upgrade establishes the protocol switch for a connection. Legitimate mobile apps also use WebSockets, and a timeout can follow an idle connection. App ownership, exchanged application data and incident impact need further evidence.

2단계 · 전환 요청과 해당 응답 연결

SPL 
index=zeek sourcetype=zeek:http pcap_case="<CASE>" id_orig_h=10.10.2.101 id_resp_p=8080
    id_resp_h IN ("101.32.207.8","43.159.143.39") status_code IN (101,408)
| stats count as rows dc(uid) as distinct_connections min(ts) as first max(ts) as last by id_resp_h status_code

조회된 101과 408을 목적지별로 묶고 고유 UID 수를 확인합니다. 요청이 관찰되지 않은 서버 응답은 Zeek의 HTTP 행으로 짝지어지지 않을 수 있으므로 원본 패킷을 살핍니다.

SPL 
index=zeek pcap_case="<CASE>" uid="<TCP_UID>" sourcetype IN ("zeek:conn","zeek:http")
| sort 0 ts
| table ts sourcetype uid id_orig_p id_resp_h id_resp_p service conn_state method status_code trans_depth

TCP 연결의 UID를 사용해 같은 Zeek 처리 실행의 연결 및 응용 계층 행을 찾습니다. 여러 번 가져온 캡처라면 한 처리 실행으로 제한합니다. 응답 코드와 연결 주소·포트를 비교하고 요청과 응답의 WebSocket 전환 헤더를 확인합니다. 원본 TCP/8080에서 출발지 포트별로 101.32.207.8에 요청과 101 쌍 일곱 건, 43.159.143.39에 한 건을 확인했습니다.

전환에 성공하면 해당 연결의 프로토콜이 바뀌었다는 근거가 됩니다. 정상 모바일 앱도 WebSocket을 사용하며 유휴 연결은 시간이 초과될 수 있습니다. 실행 앱, 응용 계층 데이터와 침해 영향은 별도 근거가 필요합니다.

3 · Cross-check the successful and timed-out sessions in Arkime

Arkime 
tags == "<CASE>" && ip.src == 10.10.2.101 && ip.dst == 101.32.207.8 && port.dst == 8080 && (port.src == 49292 || port.src == 40136)

Apply the case tag and UTC range around 22:53–22:55. Compare client ports 49292 and 40136 in the packet pane. Confirm the request and 101 on one tuple and the 408 on the other.

Arkime 
tags == "<CASE>" && ip.src == 10.10.2.101 && ip.dst == 43.159.143.39 && port.src == 59140 && port.dst == 8080

Check the later request and 101 around 22:57:04 UTC. Use the addresses, ports and timestamps to align with the source frames.

Arkime

케이스 태그와 22:53~22:55 UTC 구간을 적용합니다. 패킷 화면에서 출발지 포트 49292와 40136을 비교해 한 연결의 요청과 101, 별도 연결의 408을 각각 확인합니다.

22:57:04 UTC 전후의 후속 요청과 101을 봅니다. 주소·포트와 시각으로 원본 프레임을 대조합니다.

4 · Read selected HTTP headers offline if needed

TShark 
tshark -n -r "2025-10-02-traffic-from-infected-Android-phone.pcap" \
  -Y 'frame.number == 18303 || frame.number == 18307 || frame.number == 18535 || frame.number == 19767 || frame.number == 19769' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e tcp.srcport -e tcp.dstport \
  -e http.request.method -e http.response.code -e http.upgrade

If Arkime leaves the upgrade unclear, compare the original frames for the two upgrades and the one 408. The method, response code and upgrade fields help show which result belongs to each tuple. The example reads header metadata from the saved capture.

4단계 · 필요한 경우 선택한 헤더를 오프라인 확인

TShark 
tshark -n -r "2025-10-02-traffic-from-infected-Android-phone.pcap" \
  -Y 'frame.number == 18303 || frame.number == 18307 || frame.number == 18535 || frame.number == 19767 || frame.number == 19769' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e tcp.srcport -e tcp.dstport \
  -e http.request.method -e http.response.code -e http.upgrade

Arkime에서 전환 과정이 불분명하면 두 전환과 한 408의 원본 프레임을 읽습니다. 메서드, 응답 코드와 전환 헤더를 각 연결의 주소·포트에 연결합니다. 이 예제는 저장된 캡처의 헤더 메타데이터를 조회합니다.

5 · Document the sessions and verify app ownership

Record the capture hash, handset IP and the tuples and frames for confirmed upgrades and the timeout. Note that the POST used a separate connection. Ask for device network and installation logs, app identity and approved mobile-app inventory. Correlate with proxy or firewall records before assigning the traffic to a process or claiming data exposure.

5단계 · 세션을 기록하고 실행 앱 확인

캡처 해시, 휴대전화 IP, 전환과 시간 초과의 연결 주소·포트 및 프레임을 남깁니다. POST는 별도 연결로 기록합니다. 단말 네트워크 및 설치 로그, 앱 식별 정보와 승인 앱 목록을 요청합니다. 실행 프로세스나 데이터 노출을 판단하기 전에 프록시 또는 방화벽 기록을 대조합니다.
