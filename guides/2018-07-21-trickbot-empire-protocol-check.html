What was really running on ports 80 and 443?

The publisher describes an overnight Trickbot infection followed by PowerShell Empire activity. On the client 10.7.21.101, the original capture shows an early HTTP GET on TCP/80, a later exchange on TCP/80 whose selected packets lack recognizable HTTP headers, and plaintext HTTP requests and responses on TCP/443. Use the comparisons to determine the protocol from what each session contains.

80번과 443번 포트에서 실제로 어떤 프로토콜을 썼는가?

원문은 밤사이 Trickbot 감염이 발생하고 이후 PowerShell Empire 활동이 이어졌다고 설명합니다. 원본 캡처에서 클라이언트 10.7.21.101은 먼저 TCP/80으로 HTTP GET을 보냅니다. 이후 다른 TCP/80 연결의 조사 대상 패킷에서는 식별 가능한 HTTP 헤더가 보이지 않습니다. 더 늦은 TCP/443 연결에서는 평문 HTTP 요청과 응답이 확인됩니다. 각 세션에 담긴 근거로 프로토콜을 판단합니다.

1 · Baseline the client across the capture

Use the capture’s case tag for <CASE>. Cover the full UTC interval in Splunk, and check whether the time picker uses capture time or ingest time. Use Zeek ts for correlation and display the times in UTC. The examples use flattened field names.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

Read the inventory first. Check that the connection and HTTP logs are present, and note whether the import produced SSL logs. Analyze SSL log coverage alongside the packet evidence.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" id_orig_h=10.7.21.101 proto=tcp
| eval hour=floor(ts/3600)*3600, service_label=coalesce(mvjoin(service,","),"unidentified")
| stats count as connections dc(id_resp_h) as destinations
    sum(orig_bytes) as client_payload_bytes by hour id_resp_p service_label
| sort 0 hour

Compare hourly connection counts, destination counts and client payload bytes for each port and Zeek service label. Look near 03:02, 07:12 and 10:42 UTC. A missing service label can reflect parser coverage or an incomplete stream. The baseline describes this one client during the capture.

1 · 전체 캡처 구간에서 클라이언트 베이스라인 만들기

<CASE>에 캡처의 사례 태그를 입력합니다. Splunk에서 전체 UTC 캡처 구간을 포함하고 시간 선택기가 캡처 시각과 수집 시각 중 무엇을 쓰는지 확인합니다. 상관분석에는 Zeek ts를 쓰고 UTC로 표시합니다. 예시는 평탄화된 필드명을 사용합니다.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

먼저 로그 종류를 확인합니다. 연결 및 HTTP 로그가 있는지 확인하고 SSL 로그 생성 여부를 기록합니다. SSL 로그의 수집 범위는 패킷 근거와 함께 검토합니다.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" id_orig_h=10.7.21.101 proto=tcp
| eval hour=floor(ts/3600)*3600, service_label=coalesce(mvjoin(service,","),"unidentified")
| stats count as connections dc(id_resp_h) as destinations
    sum(orig_bytes) as client_payload_bytes by hour id_resp_p service_label
| sort 0 hour

포트와 Zeek 서비스별로 시간대별 연결 수, 목적지 수, 클라이언트 페이로드 바이트를 비교합니다. 03:02, 07:12, 10:42 UTC 전후를 살펴봅니다. 서비스 값이 비어 있으면 파서의 처리 범위나 스트림 누락을 확인합니다. 이 베이스라인은 캡처 구간의 해당 클라이언트를 설명합니다.

2 · Correlate candidate sessions and build the timeline

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" id_orig_h=10.7.21.101
    ((id_resp_h=109.234.39.56 id_resp_p=80) OR (id_resp_h=162.244.32.142 id_resp_p=443))
| sort 0 ts
| table ts uid id_orig_p id_resp_h id_resp_p service conn_state orig_bytes resp_bytes

For TCP/80, start with the row for client port 49392. For TCP/443, use client ports 49493 and 49494 to find the documented GET and POST. Check the originator and responder byte counts, then copy one row’s UID at a time.

SPL 
index=zeek pcap_case="<CASE>" uid="<TCP_UID>" sourcetype IN ("zeek:conn","zeek:http","zeek:ssl")
| sort 0 ts
| table ts sourcetype uid id_orig_p id_resp_h id_resp_p trans_depth method status_code server_name

Use the same case and the same Zeek processing run when matching the connection to HTTP or SSL logs by uid. Choose one run first if the capture was ingested more than once. An HTTP connection may have multiple transactions. Use trans_depth and ts to keep them distinct. Missing HTTP records on an unexpected port warrant packet review.

2 · 후보 세션을 연결하고 타임라인 만들기

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" id_orig_h=10.7.21.101
    ((id_resp_h=109.234.39.56 id_resp_p=80) OR (id_resp_h=162.244.32.142 id_resp_p=443))
| sort 0 ts
| table ts uid id_orig_p id_resp_h id_resp_p service conn_state orig_bytes resp_bytes

TCP/80은 클라이언트 포트 49392의 행부터 살펴봅니다. TCP/443은 49493과 49494에서 각각 아래 GET과 POST를 찾습니다. 송신 측과 응답 측 바이트 수를 확인하고 행별 UID를 복사합니다.

SPL 
index=zeek pcap_case="<CASE>" uid="<TCP_UID>" sourcetype IN ("zeek:conn","zeek:http","zeek:ssl")
| sort 0 ts
| table ts sourcetype uid id_orig_p id_resp_h id_resp_p trans_depth method status_code server_name

사례가 같고 동일한 Zeek 처리 실행에 속한 연결, HTTP, SSL 로그를 uid로 연결합니다. 캡처를 여러 번 수집했다면 먼저 실행 한 건을 선택합니다. HTTP 연결 하나에 트랜잭션이 여러 개일 수 있으므로 trans_depth와 ts로 구분합니다. 비표준 포트에서 HTTP 기록이 비어 있으면 패킷으로 확인합니다.

07:12의 선택 프레임에서 양방향 데이터 교환이 확인됩니다. 이 목적지로 향한 조사 대상 페이로드의 시작 부분에서는 식별 가능한 HTTP 요청 줄을 찾지 못했습니다. 정확한 애플리케이션 프로토콜은 추가 확인이 필요합니다. 원문은 이후 통신이 감염과 관련 있다고 설명합니다. 승인된 소프트웨어도 비표준 포트를 사용할 수 있으므로 시각이 가까운 세션들의 실행 프로세스는 별도 근거로 확인합니다.

Arkime

Find the session at 07:12 UTC and verify the TCP tuple and both directions of payload. Use the visible packet headers to compare this exchange with the early GET on TCP/80. Record the observation using the session time and tuple, since exported packets can have different frame numbers.

Arkime

Look at the sessions with client ports 49493 and 49494. In the packet view, locate the GET and POST request lines and the server’s HTTP status lines. Inspect that evidence independently of the protocol label shown in the session list.

07:12 UTC 세션을 찾고 TCP 연결의 주소와 포트, 양방향 페이로드를 확인합니다. 패킷에 보이는 헤더를 초반 TCP/80의 GET과 대조합니다. 내보내기 후 프레임 번호가 달라질 수 있으므로 세션 시각과 주소·포트도 기록합니다.

Arkime

클라이언트 포트가 49493, 49494인 세션을 엽니다. 패킷 보기에서 GET, POST 요청 줄과 서버의 HTTP 응답 상태 줄을 찾아 세션 목록의 프로토콜 표시와 대조합니다.

4 · Confirm only the four HTTP headers offline if needed

TShark 
tshark -n -r "2018-07-21-Trickbot-infection-with-PowerShell-Empire.pcap" -d tcp.port==49493,http -d tcp.port==49494,http \
  -Y 'frame.number == 20358 || frame.number == 20360 || frame.number == 20372 || frame.number == 20376' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e tcp.stream -e tcp.srcport \
  -e tcp.dstport -e http.request.method -e http.response.code

If the Arkime view leaves the request or response unclear, use the original capture. Decode HTTP on the two observed client ports and display only four frames. Match each method and response via tcp.stream. The decode hint addresses the nonstandard server port, and the decoded HTTP fields let you check the specific headers without returning bodies.

4 · 필요할 때만 HTTP 헤더 네 개를 오프라인에서 확인하기

TShark 
tshark -n -r "2018-07-21-Trickbot-infection-with-PowerShell-Empire.pcap" -d tcp.port==49493,http -d tcp.port==49494,http \
  -Y 'frame.number == 20358 || frame.number == 20360 || frame.number == 20372 || frame.number == 20376' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e tcp.stream -e tcp.srcport \
  -e tcp.dstport -e http.request.method -e http.response.code

Arkime에서 요청이나 응답을 판단하기 어려우면 원본 캡처의 네 프레임만 확인합니다. 관찰한 클라이언트 포트 두 개에 HTTP 디코딩을 적용하고 tcp.stream으로 요청 메서드와 응답 코드를 짝짓습니다. 이 디코딩 지정은 서버가 비표준 포트를 사용하는 경우에 적용하며, 선택한 헤더 필드만 출력합니다.

5 · Record protocol findings and follow up

Put the capture hash, UTC observations, full tuples and frame numbers in the SOC ticket. Record the use of plaintext HTTP on TCP/443 as a packet finding and use proxy and endpoint network logs to identify the originating process. Review approved software and egress controls. Link any independently corroborated process evidence to the original observations before attributing both exchanges to the same activity.
