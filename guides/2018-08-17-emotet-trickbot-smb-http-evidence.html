Which DC request matches the internal traffic?

The publisher reports Emotet followed by Trickbot on a workstation and Trickbot reaching the domain controller (DC). In the original PCAP, 172.16.8.205 sent TCP/445 data containing a URL to the DC at 172.16.8.5. The DC made two GET requests to the same server on separate connections. The first matches the URL bytes. Both response headers indicate HTTP 200, image/png and a length of 539,136 bytes, so the headers alone cannot link a particular request to the internal data.

DC의 어느 요청이 내부 트래픽과 일치하나

공개 원문은 워크스테이션에서 Emotet에 이어 Trickbot이 관찰됐고, Trickbot이 도메인 컨트롤러(DC)로 확산됐다고 보고합니다. 원본 PCAP에서 172.16.8.205는 DC 172.16.8.5로 URL이 포함된 TCP/445 데이터를 보냈습니다. DC는 같은 서버에 별개 연결로 GET 요청을 두 번 했고, 첫 요청이 해당 URL 바이트와 일치합니다. 두 응답 헤더 모두 HTTP 200, image/png, 길이 539,136바이트를 표시합니다. 헤더만으로는 앞선 내부 트래픽에 해당하는 요청을 특정하기 어렵습니다.

호스트 역할, 악성코드 계열과 확산 방식에 대한 판단은 공개 원문에 근거합니다. TCP 페이로드에서의 일치 여부, 요청 순서, 응답 헤더와 프레임 번호는 원본 PCAP에서 직접 확인했습니다. 아래 검색은 자신의 수집 환경에서 검증하는 예제입니다.

1 · Establish the case baseline in Splunk

Set the display timezone to UTC, cover the capture range, and use the case value assigned at ingest for <CASE>. If Splunk uses ingestion time as _time, widen the picker and use the numeric Zeek ts field for the timeline. The examples use flattened Zeek field names.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

Confirm that the case has connection and HTTP records. Check whether share, file and RPC records are present. Availability depends on analyzer coverage and the import.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp id_resp_p=445 id_orig_h=172.16.8.205
| stats count as connections dc(id_orig_p) as source_ports sum(orig_pkts) as sent_packets
        sum(resp_pkts) as reply_packets values(conn_state) as states by id_orig_h id_resp_h
| sort 0 - connections

Rank the workstation's TCP/445 destinations and compare state and packet direction. The capture has 3,809 bilateral packets for workstation-originated TCP/445 to the DC, including ACKs and control traffic. The matching URL appears in 18 client-to-DC data packets using 18 distinct source ports in a short burst. Preserve the connection tuple when selecting a representative packet. Treat the burst as activity toward one DC.

1단계 · Splunk에서 케이스 베이스라인 설정

표시 시간대를 UTC로 설정하고 캡처 구간을 선택합니다. <CASE>에는 수집 때 지정한 케이스 값을 넣습니다. Splunk의 _time이 수집 시각이면 검색 범위를 넓히고 타임라인에는 숫자형 Zeek ts를 사용합니다. 검색은 평탄화된 Zeek 필드를 기준으로 합니다.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

케이스에 연결과 HTTP 로그가 있는지 확인합니다. 공유·파일·RPC 로그도 확인합니다. 로그 유무는 분석기와 수집 범위에 따라 달라집니다.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp id_resp_p=445 id_orig_h=172.16.8.205
| stats count as connections dc(id_orig_p) as source_ports sum(orig_pkts) as sent_packets
        sum(resp_pkts) as reply_packets values(conn_state) as states by id_orig_h id_resp_h
| sort 0 - connections

워크스테이션의 TCP/445 목적지별 연결 수, 상태와 패킷 방향을 비교합니다. 원본에서는 워크스테이션이 시작한 DC 방향 TCP/445 흐름에서 ACK와 제어 트래픽을 포함해 양방향 패킷 3,809개가 보입니다. 일치하는 URL은 짧은 시간에 서로 다른 출발지 포트 18개를 쓴 워크스테이션→DC 데이터 패킷 18개에서 관찰됐습니다. 대표 패킷을 선택할 때는 주소와 포트를 함께 남깁니다. 이 전송은 한 DC를 향한 활동입니다.

2 · Compare request paths across two HTTP sessions

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" id_orig_h=172.16.8.205 id_resp_h=172.16.8.5 id_resp_p=445 id_orig_p=49234
| table ts uid id_orig_h id_orig_p id_resp_h id_resp_p duration conn_state missed_bytes

Locate the TCP/445 connection from client port 49234 around 17:19:06 UTC. Keep the UID for SMB and RPC searches from the same Zeek processing run. If you imported the case multiple times, filter down to one run first.

SPL 
index=zeek pcap_case="<CASE>" uid="<SMB_UID>"
    sourcetype IN ("zeek:conn","zeek:smb_mapping","zeek:smb_files","zeek:dce_rpc","zeek:ntlm")
| sort 0 ts
| eval log_time=strftime(ts,"%Y-%m-%d %H:%M:%S.%3N %Z")
| table log_time sourcetype uid path name action endpoint operation

Use the UID to look for analyzer-provided context. The PCAP carries URL bytes on TCP/445. A lack of events in a particular SMB sourcetype does not resolve whether those bytes are present.

SPL 
index=zeek sourcetype=zeek:http pcap_case="<CASE>" id_orig_h=172.16.8.5
    id_resp_h=213.183.63.124 id_resp_p=80 method=GET
| sort 0 ts
| eval log_time=strftime(ts,"%Y-%m-%d %H:%M:%S.%3N %Z")
| table log_time uid id_orig_p host uri status_code resp_mime_types response_body_len

Read uri with host, the client port and time for each GET to the same server. Use each HTTP UID for its own Zeek connection from the same run. Link the internal and external observations using the DC IP, timing and exact Host and path. Keep header-declared content type and length separate from any analyzer's inferred MIME type or measured body length.

UTC · 17 August Original frames Directly observed

17:19:06.469 5809 DC source port 57761 sends a GET whose Host and path match the earlier UTF-16LE URL
17:19:06.878 5811 HTTP 200, declared image/png, length 539,136 bytes
17:21:44.813 17451 DC source port 57773 sends a GET to the same host with a different path
17:21:45.193 17455 HTTP 200 and the same declared type and length as the earlier response

The first GET follows frame 5668 by about 432 ms. The later request shares the destination and header values but uses a different path. An ordinary web request or an approved update can produce similar headers. The exact path match and order support the first correlation. The headers do not establish content identity or code execution.

2단계 · 두 HTTP 연결의 요청 경로 비교

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" id_orig_h=172.16.8.205 id_resp_h=172.16.8.5 id_resp_p=445 id_orig_p=49234
| table ts uid id_orig_h id_orig_p id_resp_h id_resp_p duration conn_state missed_bytes

17:19:06 UTC 전후 출발지 포트 49234의 TCP/445 연결을 찾습니다. UID는 같은 Zeek 처리 실행의 SMB 및 RPC 검색에 사용합니다. 여러 번 가져왔다면 먼저 한 실행으로 제한합니다.

SPL 
index=zeek pcap_case="<CASE>" uid="<SMB_UID>"
    sourcetype IN ("zeek:conn","zeek:smb_mapping","zeek:smb_files","zeek:dce_rpc","zeek:ntlm")
| sort 0 ts
| eval log_time=strftime(ts,"%Y-%m-%d %H:%M:%S.%3N %Z")
| table log_time sourcetype uid path name action endpoint operation

UID로 분석기가 기록한 맥락을 확인합니다. TCP/445에 포함된 URL 바이트는 원본 PCAP에서 확인할 수 있습니다. 특정 SMB 로그가 조회되지 않아도 패킷에서 확인할 수 있는 부분은 별도로 살핍니다.

SPL 
index=zeek sourcetype=zeek:http pcap_case="<CASE>" id_orig_h=172.16.8.5
    id_resp_h=213.183.63.124 id_resp_p=80 method=GET
| sort 0 ts
| eval log_time=strftime(ts,"%Y-%m-%d %H:%M:%S.%3N %Z")
| table log_time uid id_orig_p host uri status_code resp_mime_types response_body_len

같은 서버로 향한 GET마다 uri, host, 출발지 포트와 시각을 함께 확인합니다. 각 HTTP UID는 같은 Zeek 실행에서 자신의 연결 기록을 찾을 때 사용합니다. 내부와 외부 트래픽은 DC IP, 시각, Host와 경로의 정확한 일치 여부로 대조합니다. 응답 헤더의 선언된 유형·길이는 분석기가 추정한 MIME이나 실제 수집된 본문 길이와 별도로 해석합니다.

8월 17일 UTC 원본 프레임 직접 확인한 근거
17:19:06.038–17:19:06.040 5668–5736 워크스테이션→DC TCP/445에서 URL이 확인된 패킷 18개의 구간. 대표 프레임 5668의 출발지 포트는 49234.
17:19:06.469 5809 DC 출발지 포트 57761에서 앞선 UTF-16LE URL과 Host·경로가 일치하는 GET 전송
17:19:06.878 5811 HTTP 200, 선언된 유형 image/png, 길이 539,136바이트
17:21:44.813 17451 DC 출발지 포트 57773에서 같은 호스트의 다른 경로로 GET 전송
17:21:45.193 17455 HTTP 200 및 앞선 응답과 같은 선언 유형·길이

첫 GET은 프레임 5668에서 약 432ms 뒤에 나타납니다. 나중 요청은 목적지와 응답 헤더 값이 같고 경로가 다릅니다. 일반 웹 요청이나 승인된 업데이트에서도 유사한 헤더가 나올 수 있습니다. 첫 요청과의 연관성은 경로의 정확한 일치와 순서가 뒷받침합니다. 파일의 정체나 코드 실행 여부에는 추가 증거가 필요합니다.

3 · Check the internal packet and both web sessions in Arkime

Arkime 
tags == "<CASE>" && ip.src == 172.16.8.205 && ip.dst == 172.16.8.5 && port.src == 49234 && port.dst == 445

Use the case tag and open the TCP/445 session around 17:19:06 UTC. Locate the workstation-to-DC packet using its address, ports and time. Compare the URL inside the offline packet view.

Arkime 
tags == "<CASE>" && ip.src == 172.16.8.5 && ip.dst == 213.183.63.124 && port.dst == 80

Open each of the two HTTP connections and align by source port 57761 and 57773. Compare their GET paths and responses. Use the original frame references with the tuple and timestamp because exported packet subsets can have different frame numbering.

3단계 · Arkime에서 내부 패킷과 두 웹 세션 확인

Arkime 
tags == "<CASE>" && ip.src == 172.16.8.205 && ip.dst == 172.16.8.5 && port.src == 49234 && port.dst == 445

케이스 태그를 적용해 17:19:06 UTC 전후 TCP/445 세션을 엽니다. 주소·포트와 시각으로 워크스테이션에서 DC로 향한 패킷을 찾고 오프라인 패킷 화면에서 URL을 대조합니다.

Arkime 
tags == "<CASE>" && ip.src == 172.16.8.5 && ip.dst == 213.183.63.124 && port.dst == 80

두 HTTP 연결을 출발지 포트 57761과 57773으로 구분해 GET 경로와 응답을 비교합니다. 일부 패킷만 내보냈다면 프레임 번호가 달라질 수 있으므로 원본 프레임과 주소·포트·시각을 함께 기록합니다.

4 · Read only the two response headers offline if needed

TShark 
tshark -n -r "2018-08-17-Emotet-infection-with-Trickbot.pcap" \
  -Y 'frame.number == 5811 || frame.number == 17455' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e tcp.dstport \
  -e http.response.code -e http.content_type -e http.content_length

If Arkime leaves the response headers unclear, read the two original frames with TShark. Compare status, content type and declared length using the destination port to distinguish replies. A content length is the value advertised by the server. The query reads header metadata only.

4단계 · 필요한 경우 응답 헤더 두 건만 오프라인 조회

TShark 
tshark -n -r "2018-08-17-Emotet-infection-with-Trickbot.pcap" \
  -Y 'frame.number == 5811 || frame.number == 17455' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e tcp.dstport \
  -e http.response.code -e http.content_type -e http.content_length

Arkime에서 헤더 확인이 어렵다면 TShark로 원본 프레임 두 개를 읽습니다. 응답의 목적지 포트로 두 연결을 구분하고 상태, 콘텐츠 유형과 선언 길이를 비교합니다. 길이는 서버가 헤더에 기재한 값입니다. 이 조회는 헤더 메타데이터만 출력합니다.

5 · Record the matched request and scope host follow-up

Record both internal and outbound tuples, original frames, time offset, capture hash and separate findings for the two HTTP requests. Verify endpoint process ownership for the first DC request and collect file creation, execution and proxy telemetry around it. Check scheduled update or maintenance activity if plausible. Keep any claim about downloaded file identity or endpoint compromise tied to separately verified evidence.

5단계 · 일치하는 요청을 기록하고 호스트 증거 확인

내부와 외부 연결의 주소·포트, 프레임, 시간차, 캡처 해시를 남기고 HTTP 요청 두 건은 각각 기록합니다. 첫 요청을 보낸 DC 프로세스를 확인하고 당시 파일 생성·실행·프록시 기록을 요청합니다. 예약된 업데이트나 유지보수 가능성도 확인합니다. 다운로드된 파일의 정체나 호스트 침해 판단에는 별도로 확인된 근거를 첨부합니다.
