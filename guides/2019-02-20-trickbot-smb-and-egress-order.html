Do file-write direction and outbound activity identify the same first host?

The publisher identifies an Emotet, IcedID and Trickbot incident in the PelicanWorks lab. In the original PCAP, workstation 10.2.20.101 writes to two .exe objects on the C$ share of DC 10.2.20.2. Later the DC sends the first observed HTTP POST of the pair to 190.146.112.216:8082. The workstation posts to the same endpoint about four minutes later. Track the write direction and the egress order independently.

파일 쓰기 방향과 외부 통신 순서는 무엇을 보여 주는가?

공개 원문은 PelicanWorks 실습의 Emotet, IcedID, Trickbot 감염을 설명합니다. 원본에서 워크스테이션 10.2.20.101은 DC 10.2.20.2의 C$에 .exe 객체 두 개를 씁니다. 이후 190.146.112.216:8082로 향한 두 호스트의 HTTP POST 중 DC의 요청이 먼저 관찰됩니다. 약 4분 뒤 워크스테이션도 같은 목적지로 POST를 보냅니다. 파일 쓰기 방향과 외부 통신 순서를 각각 확인합니다.

악성코드 분류와 호스트 역할은 원문에 근거합니다. 아래 프레임, 통신 방향, 응답 결과는 원본에서 확인했습니다. SPL은 자신의 Zeek 수집 환경에서 검증할 예시입니다.

1 · Baseline internal writes and external traffic for both hosts

Set <CASE> to your capture tag. Cover the full capture period in UTC. If your time picker uses ingest time, include that interval and use Zeek ts for capture time. The examples use flattened fields.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

Confirm connection, SMB and HTTP records are present. A missing SMB log can reflect analyzer coverage, especially with older dialects.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp id_resp_p IN (445,8082)
    id_orig_h IN ("10.2.20.101","10.2.20.2")
| eval minute=floor(ts/60)*60
| stats dc(uid) as connections values(conn_state) as states sum(orig_bytes) as orig_payload
    by minute id_orig_h id_resp_h id_resp_p
| sort 0 minute

Compare the originator, responder, port and minute. The original capture contains 2,031 bilateral TCP/445 packets for workstation-originated flows to the DC and three DC-originated SYN frames to the workstation without a captured reply on those flows. The SPL counts connections by UID, which differ from frame counts.

1 · 두 호스트의 내부 SMB와 외부 통신을 기준선으로 잡기

<CASE>에 캡처 태그를 넣고 전체 캡처 구간을 UTC로 표시합니다. 시간 선택기가 수집 시각을 사용하면 해당 구간을 포함한 뒤 Zeek ts로 캡처 시각을 봅니다. 예시는 평탄화된 필드명을 사용합니다.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

연결, SMB, HTTP 로그의 수집 범위를 확인합니다. 구형 SMB 등 일부 교환은 분석기가 처리하지 못할 수 있습니다.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp id_resp_p IN (445,8082)
    id_orig_h IN ("10.2.20.101","10.2.20.2")
| eval minute=floor(ts/60)*60
| stats dc(uid) as connections values(conn_state) as states sum(orig_bytes) as orig_payload
    by minute id_orig_h id_resp_h id_resp_p
| sort 0 minute

시작 호스트, 응답자, 포트, 분 단위로 비교합니다. 원본에서 워크스테이션이 시작한 DC 방향 TCP/445 흐름에는 양방향 패킷 2,031개가 있습니다. 반대 방향으로는 DC가 보낸 SYN 프레임 세 개에서 응답이 관찰되지 않았습니다. SPL의 연결 UID 집계는 프레임 수와 다른 단위입니다.

2 · Pair acknowledgements and order the POSTs

SPL 
index=zeek pcap_case="<CASE>" id_orig_h=10.2.20.101 id_resp_h=10.2.20.2 id_orig_p=49502 id_resp_p=445
    sourcetype IN ("zeek:conn","zeek:smb_mapping","zeek:smb_files","zeek:dce_rpc")
| sort 0 ts
| table ts sourcetype uid path share_type name action endpoint operation

Use the UID of client port 49502 from the same Zeek processing run to correlate connection, share, file and RPC records. In packets, follow the SMB tree and file handle through the file open and write. Match each write and DC response by SMB multiplex ID within that TCP session.

SPL 
index=zeek sourcetype=zeek:http pcap_case="<CASE>" id_resp_h=190.146.112.216 id_resp_p=8082 method=POST
    id_orig_h IN ("10.2.20.101","10.2.20.2")
| sort 0 ts
| table ts uid id_orig_h id_orig_p method trans_depth status_code

Compare the POST rows by source host and capture time. Each outbound HTTP connection has its own UID. Use uid and trans_depth to keep results with their own transactions. Report the first observed POST within this endpoint and port scope.

The accepted writes support a transfer to the DC. An authorized deployment could also write executable names to an administrative share. An external POST can come from a different process. The selected reverse SYN confirms a connection attempt. Execution, payload identity and causality across the two hosts need endpoint evidence.

2 · 파일 쓰기 응답을 연결하고 POST 순서를 확인하기

SPL 
index=zeek pcap_case="<CASE>" id_orig_h=10.2.20.101 id_resp_h=10.2.20.2 id_orig_p=49502 id_resp_p=445
    sourcetype IN ("zeek:conn","zeek:smb_mapping","zeek:smb_files","zeek:dce_rpc")
| sort 0 ts
| table ts sourcetype uid path share_type name action endpoint operation

클라이언트 포트 49502에 대해 동일한 Zeek 처리 실행에서 생성된 UID를 사용해 연결, 공유, 파일, RPC 로그를 연계합니다. 패킷에서는 SMB 트리와 파일 핸들로 열기와 쓰기를 추적합니다. 같은 TCP 세션 안에서 SMB 멀티플렉스 ID로 쓰기 요청과 DC 응답을 짝짓습니다.

SPL 
index=zeek sourcetype=zeek:http pcap_case="<CASE>" id_resp_h=190.146.112.216 id_resp_p=8082 method=POST
    id_orig_h IN ("10.2.20.101","10.2.20.2")
| sort 0 ts
| table ts uid id_orig_h id_orig_p method trans_depth status_code

송신 호스트와 캡처 시각으로 POST를 비교합니다. 외부 HTTP 연결마다 별도 UID가 있습니다. uid와 trans_depth로 각 요청에 해당하는 결과를 연결합니다. 선택한 목적지와 포트 범위에서 처음 관찰된 POST를 기록합니다.

21:51:55.392–21:51:55.393 7464, 7465, 7466, 7470 DC의 C$에서 두 번째 .exe 객체 열기와 선택한 쓰기에 성공 응답

성공 응답은 DC로의 쓰기 전송을 뒷받침합니다. 승인된 소프트웨어 배포도 관리 공유에 실행 파일을 쓸 수 있고, 외부 POST는 별도 프로세스에서 발생했을 수 있습니다. 역방향 SYN은 연결 시도를 보여 줍니다. 실행 여부, 파일 정체, 두 호스트 동작의 인과관계는 엔드포인트 증거가 필요합니다.

3 · Cross-check in Arkime

Arkime 
tags == "<CASE>" && ip.src == 10.2.20.101 && ip.dst == 10.2.20.2 && port.src == 49502 && port.dst == 445

Open the SMB session and follow both C$ file handles and their write replies. Record UTC time and tuple along with original frame references because export can renumber frames.

Arkime 
tags == "<CASE>" && ip.dst == 190.146.112.216 && port.dst == 8082 && (ip.src == 10.2.20.2 || ip.src == 10.2.20.101)

Open the two HTTP sessions with client ports 49311 and 49587. Verify the originator, method and paired reply in each session. Use the request times to establish the sequence.

3 · Arkime에서 두 종류의 흐름 교차 확인하기

Arkime 
tags == "<CASE>" && ip.src == 10.2.20.101 && ip.dst == 10.2.20.2 && port.src == 49502 && port.dst == 445

SMB 세션에서 C$ 파일 핸들 두 개와 쓰기 응답을 따라갑니다. 내보내면 번호가 바뀔 수 있으므로 원본 프레임과 함께 UTC 시각 및 주소·포트를 남깁니다.

Arkime 
tags == "<CASE>" && ip.dst == 190.146.112.216 && port.dst == 8082 && (ip.src == 10.2.20.2 || ip.src == 10.2.20.101)

클라이언트 포트 49311, 49587로 HTTP 세션을 찾습니다. 세션마다 송신자, 메서드, 대응 응답을 확인하고 요청 시각으로 순서를 정합니다.

4 · Check the POST and status pairs offline if needed

TShark 
tshark -2 -n -r "2019-02-20-Emotet-with-IcedID-and-Trickbot.pcap" -d tcp.port==8082,http \
  -Y 'frame.number == 11059 || frame.number == 11065 || frame.number == 21240 || frame.number == 21245' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e tcp.stream \
  -e ip.src -e ip.dst -e http.request.method -e http.response.code

If the Arkime view cannot distinguish the paired HTTP replies on TCP/8082, inspect four frames in the original capture. Match each POST and HTTP 200 by stream and check the source IP to distinguish the hosts.

4 · 필요할 때만 POST와 응답을 오프라인으로 확인하기

TShark 
tshark -2 -n -r "2019-02-20-Emotet-with-IcedID-and-Trickbot.pcap" -d tcp.port==8082,http \
  -Y 'frame.number == 11059 || frame.number == 11065 || frame.number == 21240 || frame.number == 21245' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e tcp.stream \
  -e ip.src -e ip.dst -e http.request.method -e http.response.code

Arkime에서 TCP/8082의 HTTP 응답을 구분하기 어렵다면 원본 네 프레임을 확인합니다. 스트림으로 POST와 HTTP 200을 연결하고 송신 IP로 두 호스트를 구분합니다.

5 · Record the write direction and validate execution separately

Include the PCAP hash, host roles, timestamps, C$ write outcomes and both HTTP tuples in the SOC ticket. Compare DC file, service and process-network telemetry with the SMB and POST sequence. Review planned software deployment and check for endpoint evidence of activity on the workstation.
