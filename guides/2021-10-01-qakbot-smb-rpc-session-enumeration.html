Which hosts received the session enumeration requests?

The original report describes a Qakbot infection with spambot activity. The same capture contains a separate internal sequence. Workstation 10.9.99.134 connects to IPC$ on the DC and two workstations and sends a Server Service RPC request consistent with session enumeration to each. Check the RPC operation, SMB transport result and actual IP peer separately.

어느 호스트가 세션 열거 요청을 받았는가?

공개 원문은 스팸봇 활동을 동반한 Qakbot 감염을 설명합니다. 같은 캡처에는 별도의 내부 통신도 있습니다. 워크스테이션 10.9.99.134가 DC와 워크스테이션 두 대의 IPC$에 연결해 각각 세션 열거에 해당하는 Server Service RPC 요청을 보냅니다. RPC 작업, SMB 전송 결과, 실제 상대 IP를 각각 확인합니다.

악성코드 분류는 공개 원문에 근거합니다. 아래 주소·포트, SMB 상태, 작업 번호는 원본 PCAP에서 확인했습니다. SPL은 자신의 Zeek 수집 환경에서 검증할 예시입니다.

1 · Baseline the client’s SMB connections by responder

Set <CASE> to the capture tag. Include the full UTC capture interval, and include the import interval if Splunk filters on ingest time. Use numeric Zeek ts for capture-time sorting. These searches assume flattened fields.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

Check for connection, SMB and DCE/RPC sourcetypes. Import settings and analyzer coverage can affect the number of available RPC rows.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp id_orig_h=10.9.99.134 id_resp_p=445
| eval minute=floor(ts/60)*60
| stats dc(uid) as connections sum(orig_pkts) as client_packets sum(resp_pkts) as peer_packets
    values(conn_state) as states by minute id_resp_h
| sort 0 minute id_resp_h

Compare the DC with the two peers near 13:56 UTC. Across the capture, the original TCP/445 flows from .134 contain 545 bilateral packets for .9 and 125 each for .135 and .133. The packet totals include control packets. Use connection counts to find sessions for the protocol pivot.

1 · 응답자별 SMB 접속 기준선 만들기

<CASE>에 캡처 태그를 넣습니다. 전체 UTC 캡처 구간을 포함하고 Splunk가 수집 시각으로 필터링하면 가져온 구간도 포함합니다. 캡처 시각에는 숫자형 Zeek ts를 사용합니다. 예시는 평탄화된 필드명을 사용합니다.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

연결, SMB, DCE/RPC 로그가 있는지 확인합니다. 가져오기 설정과 분석기의 처리 범위에 따라 RPC 기록 수가 달라질 수 있습니다.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp id_orig_h=10.9.99.134 id_resp_p=445
| eval minute=floor(ts/60)*60
| stats dc(uid) as connections sum(orig_pkts) as client_packets sum(resp_pkts) as peer_packets
    values(conn_state) as states by minute id_resp_h
| sort 0 minute id_resp_h

13:56 UTC 전후의 DC와 두 피어를 비교합니다. 캡처 전체에서 .134가 시작한 TCP/445 흐름은 .9와 양방향 545패킷, .135 및 .133과 각각 125패킷입니다. 패킷 수에는 전송 제어 패킷도 포함됩니다. 연결 수를 참고해 어떤 세션의 프로토콜을 확인할지 정합니다.

2 · Identify the repeated Server Service operation

SPL 
index=zeek sourcetype=zeek:dce_rpc pcap_case="<CASE>" id_orig_h=10.9.99.134 id_resp_p=445
    id_orig_p IN (56003,56005,56008)
| eval pipe=coalesce(named_pipe,"unknown"), rpc_endpoint=coalesce(endpoint,"unknown"),
    rpc_operation=coalesce(operation,"unknown")
| stats count as rpc_rows min(ts) as first max(ts) as last
    by uid id_resp_h id_orig_p pipe rpc_endpoint rpc_operation
| sort 0 first

Focus on srvsvc on client ports 56003, 56005 and 56008. The packet parser identified interface operation number 12, which Microsoft documents as NetrSessionEnum. Where available, compare Zeek’s endpoint and operation with the packet evidence. Use the TCP peer address to scope the incident, since a later SMB Tree Connect names a different address in its UNC path.

SPL 
index=zeek pcap_case="<CASE>" uid="<SELECTED_UID>"
    sourcetype IN ("zeek:conn","zeek:smb_mapping","zeek:smb_files","zeek:dce_rpc")
| sort 0 ts
| table ts sourcetype uid id_resp_h id_orig_p path share_type name action endpoint operation

Run this lookup separately for each selected TCP UID within the same Zeek processing run. The UID connects conn, SMB and RPC records for one session. Use the SMB message ID to pair each IOCTL request and SMB reply. DCE/RPC call identifiers can repeat across sessions, so keep each TCP stream’s RPC requests and replies separate.

UTC · 1 October 2021 Original frames Directly observed
13:56:00.653 19801, 19802 srvsvc opnum 12 to 10.9.99.135:445 from port 56003. SMB IOCTL response reports success.
13:56:01.287–13:56:01.288 19848, 19849 Same operation to the DC 10.9.99.9:445 from port 56005, with SMB IOCTL success
13:56:01.408 20075, 20076 Same operation to 10.9.99.133:445 from port 56008, with SMB IOCTL success
14:06:45.475–14:06:45.476 26506, 26507 Successful IPC$ tree connection with 10.9.27.135 in the path and 10.9.99.135 as the IP peer
14:51:24.583 32906, 32907 Later SMB2 SYSVOL read of gpt.ini from the DC returns 22 bytes

The near-simultaneous calls to three peers support an automated discovery hypothesis. Legitimate inventory or administration could also query sessions. An SMB success response confirms the transport result. The reviewed metadata leaves the RPC return status, number of sessions disclosed, and relationship to the spambot activity unresolved.

2 · 반복된 Server Service 작업 식별하기

SPL 
index=zeek sourcetype=zeek:dce_rpc pcap_case="<CASE>" id_orig_h=10.9.99.134 id_resp_p=445
    id_orig_p IN (56003,56005,56008)
| eval pipe=coalesce(named_pipe,"unknown"), rpc_endpoint=coalesce(endpoint,"unknown"),
    rpc_operation=coalesce(operation,"unknown")
| stats count as rpc_rows min(ts) as first max(ts) as last
    by uid id_resp_h id_orig_p pipe rpc_endpoint rpc_operation
| sort 0 first

클라이언트 포트 56003, 56005, 56008의 srvsvc를 봅니다. 원본 패킷에서 확인한 작업 번호는 12이며 Microsoft 명세의 NetrSessionEnum에 해당합니다. Zeek에 기록됐다면 엔드포인트와 작업 이름을 패킷 근거와 비교합니다. 이후 SMB Tree Connect의 UNC 경로에는 다른 주소가 나타나므로 조사 범위는 실제 TCP 상대 주소를 기준으로 잡습니다.

SPL 
index=zeek pcap_case="<CASE>" uid="<SELECTED_UID>"
    sourcetype IN ("zeek:conn","zeek:smb_mapping","zeek:smb_files","zeek:dce_rpc")
| sort 0 ts
| table ts sourcetype uid id_resp_h id_orig_p path share_type name action endpoint operation

선택한 연결마다 동일한 Zeek 처리 실행의 UID를 하나씩 넣습니다. UID로 한 연결의 conn, SMB, RPC 로그를 연결합니다. SMB 메시지 ID로 각 IOCTL 요청과 SMB 응답을 맞춥니다. DCE/RPC 호출 ID는 다른 세션에서 반복될 수 있으므로 스트림마다 요청과 응답을 구분합니다.

13:56:00.653 19801, 19802 포트 56003에서 10.9.99.135:445로 srvsvc opnum 12를 보내고 SMB IOCTL 성공 응답 수신
13:56:01.287–13:56:01.288 19848, 19849 포트 56005에서 DC 10.9.99.9:445에 같은 작업을 보내고 SMB IOCTL 성공 응답 수신
13:56:01.408 20075, 20076 포트 56008에서 10.9.99.133:445에 같은 작업을 보내고 SMB IOCTL 성공 응답 수신
14:06:45.475–14:06:45.476 26506, 26507 IPC$ 트리 연결 성공. UNC 경로에는 10.9.27.135, 실제 IP 상대는 10.9.99.135
14:51:24.583 32906, 32907 이후 DC의 SYSVOL에서 SMB2로 gpt.ini를 읽고 22바이트 반환

세 피어에 거의 동시에 호출한 패턴은 자동화된 탐색과 부합합니다. 정상적인 인벤토리 또는 관리 도구도 세션을 조회할 수 있습니다. SMB 성공 응답은 전송 결과를 보여 줍니다. RPC 자체의 반환 상태, 제공된 세션 수와 스팸봇 활동과의 관계는 확인이 필요합니다.

3 · Cross-check the same operation across peers in Arkime

Arkime 
tags == "<CASE>" && ip.src == 10.9.99.134 && ip.dst == 10.9.99.135 && port.src == 56003 && port.dst == 445

Check the IPC$ tree, srvsvc pipe open, and the IOCTL request and response on the first peer. Record its tuple and UTC timestamp because session exports can renumber packets.

Arkime 
tags == "<CASE>" && ip.src == 10.9.99.134 && port.dst == 445 && ((ip.dst == 10.9.99.9 && port.src == 56005) || (ip.dst == 10.9.99.133 && port.src == 56008))

Repeat for the DC and the second peer. Compare which IP receives each request and check the separate response. For the later Tree Connect discrepancy, use the IP header and record the path string as a separate value.

3 · Arkime에서 피어별로 같은 작업인지 교차 확인하기

Arkime 
tags == "<CASE>" && ip.src == 10.9.99.134 && ip.dst == 10.9.99.135 && port.src == 56003 && port.dst == 445

첫 피어의 IPC$ 트리, srvsvc 파이프 열기, IOCTL 요청과 응답을 확인합니다. 내보낸 프레임 번호가 바뀔 수 있으므로 주소·포트와 UTC 시각도 남깁니다.

Arkime 
tags == "<CASE>" && ip.src == 10.9.99.134 && port.dst == 445 && ((ip.dst == 10.9.99.9 && port.src == 56005) || (ip.dst == 10.9.99.133 && port.src == 56008))

DC와 두 번째 피어도 같은 방식으로 확인합니다. 각 요청을 받은 IP와 그에 대응하는 응답을 찾습니다. 이후 Tree Connect의 주소 차이는 IP 헤더와 경로 문자열을 별도로 기록합니다.

4 · Check two opnums offline if needed

TShark 
tshark -2 -n -r "2021-10-01-TR-Qakbot-infection-wtih-spambot-acitvity.pcap" \
  -Y 'frame.number == 19801 || frame.number == 19802 || frame.number == 20075 || frame.number == 20076' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e tcp.stream -e ip.src -e ip.dst \
  -e smb2.msg_id -e smb2.nt_status -e dcerpc.cn_call_id -e dcerpc.opnum

If Arkime does not expose the RPC fields, inspect the four original frames for the two workstations. Check opnum on each request and the outer SMB status on the reply. Compare message IDs within each TCP stream. This command returns selected headers and identifiers.

4 · 필요할 때만 두 RPC 작업 번호를 오프라인으로 확인하기

TShark 
tshark -2 -n -r "2021-10-01-TR-Qakbot-infection-wtih-spambot-acitvity.pcap" \
  -Y 'frame.number == 19801 || frame.number == 19802 || frame.number == 20075 || frame.number == 20076' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e tcp.stream -e ip.src -e ip.dst \
  -e smb2.msg_id -e smb2.nt_status -e dcerpc.cn_call_id -e dcerpc.opnum

Arkime에서 RPC 필드가 보이지 않으면 두 워크스테이션에 해당하는 원본 네 프레임을 확인합니다. 요청의 opnum과 응답의 SMB 상태를 확인합니다. TCP 스트림 안에서 메시지 ID를 비교합니다. 출력은 선택한 헤더와 식별자로 제한합니다.

5 · Record the affected peers and validate the discovery hypothesis

Put the capture hash, source host, three peers, operation name, UTC times and evidence references in the SOC ticket. Check the endpoint process that opened the SMB connections and verify DC and workstation share-audit records. Compare authorized discovery activity and seek corroboration before expanding scope to other hosts or declaring lateral compromise.

5 · SOC 티켓에 피어를 기록하고 탐색 가설 확인하기

캡처 해시, 송신 호스트, 피어 세 곳, 작업 이름, UTC 시각과 근거 프레임을 기록합니다. SMB 연결을 연 엔드포인트 프로세스를 확인하고, DC와 워크스테이션의 공유 감사 로그를 대조합니다. 승인된 탐색 활동을 확인하고, 다른 호스트까지 조사 범위를 넓히거나 횡적 침해를 확정하기 전에 별도 근거를 확보합니다.
