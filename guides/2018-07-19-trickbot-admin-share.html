Which share received the files?

The 19 July source post identifies Trickbot moving from an infected client to a domain controller (DC). In the original capture, 172.16.5.237 started an SMB1 connection to 172.16.5.5. On that connection, two successful file-write exchanges belong to the DC's C$ administrative disk share. A nearby service-control pipe exchange belongs to IPC$. The share names and successful replies come from the packet data. The malware family and host roles come from the publisher.

어느 공유에 파일을 썼나

7월 19일자 원문은 감염된 클라이언트에서 도메인 컨트롤러(DC)로 Trickbot이 확산된 사례를 소개합니다. 원본 PCAP에서 172.16.5.237이 172.16.5.5로 SMB1 연결을 시작했습니다. 이 연결에서 성공 응답을 받은 파일 쓰기 두 건은 DC의 C$ 관리 디스크 공유에 속합니다. 인접한 서비스 제어 파이프 통신은 IPC$에서 발생했습니다. 공유 이름과 성공 응답은 패킷을 직접 확인했고, 악성코드 계열과 호스트 역할은 공개 원문에 근거합니다.

1 · Baseline the client’s TCP/445 connections in Splunk

Use the UTC capture range in your time picker and replace <CASE> with the value assigned during ingest. If the picker uses ingest time, set it to cover ingestion and use numeric Zeek ts for packet-era timing. Adjust the flattened fields to match the import.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

Check which sourcetypes are available. Without zeek:smb_mapping or zeek:smb_files, use packet evidence to validate share and file activity.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp id_resp_p=445 id_orig_h=172.16.5.237
| stats count as connections dc(id_orig_p) as source_ports sum(orig_pkts) as sent_packets
        sum(resp_pkts) as reply_packets values(conn_state) as states by id_orig_h id_resp_h
| sort 0 - connections

Compare destination counts, distinct client ports, connection state, and the two packet directions. The PCAP has 1,330 bilateral packets for workstation-initiated TCP/445 toward the DC, including ACKs and control traffic. It also shows low-volume attempts to 172.16.5.1 and 172.16.5.254. Use destination and port to focus on the DC exchange. A Zeek connection count has a different unit from a raw packet count.

1단계 · Splunk에서 클라이언트의 TCP/445 베이스라인 확인

시간 선택기를 UTC 캡처 구간에 맞추고 <CASE>를 가져올 때 지정한 케이스 값으로 바꿉니다. 시간 선택기가 수집 시각을 기준으로 한다면 해당 수집 시간을 포함하고, 사건 타임라인에는 숫자형 Zeek ts를 사용합니다. 평탄화된 필드 이름은 실제 수집 환경에 맞춥니다.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

어떤 sourcetype이 들어왔는지 확인합니다. zeek:smb_mapping 또는 zeek:smb_files가 없다면 패킷 근거로 공유 및 파일 작업을 확인합니다.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp id_resp_p=445 id_orig_h=172.16.5.237
| stats count as connections dc(id_orig_p) as source_ports sum(orig_pkts) as sent_packets
        sum(resp_pkts) as reply_packets values(conn_state) as states by id_orig_h id_resp_h
| sort 0 - connections

목적지별 연결 수, 출발지 포트 수, 연결 상태와 양방향 패킷 수를 비교합니다. 원본 PCAP에서 워크스테이션이 시작한 DC 방향 TCP/445 흐름에는 ACK와 제어 패킷을 포함한 양방향 패킷 1,330개가 있었습니다. 172.16.5.1과 172.16.5.254를 향한 소량의 연결 시도도 보입니다. 목적지와 출발지 포트로 DC 연결을 좁힙니다. Zeek의 연결 수와 원본 패킷 수는 단위가 다릅니다.

2 · Map the writes to their shares

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" id_orig_h=172.16.5.237 id_resp_h=172.16.5.5 id_resp_p=445 id_orig_p=49280
| table ts uid id_orig_h id_orig_p id_resp_h id_resp_p duration conn_state missed_bytes

Copy the connection UID and constrain the next search to the same Zeek processing run. If the capture was imported more than once, select one run first.

SPL 
index=zeek pcap_case="<CASE>" uid="<SMB_UID>"
    sourcetype IN ("zeek:conn","zeek:smb_mapping","zeek:smb_files","zeek:dce_rpc","zeek:ntlm")
| sort 0 ts
| eval log_time=strftime(ts,"%Y-%m-%d %H:%M:%S.%3N %Z")
| table log_time sourcetype uid path name action endpoint operation

Check path on share records, and name and action on file records. The UID scopes these events to the TCP connection. Several shares can have the same UID, so match the share path and inspect SMB tree IDs in the original packets before assigning a file to a share.

The file names are abbreviated. The two executable names use different tree IDs for the same disk share. The pipe write belongs to another share on the same TCP connection. A pipe-write success shows the server accepted the data for that operation. Service creation and execution require endpoint evidence.

2단계 · 쓰기 작업을 공유 경로에 연결

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" id_orig_h=172.16.5.237 id_resp_h=172.16.5.5 id_resp_p=445 id_orig_p=49280
| table ts uid id_orig_h id_orig_p id_resp_h id_resp_p duration conn_state missed_bytes

연결 UID를 가져오고 이후 검색은 같은 Zeek 처리 실행으로 제한합니다. 여러 번 가져온 케이스는 먼저 한 처리 실행만 선택합니다.

SPL 
index=zeek pcap_case="<CASE>" uid="<SMB_UID>"
    sourcetype IN ("zeek:conn","zeek:smb_mapping","zeek:smb_files","zeek:dce_rpc","zeek:ntlm")
| sort 0 ts
| eval log_time=strftime(ts,"%Y-%m-%d %H:%M:%S.%3N %Z")
| table log_time sourcetype uid path name action endpoint operation

공유 기록의 path와 파일 기록의 name·action을 확인합니다. UID는 조사 범위를 해당 TCP 연결로 좁혀 줍니다. 한 UID에서 여러 공유가 사용될 수 있으므로 파일이 어느 공유에 속하는지는 공유 경로와 원본 패킷의 SMB 트리 ID를 대조해 판단합니다.

23:33:35.955–23:33:35.963 7270, 7271, 7272, 7274, 7278 트리 ID 2050으로 C$ 연결에 성공한 뒤 \WINDOWS\hjdogr14…exe 열기와 쓰기 성공 응답
23:33:36.010–23:33:36.017 7793, 7794, 7795, 7797, 7801 트리 ID 2051의 별도 C$ 연결과 \WINDOWS\chz14um6…exe 쓰기 성공 응답
23:33:36.042–23:33:36.048 7943, 7944, 7947, 7948 트리 ID 2052로 IPC$ 연결에 성공한 뒤 서비스 제어 파이프에 쓰기 성공

파일 이름은 줄여 표시했습니다. 두 실행 파일 이름은 같은 디스크 공유에서 서로 다른 트리 ID를 사용했습니다. 파이프 쓰기는 같은 TCP 연결의 별도 공유에 속합니다. 파이프 쓰기 성공 응답은 서버가 해당 데이터를 수락했다는 근거입니다. 서비스 생성과 실행은 엔드포인트에서 확인합니다.

3 · Cross-check tree and write responses in Arkime

Arkime 
tags == "<CASE>" && ip.src == 172.16.5.237 && ip.dst == 172.16.5.5 && port.src == 49280 && port.dst == 445

Use the case tag applied during import and open the TCP session around 23:33:36 UTC. In the packet view, start with the share request and reply. Use the assigned tree ID to follow the relevant file open and write. Check that the paired write response comes from the DC. Align by tuple and packet timestamp if you are looking at an exported subset.

3단계 · Arkime에서 공유 연결과 쓰기 응답 확인

Arkime 
tags == "<CASE>" && ip.src == 172.16.5.237 && ip.dst == 172.16.5.5 && port.src == 49280 && port.dst == 445

가져올 때 지정한 태그를 사용해 23:33:36 UTC 전후의 TCP 세션을 엽니다. 패킷 화면에서 공유 연결 요청과 응답을 찾고, 할당된 트리 ID로 파일 열기와 쓰기를 추적합니다. 해당 쓰기의 응답이 DC에서 왔는지 확인합니다. 일부 패킷만 내보냈다면 연결의 주소·포트와 시각으로 원본에 대조합니다.

4 · Read share and write IDs offline if needed

TShark 
tshark -n -r "2018-07-19-Trickbot-infection-moves-from-client-to-DC.pcap" \
  -Y 'ip.addr == 172.16.5.237 && ip.addr == 172.16.5.5 && tcp.port == 49280 && tcp.port == 445 && (smb.cmd == 0x75 || smb.cmd == 0x2f)' \
  -T fields -E header=y -e frame.number -e ip.src -e tcp.stream -e smb.cmd \
  -e smb.mid -e smb.tid -e smb.path -e smb.nt_status

Use this filter if the packet view leaves the tree ID or response status unclear. It returns only metadata from SMB1 tree connects and writes on the selected connection. Use TCP stream, direction and multiplex ID to pair each request and response. Use the tree ID assigned in the share response to locate the corresponding writes. Read SMB status on the response.

4단계 · 필요한 경우 오프라인에서 공유와 쓰기의 ID 확인

TShark 
tshark -n -r "2018-07-19-Trickbot-infection-moves-from-client-to-DC.pcap" \
  -Y 'ip.addr == 172.16.5.237 && ip.addr == 172.16.5.5 && tcp.port == 49280 && tcp.port == 445 && (smb.cmd == 0x75 || smb.cmd == 0x2f)' \
  -T fields -E header=y -e frame.number -e ip.src -e tcp.stream -e smb.cmd \
  -e smb.mid -e smb.tid -e smb.path -e smb.nt_status

패킷 화면에서 트리 ID나 응답 상태가 불분명할 때 선택한 연결의 SMB1 공유 연결과 쓰기 메타데이터만 조회합니다. TCP 스트림, 방향, multiplex ID로 각 요청과 응답을 짝짓습니다. 공유 연결 응답에서 할당된 트리 ID로 해당 쓰기를 찾아 응답의 SMB 상태를 읽습니다.

5 · Write the SOC ticket and verify host impact

Record the PCAP hash, client and DC IPs, client port, the two C$ tree IDs and write frames, and the separate IPC$ observation. Administrative shares and service-control pipes have legitimate uses. Check the source host and authenticated identity against approved deployment or maintenance activity. Request DC file-creation, process and service events around 23:33:36 UTC and document any gaps in endpoint coverage.
