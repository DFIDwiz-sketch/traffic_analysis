Which host made the external request after the SMB burst?

The publisher describes an Emotet and Trickbot infection in which Trickbot spreads from a Windows workstation to the domain controller (DC). In the original capture, the workstation 10.9.25.102 opens an SMB1 session to the DC 10.9.25.9. Within the same second, the DC sends its own HTTP GET to an external server. Reconstruct the direction of both flows before attributing the external traffic.

SMB 활동 직후 어느 호스트가 외부 요청을 보냈는가?

공개 원문은 Emotet 감염에 이어 Trickbot이 Windows 워크스테이션에서 도메인 컨트롤러(DC)로 퍼진 사례를 설명합니다. 원본에서 워크스테이션 10.9.25.102가 DC 10.9.25.9에 SMB1 연결을 엽니다. 같은 초에 DC도 외부 서버로 자체 HTTP GET을 보냅니다. 외부 트래픽의 송신 주체를 판단하기 위해 두 흐름의 방향을 재구성합니다.

Emotet와 Trickbot 분류는 원문에 근거합니다. 아래 주소 쌍, 패킷 시각, HTTP 응답 헤더는 원본에서 확인했습니다. SPL은 자신의 Zeek 수집 환경에서 검증할 예시입니다.

1 · Baseline both internal hosts and keep their roles visible

Set <CASE> to the capture tag and cover the full UTC window. If the time picker uses ingest time, include that interval and use Zeek ts to order capture events. The examples use flattened field names.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

Check which connection, SMB and HTTP logs are available. Capture boundaries and parser coverage can affect the application logs.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp
    id_orig_h IN ("10.9.25.102","10.9.25.9")
| eval second=floor(ts)
| stats dc(uid) as connections sum(orig_bytes) as orig_payload
    sum(resp_bytes) as resp_payload values(conn_state) as states by second id_orig_h id_resp_h id_resp_p
| sort 0 second

Look at which host originates each connection and which one responds. Compare the earlier TCP/445 activity to the burst around 21:57:11 UTC. For the workstation-to-DC traffic there are 651 TCP/445 packets across both directions and 28 outbound SYN frames over the capture. SYN frames can include retransmissions. The SPL counts Zeek connection UIDs instead.

1 · 두 내부 호스트의 연결을 시작 방향별로 비교하기

<CASE>에 캡처 태그를 넣고 UTC로 전체 캡처 구간을 선택합니다. 시간 선택기가 수집 시각을 쓰면 해당 구간을 포함한 뒤 Zeek ts로 캡처 이벤트 순서를 정합니다. 예시는 평탄화된 필드명을 사용합니다.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

연결, SMB, HTTP 로그의 수집 범위를 확인합니다. 캡처 시작·종료 시점과 파서의 처리 범위에 따라 애플리케이션 기록이 달라질 수 있습니다.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp
    id_orig_h IN ("10.9.25.102","10.9.25.9")
| eval second=floor(ts)
| stats dc(uid) as connections sum(orig_bytes) as orig_payload
    sum(resp_bytes) as resp_payload values(conn_state) as states by second id_orig_h id_resp_h id_resp_p
| sort 0 second

어느 호스트가 연결을 시작했고 누가 응답했는지 확인합니다. 앞선 TCP/445 활동과 21:57:11 UTC 전후를 비교합니다. 캡처 전체에서 워크스테이션이 시작한 DC 방향 TCP/445 흐름에는 양방향 패킷 651개와 송신 SYN 프레임 28개가 있습니다. SYN에는 재전송이 포함될 수 있습니다. SPL은 Zeek 연결 UID를 집계합니다.

2 · Track the SMB and HTTP sessions independently

SPL 
index=zeek pcap_case="<CASE>" id_orig_h=10.9.25.102 id_resp_h=10.9.25.9 id_resp_p=445
    id_orig_p IN (49204,49300) sourcetype IN ("zeek:conn","zeek:smb_mapping","zeek:smb_files")
| sort 0 ts
| table ts sourcetype uid id_orig_p service path name action

Compare the earlier client port 49204 with port 49300 at 21:57:11. Within each TCP connection, correlate Zeek records by uid from the same Zeek processing run. Treat sparse or absent SMB log rows as a reason to check the packets for that session. The packet-level SMB baseline uses the known policy read as a comparison.

SPL 
index=zeek sourcetype=zeek:http pcap_case="<CASE>" id_resp_h=185.98.87.185 id_resp_p=80
    id_orig_h IN ("10.9.25.102","10.9.25.9") method=GET
| eval png_suffix=if(match(uri,"[.]png([?]|$)"),"yes","no")
| sort 0 ts
| table ts uid id_orig_h id_orig_p trans_depth method png_suffix status_code response_body_len

Compare the HTTP rows for the DC and workstation. Each outward TCP connection has its own UID. Compare times and originating addresses across flows. Associate an HTTP response with its own connection and transaction, using uid and trans_depth in Zeek. The header length shown below is declared by the server and can differ from the bytes Zeek observed.

UTC · 25 September 2019 Original frames Directly observed
21:28:28.162 326, 327 Workstation reads gpt.ini over SMB2 from the DC. The read reply reports 22 bytes.
21:57:11.825–21:57:11.826 8369, 8370, 8374 Workstation port 49300 connects to DC TCP/445 and sends an SMB1 Session Setup request
21:57:12.084–21:57:12.317 8708, 8714 DC port 63887 sends a GET for a .png path to 185.98.87.185:80 and receives HTTP 200
21:57:12.106–21:57:12.353 8712, 8728 Workstation port 49344 also sends a GET for the same path and receives its own HTTP 200
22:09:44.229–22:09:44.471 14117, 14119 DC port 63994 makes a later GET for a .png path to the same server and receives HTTP 200

The two near-simultaneous replies advertise image/png and a Content-Length of 567,808 bytes. These headers describe what the server declared. The PCAP metadata reviewed here leaves file identity and execution unresolved. Independent fetches by a browser, an approved process or a test harness could generate similar HTTP timing. The publisher’s interpretation of the incident gives context for prioritizing DC follow-up.

2 · SMB와 HTTP 세션을 각각 추적하기

SPL 
index=zeek pcap_case="<CASE>" id_orig_h=10.9.25.102 id_resp_h=10.9.25.9 id_resp_p=445
    id_orig_p IN (49204,49300) sourcetype IN ("zeek:conn","zeek:smb_mapping","zeek:smb_files")
| sort 0 ts
| table ts sourcetype uid id_orig_p service path name action

앞선 클라이언트 포트 49204 세션과 21:57:11의 포트 49300 세션을 비교합니다. TCP 연결 안에서는 동일한 Zeek 처리 실행의 uid로 로그를 연결합니다. SMB 기록이 드물거나 비어 있으면 해당 세션의 패킷을 확인합니다. 앞서 관찰한 정책 파일 읽기를 비교 기준으로 삼습니다.

SPL 
index=zeek sourcetype=zeek:http pcap_case="<CASE>" id_resp_h=185.98.87.185 id_resp_p=80
    id_orig_h IN ("10.9.25.102","10.9.25.9") method=GET
| eval png_suffix=if(match(uri,"[.]png([?]|$)"),"yes","no")
| sort 0 ts
| table ts uid id_orig_h id_orig_p trans_depth method png_suffix status_code response_body_len

DC와 워크스테이션의 HTTP 행을 비교합니다. 외부 TCP 연결에는 각각 별도 UID가 있습니다. 연결 간에는 시각과 송신 주소를 비교하고, Zeek에서는 uid와 trans_depth로 HTTP 응답을 해당 연결의 요청에 연결합니다. 아래 헤더 길이는 서버 선언값이며 Zeek가 관찰한 바이트 수와 다를 수 있습니다.

UTC · 2019년 9월 25일 원본 프레임 직접 관찰한 내용
21:28:28.162 326, 327 워크스테이션이 DC에서 SMB2로 gpt.ini를 읽음. 읽기 응답의 길이는 22바이트
21:57:11.825–21:57:11.826 8369, 8370, 8374 워크스테이션 포트 49300이 DC의 TCP/445에 연결해 SMB1 Session Setup 요청 전송
21:57:12.084–21:57:12.317 8708, 8714 DC 포트 63887이 185.98.87.185:80으로 .png 경로를 GET하고 HTTP 200 수신
21:57:12.106–21:57:12.353 8712, 8728 워크스테이션 포트 49344도 같은 경로를 GET하고 별도 HTTP 200 수신
22:09:44.229–22:09:44.471 14117, 14119 DC 포트 63994가 같은 서버의 .png 경로를 다시 GET하고 HTTP 200 수신

거의 동시에 받은 두 응답은 모두 image/png와 Content-Length 567,808바이트를 선언합니다. 이 헤더 값은 서버가 표시한 메타데이터입니다. 조사한 PCAP 메타데이터로는 파일의 실제 정체와 실행 여부를 확인할 수 없습니다. 브라우저, 승인된 프로세스, 실습 도구가 각각 요청을 보내도 비슷한 타이밍이 나타날 수 있습니다. 원문의 사건 해석은 DC 후속 조사의 우선순위를 정하는 데 참고할 수 있습니다.

3 · Cross-check direction and timing in Arkime

Arkime 
tags == "<CASE>" && ip.src == 10.9.25.102 && ip.dst == 10.9.25.9 && port.src == 49300 && port.dst == 445

Verify the client’s SYN, the DC’s reply and the SMB1 messages after the connection is established. Record the tuple and UTC timestamp. An exported view may renumber the packets.

Arkime 
tags == "<CASE>" && ip.dst == 185.98.87.185 && port.dst == 80 && (ip.src == 10.9.25.9 || ip.src == 10.9.25.102)

Open the two early HTTP sessions with client ports 63887 and 49344. Verify who sent each request line and find its server response in the reverse direction. Keep the later DC request separate from the initial pair.

3 · Arkime에서 방향과 시각 교차 확인하기

Arkime 
tags == "<CASE>" && ip.src == 10.9.25.102 && ip.dst == 10.9.25.9 && port.src == 49300 && port.dst == 445

클라이언트의 SYN, DC의 응답, 연결 성립 이후 SMB1 메시지를 확인합니다. 내보내면 프레임 번호가 바뀔 수 있으므로 전체 주소·포트와 UTC 시각을 남깁니다.

Arkime 
tags == "<CASE>" && ip.dst == 185.98.87.185 && port.dst == 80 && (ip.src == 10.9.25.9 || ip.src == 10.9.25.102)

앞선 HTTP 세션 두 개를 클라이언트 포트 63887과 49344로 찾습니다. 각 요청 줄을 누가 보냈는지 확인하고 반대 방향에서 해당 서버 응답을 찾습니다. 나중에 발생한 DC 요청은 처음 두 요청과 분리해 기록합니다.

4 · Compare the two HTTP pairs offline if needed

TShark 
tshark -2 -n -r "2019-09-25-Emotet-infection-with-Trickbot-in-AD-environment.pcap" \
  -Y 'frame.number == 8708 || frame.number == 8712 || frame.number == 8714 || frame.number == 8728' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e tcp.stream \
  -e ip.src -e ip.dst -e http.request.method -e http.response.code -e http.content_length_header

If the Arkime view makes it difficult to distinguish the two replies, request four original frames. Use ip.src on the requests and tcp.stream for the pairing. The output shows methods, status and declared size without copying the HTTP bodies.

4 · 필요할 때만 HTTP 요청과 응답 두 쌍을 오프라인에서 비교하기

TShark 
tshark -2 -n -r "2019-09-25-Emotet-infection-with-Trickbot-in-AD-environment.pcap" \
  -Y 'frame.number == 8708 || frame.number == 8712 || frame.number == 8714 || frame.number == 8728' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e tcp.stream \
  -e ip.src -e ip.dst -e http.request.method -e http.response.code -e http.content_length_header

Arkime 화면에서 응답 쌍을 구분하기 어려우면 원본의 네 프레임만 조회합니다. 요청의 ip.src로 송신자를 확인하고 tcp.stream으로 응답과 짝짓습니다. 출력은 메서드, 상태, 선언된 크기 등의 헤더 정보입니다.

5 · 송신 방향 변화와 DC의 활동을 SOC 티켓에 기록하기
