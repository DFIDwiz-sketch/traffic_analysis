What the capture shows

David Szili’s lab notes identify the Windows 7 host at 192.168.116.149 as the starting point for WannaCry and report subsequent propagation. A read-only pass over the original capture independently confirmed a burst of TCP/445 attempts from that host, followed by new TCP/445 initiators at 192.168.116.138 and 192.168.116.172. This is a useful scoping pattern for an analyst. The transport metadata by itself does not establish the compromise status of every destination.

한눈에 보는 결과

David Szili의 실습 기록은 Windows 7 호스트 192.168.116.149에서 WannaCry가 시작돼 다른 호스트로 전파됐다고 설명합니다. 원본 캡처를 읽기 전용으로 확인한 결과, 먼저 이 호스트에서 TCP/445 연결 시도가 집중됐고 이후 192.168.116.138과 192.168.116.172가 새 TCP/445 연결을 시작했습니다. 이 패턴은 조사 범위를 넓힐 단서입니다. 목적지별 감염 여부는 전송 계층 기록만으로 판단할 수 없습니다.

1 · Establish the capture baseline in Splunk

Set the display time to UTC and select a time range covering the historical capture. Replace <CASE> with the case tag supplied by your importer. The SPL uses the site’s flattened Zeek field names. It is supplied for execution in your lab. No Splunk or Arkime output counts are asserted below.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

Check for zeek:conn and note which SMB logs your import produced. min(ts) and max(ts) here describe each log’s event range. The independently observed first and last packet times above describe the entire file.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp id_resp_p=445
| where cidrmatch("192.168.116.0/24",id_orig_h) AND cidrmatch("192.168.116.0/24",id_resp_h)
| stats dc(id_resp_h) as unique_targets count as connections
        min(ts) as first values(conn_state) as states by id_orig_h
| sort - connections
| eval first=strftime(first,"%H:%M:%S.%3N %Z")

The first search limits the analysis to connections toward TCP/445. The CIDR checks limit both endpoints to the lab segment. dc(id_resp_h) counts different destinations, while count counts Zeek connection records. Compare the number of destinations and the start times together. A backup server or vulnerability scanner can also have many SMB targets.

1단계 · Splunk에서 캡처 범위 확인

표시 시간을 UTC로 맞추고 과거 캡처가 포함된 시간대를 선택합니다. <CASE>를 수집기가 붙인 케이스 태그로 바꾸세요. SPL은 사이트에서 쓰는 평탄화된 Zeek 필드명을 가정합니다. 아래 쿼리는 실습 환경에서 검증할 예제이며 Splunk와 Arkime의 실제 출력 건수는 측정하지 않았습니다.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

zeek:conn과 수집된 SMB 로그를 확인합니다. 여기서 min(ts)와 max(ts)는 로그 종류별 이벤트 범위입니다. 위의 첫·마지막 패킷 시각은 PCAP 전체를 기준으로 합니다.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp id_resp_p=445
| where cidrmatch("192.168.116.0/24",id_orig_h) AND cidrmatch("192.168.116.0/24",id_resp_h)
| stats dc(id_resp_h) as unique_targets count as connections
        min(ts) as first values(conn_state) as states by id_orig_h
| sort - connections
| eval first=strftime(first,"%H:%M:%S.%3N %Z")

먼저 목적지 TCP/445에 해당하는 연결을 선택합니다. CIDR 조건은 양 끝이 실습망인 경우만 남깁니다. dc(id_resp_h)는 서로 다른 목적지 수, count는 Zeek 연결 기록 수입니다. 목적지가 몇 곳인지와 언제 연결을 시작했는지를 함께 보세요. 백업 서버나 취약점 스캐너도 여러 SMB 목적지에 접속할 수 있습니다.

2 · Find the change in direction

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp id_resp_p=445
| where cidrmatch("192.168.116.0/24",id_orig_h) AND cidrmatch("192.168.116.0/24",id_resp_h)
| eval bucket=floor(ts/5)*5
| stats count as connections values(id_resp_h) as targets by bucket id_orig_h
| sort 0 bucket id_orig_h
| eval time_utc=strftime(bucket,"%H:%M:%S %Z")
| table time_utc id_orig_h connections targets

A five-second bin makes the burst visible. Read the output in chronological order and note when each workstation begins originating sessions. Expand the relevant window and retrieve an individual connection with uid, ts, both endpoints and both ports. Use that uid only to pivot to corresponding SMB records from the same Zeek processing run. A new outbound 445 connection has a new UID. Link it to the previous host by IP and time, preserving both connections as separate evidence.

2단계 · 연결 시작 방향이 바뀐 시각 찾기

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp id_resp_p=445
| where cidrmatch("192.168.116.0/24",id_orig_h) AND cidrmatch("192.168.116.0/24",id_resp_h)
| eval bucket=floor(ts/5)*5
| stats count as connections values(id_resp_h) as targets by bucket id_orig_h
| sort 0 bucket id_orig_h
| eval time_utc=strftime(bucket,"%H:%M:%S %Z")
| table time_utc id_orig_h connections targets

5초 단위로 묶으면 연결 시도의 집중 구간을 보기 쉽습니다. 어느 호스트가 언제부터 연결을 시작했는지 비교하세요. 구간을 좁힌 뒤 개별 연결의 uid, ts, 양쪽 IP와 포트를 확인합니다. uid는 같은 Zeek 처리 실행에서 생성된 해당 연결의 SMB 로그와 연결할 때만 사용합니다. 이후 다른 호스트가 시작한 TCP/445 연결에는 새로운 UID가 부여됩니다. 각각을 별도 근거로 기록하고 IP와 시각으로 흐름을 비교합니다.

3 · Cross-check sessions in Arkime

Arkime 
tags == "<CASE>" && port.dst == 445 &&
(ip.src == 192.168.116.149 || ip.src == 192.168.116.138 || ip.src == 192.168.116.172)

In Sessions, set the time picker to 08:12–08:15 UTC and select an individual pair. For .149 → .138, expand the session on client port 49367 and look for the SYN and reverse SYN/ACK. Next, check a later session originated by .138 or .172. An Arkime session count, a Zeek record count and a packet count have different units.

3단계 · Arkime으로 세션 교차 확인

Arkime 
tags == "<CASE>" && port.dst == 445 &&
(ip.src == 192.168.116.149 || ip.src == 192.168.116.138 || ip.src == 192.168.116.172)

Sessions에서 08:12–08:15 UTC로 좁힙니다. .149 → .138의 클라이언트 포트 49367 세션을 열어 SYN과 역방향 SYN/ACK를 확인합니다. 다음으로 .138 또는 .172가 새로 시작한 세션을 엽니다. Arkime 세션 수, Zeek 연결 기록 수, 패킷 수는 서로 집계 단위가 다릅니다.

4 · Verify the handshake offline if flags are unclear

TShark 
tshark -n -r "2017-05-18-WannaCry-ransomware-using-EnternalBlue-exploit.pcap" \
  -Y 'ip.addr == 192.168.116.149 && ip.addr == 192.168.116.138 && tcp.port == 49367 && tcp.port == 445 && tcp.flags.syn == 1' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e ip.src -e ip.dst -e tcp.flags

This narrow check prints TCP flags and frame times from the original PCAP. Use it when the Arkime session view makes packet direction unclear. Frame numbers may change after export. A reply shows that the destination answered the transport attempt. Check the final ACK separately before describing a completed handshake. Neither the SYN/ACK nor a blank SMB log establishes exploitation.

4단계 · 플래그가 불명확할 때 TShark로 확인

TShark 
tshark -n -r "2017-05-18-WannaCry-ransomware-using-EnternalBlue-exploit.pcap" \
  -Y 'ip.addr == 192.168.116.149 && ip.addr == 192.168.116.138 && tcp.port == 49367 && tcp.port == 445 && tcp.flags.syn == 1' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e ip.src -e ip.dst -e tcp.flags

Arkime에서 방향이나 플래그를 보기 어려울 때 원본의 TCP 플래그와 프레임 시각을 확인합니다. 내보낸 파일의 프레임 번호는 달라질 수 있습니다. SYN/ACK는 상대가 응답했다는 근거입니다. 핸드셰이크가 끝났다고 쓰려면 마지막 ACK까지 확인하세요. SYN/ACK만으로 취약점 악용을 입증할 수 없으며 SMB 로그가 비어 있다고 결론을 내릴 수도 없습니다.

5 · Write the SOC ticket

Record the initial source, follow-on sources, first times and capture hash. Treat the domain controller and file server as destinations requiring verification, and attribute any infection claims to the publisher or your endpoint evidence. Ask for endpoint process and file-change records plus approved scanner or backup windows. For a live incident, follow containment policy, check SMBv1 exposure and verify the applicable Windows security updates before restoring connectivity.

최초 출발지와 후속 출발지, 첫 관측 시각, 캡처 해시를 기록합니다. 도메인 컨트롤러와 파일 서버는 확인할 대상으로 두고, 감염 판정은 공개 원문의 보고 또는 별도로 확인한 엔드포인트 증거에 근거를 둡니다. 프로세스·파일 변경 기록과 승인된 스캐너 또는 백업 작업 시간을 요청하세요. 실제 사고라면 조직의 격리 절차를 따르고, 연결 복구 전에 SMBv1 노출과 관련 Windows 보안 업데이트 적용 여부를 확인합니다.
