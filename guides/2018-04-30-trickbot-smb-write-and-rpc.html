What happened in the capture

The publisher identifies the workstation at 10.4.30.101 and the domain controller (DC) at 10.4.30.5 in a Trickbot lab and reports an SMB transfer between them. The original PCAP independently shows successful SMB1 writes to two executable filenames on the same TCP stream, followed by traffic on a service-control named pipe. This guide uses that sequence to decide what to verify on the DC.

1 · Establish the workstation’s SMB baseline in Splunk

Replace <CASE> with the case value attached at import. Use UTC in your Splunk user settings and select the capture interval, extending the picker if Splunk indexed ingestion time as _time. The examples use numeric Zeek ts and flattened fields such as id_orig_h. Adjust the index and field names to match your ingestion.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

Use this inventory to confirm which sourcetypes are present and their event time ranges. A missing analyzer log or unparsed timestamp limits the findings you can draw from Splunk.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp id_resp_p=445 id_orig_h=10.4.30.101
| stats count as connections dc(id_orig_p) as client_ports sum(orig_bytes) as sent
        sum(resp_bytes) as received min(ts) as first values(conn_state) as states by id_orig_h id_resp_h
| sort - connections
| eval first=strftime(first,"%H:%M:%S.%3N %Z")

Compare destinations by distinct client ports, connection states and bytes. Inspect the DC row and expand it by client port. The PCAP contains 1,517 bidirectional packets for workstation-initiated TCP/445 toward the DC, including ACKs and control packets. That total measures packets. Use the result’s connection counts to compare Zeek sessions.

1단계 · Splunk에서 워크스테이션 SMB 베이스라인 확인

<CASE>를 가져오기 단계에서 지정한 케이스 값으로 바꿉니다. Splunk 사용자 설정에서 UTC를 선택하고 시간 범위를 캡처 구간에 맞춥니다. 수집 시간이 _time으로 저장됐다면 시간 범위를 넓혀야 할 수 있습니다. 예제는 숫자형 Zeek ts와 id_orig_h처럼 평탄화된 필드를 사용하므로 실제 인덱스와 필드에 맞춰 조정합니다.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

수집된 sourcetype과 이벤트 시간 범위를 먼저 확인합니다. 분석기 로그가 빠졌거나 시간이 파싱되지 않은 경우 Splunk에서 판단할 수 있는 범위가 줄어듭니다.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp id_resp_p=445 id_orig_h=10.4.30.101
| stats count as connections dc(id_orig_p) as client_ports sum(orig_bytes) as sent
        sum(resp_bytes) as received min(ts) as first values(conn_state) as states by id_orig_h id_resp_h
| sort - connections
| eval first=strftime(first,"%H:%M:%S.%3N %Z")

목적지별로 출발지 포트 수, 연결 상태, 송수신 바이트를 비교합니다. DC에 해당하는 행을 출발지 포트별로 다시 펼쳐 보세요. PCAP에서 워크스테이션이 시작한 DC 방향 TCP/445 흐름에는 ACK와 제어 패킷을 포함해 양방향 1,517개 패킷이 있었습니다. 이 값은 패킷 수입니다. Zeek 세션은 SPL 결과의 연결 수로 비교합니다.

2 · Separate completed file writes from named-pipe activity

SPL 
index=zeek pcap_case="<CASE>" id_orig_h=10.4.30.101 id_resp_h=10.4.30.5 id_orig_p=49453 id_resp_p=445
    sourcetype IN ("zeek:conn","zeek:smb_mapping","zeek:smb_files","zeek:dce_rpc","zeek:ntlm")
| sort 0 ts
| eval log_time=strftime(ts,"%Y-%m-%d %H:%M:%S.%3N %Z")
| table log_time sourcetype uid id_orig_p path name action endpoint operation conn_state

Read the connection row and take its uid into the SMB share, file or RPC records from the same Zeek processing run. If you imported the case twice, filter to one run before cross-referencing. Use action, path and name to identify the object, then read available endpoint and operation values for the RPC context. A file log can omit the packet-level reply. Check it in Arkime before marking a write as successful.

The following search takes the connection UID as <UID>. The output orders the available share, file and RPC records by Zeek event time.

SPL 
index=zeek pcap_case="<CASE>" uid="<UID>"
    sourcetype IN ("zeek:conn","zeek:smb_mapping","zeek:smb_files","zeek:dce_rpc","zeek:ntlm")
| sort 0 ts
| table ts sourcetype uid path name action endpoint operation

The table uses request timestamps and abbreviates the executable names. The write requests were matched to file or pipe handles and the corresponding SMB server replies. A success reply to a pipe write shows the SMB write was accepted. Assess the RPC operation and verify any service or process change on the endpoint separately. The publisher filtered out some background traffic, so this capture provides only a lab baseline.

2단계 · 성공한 파일 쓰기와 명명된 파이프 활동 구분

SPL 
index=zeek pcap_case="<CASE>" id_orig_h=10.4.30.101 id_resp_h=10.4.30.5 id_orig_p=49453 id_resp_p=445
    sourcetype IN ("zeek:conn","zeek:smb_mapping","zeek:smb_files","zeek:dce_rpc","zeek:ntlm")
| sort 0 ts
| eval log_time=strftime(ts,"%Y-%m-%d %H:%M:%S.%3N %Z")
| table log_time sourcetype uid id_orig_p path name action endpoint operation conn_state

연결 행의 uid를 기준으로 같은 Zeek 처리 실행의 SMB 공유·파일·RPC 기록을 찾습니다. 두 번 가져온 케이스라면 먼저 처리 실행 하나로 범위를 좁힙니다. action, path, name으로 작업 대상이 무엇인지 보고, RPC 맥락은 수집된 endpoint와 operation에서 확인합니다. 파일 로그에 패킷 수준 응답이 없을 수 있으므로, 성공 여부는 Arkime에서 확인합니다.

아래 검색의 <UID>에 연결 행의 값을 넣습니다. 조회된 공유·파일·RPC 기록은 Zeek 이벤트 시간순으로 확인합니다.

SPL 
index=zeek pcap_case="<CASE>" uid="<UID>"
    sourcetype IN ("zeek:conn","zeek:smb_mapping","zeek:smb_files","zeek:dce_rpc","zeek:ntlm")
| sort 0 ts
| table ts sourcetype uid path name action endpoint operation

표의 시간은 요청 시각이며 실행 파일 이름은 줄여 표시했습니다. 파일 또는 파이프 핸들로 쓰기 대상을 확인하고 SMB 서버의 응답을 짝지었습니다. 파이프의 성공 응답은 SMB 쓰기를 수락했다는 뜻입니다. RPC 작업의 의미와 실제 서비스 또는 프로세스 변경은 엔드포인트에서 별도로 확인합니다. 원문 작성자가 일부 배경 트래픽을 제거했으므로 이 캡처는 실습 범위의 베이스라인으로 사용합니다.

3 · Verify the request and reply in Arkime

Arkime 
tags == "<CASE>" && ip.src == 10.4.30.101 && ip.dst == 10.4.30.5 && port.src == 49453 && port.dst == 445

Filter to the tag applied at import and open the session around 21:31:09 UTC. In the packet pane compare client request and server reply for each write above. Use the TCP tuple and packet time to align with the original PCAP. Packet numbers in an exported subset may differ. Note which writes went to executable names and which went to named pipes.

3단계 · Arkime에서 요청과 응답 대조

Arkime 
tags == "<CASE>" && ip.src == 10.4.30.101 && ip.dst == 10.4.30.5 && port.src == 49453 && port.dst == 445

가져올 때 지정한 태그로 필터링하고 21:31:09 UTC 전후의 세션을 엽니다. 패킷 화면에서 표에 나온 쓰기의 클라이언트 요청과 서버 응답을 확인합니다. TCP 주소·포트 조합과 패킷 시각을 원본 PCAP과 대조합니다. 일부만 내보냈다면 프레임 번호가 달라질 수 있습니다. 실행 파일 이름이 있는 쓰기와 명명된 파이프의 쓰기를 구분해 기록합니다.

4 · Check the SMB reply code offline when needed

TShark 
tshark -n -r "2018-04-30-Trickbot-goes-from-client-to-domain-controller.pcap" \
  -Y 'ip.addr == 10.4.30.101 && ip.addr == 10.4.30.5 && tcp.port == 49453 && tcp.port == 445 && smb.cmd == 0x2f' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e ip.src -e ip.dst \
  -e tcp.stream -e smb.mid -e smb.nt_status

If Arkime leaves the status uncertain, this filter reads only the SMB1 Write AndX metadata on the verified TCP connection. Compare request and response within the same TCP stream by SMB multiplex ID and direction. Confirm the server's status for the exchange under review. Use the file-handle or original frame context to tie it back to the correct object.

4단계 · 필요한 경우 TShark로 SMB 응답 코드 확인

TShark 
tshark -n -r "2018-04-30-Trickbot-goes-from-client-to-domain-controller.pcap" \
  -Y 'ip.addr == 10.4.30.101 && ip.addr == 10.4.30.5 && tcp.port == 49453 && tcp.port == 445 && smb.cmd == 0x2f' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e ip.src -e ip.dst \
  -e tcp.stream -e smb.mid -e smb.nt_status

Arkime에서 상태를 판독하기 어렵다면 이 오프라인 필터로 확인된 TCP 연결의 SMB1 Write AndX 메타데이터만 읽습니다. 동일 TCP 스트림 내에서 SMB multiplex ID와 송수신 방향으로 요청과 응답을 짝짓고 서버의 응답 상태를 확인합니다. 파일 핸들이나 원본 프레임을 근거로 확인하려는 작업 대상과 연결합니다.

5 · Follow up on the DC

Record the two hosts, PCAP hash, successful write pairs, and adjacent pipe activity in the ticket. Assess whether the filenames, account, source host and timing fit an approved deployment or administrative change. Request DC file-creation and process evidence and correlate service-install events with the write window. If endpoint visibility is missing, record execution and service impact as unresolved and assign collection to the host owner.

5단계 · DC 후속 점검

호스트 두 대, PCAP 해시, 쓰기와 성공 응답의 프레임 쌍, 전후의 파이프 활동을 티켓에 남깁니다. 파일 이름, 계정, 출발지 호스트와 시간이 승인된 배포나 관리 변경과 일치하는지 확인합니다. DC의 파일 생성과 프로세스 증거를 요청하고 같은 시간대의 서비스 설치 이벤트를 대조합니다. 엔드포인트 기록이 없다면 실행 여부와 서비스 영향을 미확인으로 남기고 호스트 담당자에게 로그 수집을 요청합니다.
