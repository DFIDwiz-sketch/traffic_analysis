How much upload data is visible in the capture?

The publisher identifies the traffic as MacSync Stealer and says the archive in the public capture was modified to protect lab host information. The PCAP shows 10.12.23.101 making a GET and a later multipart HTTP POST with the same Host, on two different server IPs. The POST declares a 60,928-byte body. Captured client TCP bytes after the HTTP headers cover that length contiguously. The reply is HTTP 200.

캡처에서 업로드 데이터가 얼마나 확인되나

공개 원문은 MacSync Stealer 트래픽을 소개하며 실습 호스트 정보를 보호하려고 공개 캡처의 아카이브를 변경했다고 설명합니다. 원본 PCAP에서 10.12.23.101은 서로 다른 서버 IP에 같은 HTTP Host로 GET과 후속 멀티파트 POST를 보냈습니다. POST가 선언한 본문 길이는 60,928바이트입니다. HTTP 헤더 뒤의 클라이언트 TCP 바이트가 이 길이만큼 끊김 없이 캡처됐고, HTTP 200 응답이 돌아왔습니다.

1 · Establish the host baseline in Splunk

Replace <CASE> with the capture’s import label, use UTC, and cover the full capture. If _time is ingest time, adjust the picker and use numeric Zeek ts for PCAP-era ordering. The examples assume flattened fields. Map the Zeek HTTP Host to http_host to keep it separate from Splunk’s host metadata.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

Verify that connection, HTTP and TLS logs arrived. This short source capture provides a case baseline for its own time window.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" id_orig_h=10.12.23.101 proto=tcp
| eval service_label=coalesce(mvjoin(service,","),"unidentified")
| stats count as connections values(service_label) as services
        values(conn_state) as states sum(orig_bytes) as sender_bytes by id_resp_h id_resp_p
| sort 0 - sender_bytes

Compare server IPs, ports, analyzer services and client bytes. The PCAP shows four client-initiated TCP connections for the selected host. Two start TLS on port 443 and two carry HTTP on port 80. Zeek’s orig_bytes covers the connection’s payload. Use request_body_len or packet evidence for one HTTP body.

1단계 · Splunk에서 호스트 베이스라인 설정

<CASE>에 수집 때 붙인 값을 넣고 UTC로 표시합니다. 전체 캡처 구간을 포함합니다. _time이 수집 시각이면 범위를 조정하고 패킷의 사건 순서는 숫자형 Zeek ts로 읽습니다. 예제는 평탄화된 필드를 사용합니다. HTTP Host는 Splunk 호스트 메타데이터와 구분할 수 있도록 Zeek에서 http_host로 추출합니다.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

연결, HTTP, TLS 로그가 들어왔는지 확인합니다. 베이스라인은 짧은 원본 캡처 구간에 해당합니다.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" id_orig_h=10.12.23.101 proto=tcp
| eval service_label=coalesce(mvjoin(service,","),"unidentified")
| stats count as connections values(service_label) as services
        values(conn_state) as states sum(orig_bytes) as sender_bytes by id_resp_h id_resp_p
| sort 0 - sender_bytes

서버 IP, 포트, 분석기가 식별한 서비스와 클라이언트 바이트를 비교합니다. 원본에서는 해당 호스트가 시작한 TCP 연결 네 개가 확인됩니다. 두 개는 443에서 TLS를 시작했고, 두 개는 80에서 HTTP를 보냈습니다. Zeek orig_bytes는 연결 전체의 페이로드입니다. HTTP 본문 하나의 길이는 request_body_len이나 패킷 근거로 확인합니다.

2 · Match the Host across sessions and verify the upload

SPL 
index=zeek sourcetype=zeek:http pcap_case="<CASE>" id_orig_h=10.12.23.101
    id_resp_h IN ("172.67.145.157","104.21.87.188") id_resp_p=80 method IN ("GET","POST")
| sort 0 ts
| table ts uid id_orig_p id_resp_h method http_host status_code request_body_len

Review the HTTP method, Host, IP, client port and time. The two HTTP connections present the same Host, focusgroovy.com, despite different destination IPs. Check the Host on the original packets, especially if Zeek only captured one of the requests.

SPL 
index=zeek pcap_case="<CASE>" uid="<HTTP_UID>" sourcetype IN ("zeek:conn","zeek:http")
| sort 0 ts
| table ts sourcetype uid id_orig_p id_resp_h id_resp_p missed_bytes method status_code request_body_len

Use the POST UID for zeek:conn and zeek:http from the same Zeek processing run. Select one ingest when the file was imported more than once. The GET has its own UID. Relate requests across UIDs using the Host, workstation and timing.

The server’s retention, the original unmodified archive’s contents and local process ownership need independent evidence.

HTTP 메서드, Host, IP, 출발지 포트와 시각을 비교합니다. 두 요청은 목적지 IP가 달랐지만 Host는 focusgroovy.com으로 같았습니다. Zeek에서 요청 하나만 조회된다면 원본 패킷의 Host를 대조합니다.

SPL

| sort 0 ts
| table ts sourcetype uid id_orig_p id_resp_h id_resp_p missed_bytes method status_code request_body_len

POST UID를 같은 Zeek 처리 실행의 zeek:conn과 zeek:http에서 사용합니다. 캡처를 여러 번 가져왔다면 한 실행으로 제한합니다. GET에는 별도 UID가 있으므로 두 요청은 Host, 워크스테이션과 시각으로 대조합니다.

4 · Verify declared length and status offline if needed

TShark 
tshark -n -r "2025-12-23-MacSync-Stealer-traffic.pcap" \
  -Y 'frame.number == 104 || frame.number == 171 || frame.number == 189' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e tcp.stream -e ip.src \
  -e http.request.method -e http.content_length -e http.response.code

If the view leaves the header fields unclear, read the original request start, final client data frame and response header. Compare the method, declared length and status in the same TCP stream. Depending on reassembly, TShark may report the request fields on the later frame. This view prints header metadata. The independently measured byte coverage comes from counting TCP sequence positions after the HTTP headers.

4단계 · 필요한 경우 선언 길이와 상태를 오프라인에서 확인

TShark 
tshark -n -r "2025-12-23-MacSync-Stealer-traffic.pcap" \
  -Y 'frame.number == 104 || frame.number == 171 || frame.number == 189' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e tcp.stream -e ip.src \
  -e http.request.method -e http.content_length -e http.response.code

헤더가 분명하지 않으면 원본 요청의 시작, 마지막 클라이언트 데이터 프레임과 응답 헤더를 읽습니다. 같은 TCP 스트림의 메서드, 선언 길이와 응답 상태를 비교합니다. 재조립 방식에 따라 TShark가 요청 필드를 뒤쪽 프레임에 표시할 수 있습니다. 이 조회는 헤더 메타데이터를 출력합니다. 실제 바이트 범위는 HTTP 헤더 뒤 TCP 시퀀스 위치를 세어 별도로 확인했습니다.

5 · Record the transfer and the publisher’s modification

Record the capture hash, destination changes, HTTP Host, observed body length and reply frame. Include the publisher’s statement that the public archive was altered. Verify authorized uploads and ask the incident owner for endpoint process, file-access and proxy records. Use evidence collected in that incident to assess what data was exposed.
