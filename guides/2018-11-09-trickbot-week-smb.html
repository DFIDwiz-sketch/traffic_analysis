What the capture shows

The archive’s author reports that Trickbot spread from a lab workstation, 172.16.9.233, to its domain controller, 172.16.9.5. The length of this capture makes one distinction especially important. Routine SMB can be present before and after the suspicious transfer. Start with the pair and then identify the specific operation, time and connection that support your conclusion.

1 · Establish daily SMB activity in Splunk

Use the capture metadata to set the time range and set the display time zone to UTC. Replace <CASE> with your real pcap_case value. Splunk examples use flattened Zeek fields. Keep only one Zeek import in scope if the same input was ingested repeatedly.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

The inventory verifies that events have arrived and shows which SMB logs are available. An absent sourcetype can reflect analyzer coverage or ingestion settings. Check the source file and index mappings before interpreting an empty result.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp id_resp_p=445 id_orig_h=172.16.9.233 id_resp_h=172.16.9.5
| eval utc_day=floor(ts/86400)*86400
| stats count as connections sum(orig_bytes) as sent sum(resp_bytes) as received
        min(ts) as first max(ts) as last by utc_day
| sort 0 utc_day
| eval day=strftime(utc_day,"%Y-%m-%d"), first=strftime(first,"%H:%M:%S"), last=strftime(last,"%H:%M:%S")
| table day connections sent received first last

This search aggregates the workstation-to-DC direction by UTC day using the numeric epoch value in ts. Check connection count, payload in each direction and the first time on each day. Zeek connection counts are distinct from SYN packet counts, which can include retries. To check for DC-initiated activity, swap the endpoints and run a separate search. A server's replies on an existing session do not make it its initiator.

1단계 · Splunk에서 날짜별 SMB 활동 확인

위 캡처 메타데이터를 기준으로 검색 기간을 지정하고 표시 시간은 UTC로 설정합니다. <CASE>를 실제 pcap_case 값으로 바꾸세요. SPL은 평탄화된 Zeek 필드명을 가정합니다. 같은 파일을 여러 번 수집했다면 Zeek 처리 한 건으로 범위를 좁힙니다.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

이 검색으로 수집 여부와 확인 가능한 SMB 로그 종류를 파악합니다. 특정 sourcetype이 없으면 분석기 가시성이나 수집 설정을 확인하세요. 결과가 비어 있을 때는 원본 파일과 인덱스 설정도 확인합니다.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp id_resp_p=445 id_orig_h=172.16.9.233 id_resp_h=172.16.9.5
| eval utc_day=floor(ts/86400)*86400
| stats count as connections sum(orig_bytes) as sent sum(resp_bytes) as received
        min(ts) as first max(ts) as last by utc_day
| sort 0 utc_day
| eval day=strftime(utc_day,"%Y-%m-%d"), first=strftime(first,"%H:%M:%S"), last=strftime(last,"%H:%M:%S")
| table day connections sent received first last

워크스테이션이 DC로 시작한 연결을 ts의 숫자 epoch 값으로 UTC 날짜별 집계합니다. 연결 수와 방향별 페이로드 바이트, 날짜별 첫 시각을 봅니다. Zeek 연결 수는 재시도가 포함될 수 있는 SYN 패킷 수와 다릅니다. DC가 시작한 연결을 비교하려면 주소를 바꿔 별도로 검색하세요. 기존 연결에서 서버가 보내는 응답은 새로운 연결 시작이 아닙니다.

2 · Find the executable-write evidence

SPL 
index=zeek pcap_case="<CASE>" id_orig_h=172.16.9.233 id_resp_h=172.16.9.5 id_resp_p=445
    sourcetype IN ("zeek:conn","zeek:smb_mapping","zeek:smb_files","zeek:dce_rpc","zeek:ntlm")
| sort 0 ts
| eval time_utc=strftime(ts,"%Y-%m-%d %H:%M:%S.%3N %Z")
| table time_utc sourcetype uid id_orig_p path name action endpoint operation conn_state

Find the relevant zeek:conn record using the client port in the evidence table. Compare its uid with SMB share and file records from the same Zeek processing run. Use path, name and action together. A file-open record by itself does not show a write. RPC on a named pipe can also look like a file operation. Check the object name before reporting a disk file.

UTC, 2 Nov 2018 Frames Directly observed

00:16:29.889 9936, 9937 SMB write and zero-status reply associated with the netlogon named pipe
00:16:29.906 9998, 10002 First observed successful write exchange for \WINDOWS\44783m8u…exe on client port 52372
00:16:29.975 10535, 10539 Successful write exchange for \WINDOWS\lgwgf4lr…exe on the same TCP connection
00:16:30.051 10685, 10686 Write and zero-status reply to the svcctl named pipe. Check host evidence for actual service activity.

The workstation sent 906 SYN packets without ACK toward DC TCP/445 over the full capture. The same direction’s flows accounted for 22,903 packets including both directions and control traffic. Do not count them as 906 incidents or 22,903 SMB operations. The executable names are shortened. These names also appear in the June case, but different capture hashes and timestamps identify two separate observations. Filenames alone do not establish identical file content.

The file evidence associates SMB1 file-open and write metadata with the reply on the same session. A successful write reply supports data transfer to that object. Confirm process or service execution separately. An administrative deployment could produce similar SMB metadata, particularly if the filename and timing match an approved change.

2단계 · 실행 파일 쓰기 근거 찾기

SPL 
index=zeek pcap_case="<CASE>" id_orig_h=172.16.9.233 id_resp_h=172.16.9.5 id_resp_p=445
    sourcetype IN ("zeek:conn","zeek:smb_mapping","zeek:smb_files","zeek:dce_rpc","zeek:ntlm")
| sort 0 ts
| eval time_utc=strftime(ts,"%Y-%m-%d %H:%M:%S.%3N %Z")
| table time_utc sourcetype uid id_orig_p path name action endpoint operation conn_state

근거 표의 클라이언트 포트로 해당 zeek:conn 기록을 찾습니다. 같은 Zeek 처리 실행에서 생성된 공유 매핑·파일 로그와 uid를 대조합니다. path, name, action을 함께 확인하세요. 파일을 열었다는 기록만으로 데이터 쓰기를 입증할 수 없습니다. 이름 파이프의 RPC 통신도 파일 작업처럼 보일 수 있으므로 디스크 파일로 기록하기 전에 대상 이름을 확인합니다.

2018년 11월 2일 UTC 프레임 원본에서 직접 확인한 근거
00:05:37.710 126, 127 워크스테이션이 DC의 TCP/445로 보낸 첫 관측 SYN과 대응 SYN/ACK. 클라이언트 포트는 49164.
00:16:29.889 9936, 9937 netlogon 이름 파이프에 대한 SMB 쓰기와 상태값 0인 응답
00:16:29.906 9998, 10002 클라이언트 포트 52372에서 \WINDOWS\44783m8u…exe의 첫 관측 쓰기 성공
00:16:29.975 10535, 10539 같은 TCP 연결에서 \WINDOWS\lgwgf4lr…exe 쓰기 성공
00:16:30.051 10685, 10686 svcctl 이름 파이프 쓰기와 상태값 0인 응답. 실제 서비스 동작은 호스트 기록에서 확인.

전체 캡처에서 워크스테이션은 DC의 TCP/445로 ACK 플래그가 없는 SYN 패킷 906개를 보냈습니다. 워크스테이션이 시작한 흐름에는 응답과 제어 패킷을 포함해 양방향 패킷 22,903개가 있었습니다. 이를 각각 사고 건수나 SMB 작업 수로 해석하면 안 됩니다. 파일명은 축약했습니다. 6월 사례에도 같은 이름이 나오지만 두 캡처의 해시와 시각은 서로 다릅니다. 파일명만으로 내용까지 같다고 판단할 수 없습니다.

SMB1 파일 열기와 쓰기 메타데이터를 같은 세션의 응답과 연결해 확인했습니다. 쓰기 성공 응답은 해당 대상에 데이터가 전송됐다는 근거입니다. 프로세스나 서비스 실행에는 별도 근거가 필요합니다. 승인된 소프트웨어 배포도 비슷한 SMB 기록을 남길 수 있으므로 파일명과 시각을 변경 작업 기록과 대조합니다.

3 · Cross-check one session in Arkime

Arkime 
tags == "<CASE>" && ip.src == 172.16.9.233 && ip.dst == 172.16.9.5 &&
port.src == 52372 && port.dst == 445

Set the UTC picker around the first verified executable write in the table. Open the matching session and check both endpoints and ports before examining the packet timeline. If Zeek and Arkime disagree, compare the PCAP hash, direction and selected time range. If packet retention is incomplete, use the original PCAP for the narrow check below.

3단계 · Arkime에서 세션 하나 교차 확인

Arkime 
tags == "<CASE>" && ip.src == 172.16.9.233 && ip.dst == 172.16.9.5 &&
port.src == 52372 && port.dst == 445

근거 표의 첫 실행 파일 쓰기 시각 전후로 UTC 범위를 좁힙니다. 세션을 열어 양쪽 주소와 포트를 확인한 뒤 패킷 타임라인을 봅니다. Zeek와 Arkime의 결과가 다르면 PCAP 해시, 연결 방향, 검색 기간을 대조하세요. 보존된 패킷이 부족하면 아래처럼 원본 PCAP의 좁은 범위를 확인합니다.

4 · Check the response in TShark if needed

TShark 
tshark -n -r "2018-11-09-one-week-of-a-Trickbot-infection.pcap" \
  -Y 'ip.addr == 172.16.9.233 && ip.addr == 172.16.9.5 && tcp.port == 52372 && smb.cmd == 0x2f' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e ip.src -e ip.dst \
  -e tcp.stream -e smb.mid -e smb.nt_status

Read the original file and print only metadata for SMB1 write exchanges on the chosen connection. Match the request and reply by TCP stream and SMB multiplex ID. Compare the response status and direction. Subsequent retransmissions or reassembly can change where a dissector displays the transaction, so retain the timestamp and endpoint tuple alongside the frame numbers.

4단계 · 필요할 때 TShark에서 응답 확인

TShark 
tshark -n -r "2018-11-09-one-week-of-a-Trickbot-infection.pcap" \
  -Y 'ip.addr == 172.16.9.233 && ip.addr == 172.16.9.5 && tcp.port == 52372 && smb.cmd == 0x2f' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e ip.src -e ip.dst \
  -e tcp.stream -e smb.mid -e smb.nt_status

원본에서 선택한 연결의 SMB1 쓰기 메타데이터만 출력합니다. TCP 스트림과 SMB Multiplex ID로 요청과 응답을 연결하고, 응답 방향과 상태값을 봅니다. 재전송이나 재조립에 따라 디섹터가 작업을 표시하는 프레임이 달라질 수 있으므로 프레임 번호와 함께 시각, 양쪽 주소와 포트를 기록합니다.

5 · Prepare the incident ticket

Record the workstation, destination DC, the successful write time, frame pair and capture hash. Report Trickbot attribution as the publisher’s conclusion. In a live case, request host-side evidence of file creation and process or service activity on the DC. Review the file transfer against approved change records, and scope related connections from both systems independently.
