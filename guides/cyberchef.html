When a traffic capture contains unreadable text, start by looking at its shape and choosing a CyberChef operation that fits. Decode one layer, inspect the result, then choose the next operation.

트래픽 분석에서 만나는 알아볼 수 없는 글자를 모양으로 구별하고, 맞는 CyberChef 작업을 고르는 방법을 정리했어요. 핵심은 한 번에 다 풀려고 하지 않고, 한 겹 풀고 → 결과 모양을 다시 보고 → 다음 겹을 고르는 것이에요.

How to choose a decoder

Use the following checks whenever you find unfamiliar text. After peeling off a layer, start again from step 1. Malware traffic can have several layers. For example, an analyst might decode Hex, then XOR, then URL encoding.

  1. Isolate the value. Remove enclosing quotes, field labels such as a=, and any formatting whitespace or line breaks that are outside the data. Paste the value into CyberChef and check the character count beside ABC.
  2. Look at the character set. Is it limited to 0-9a-f? Does it use A-Z a-z 0-9 + /, possibly with = at the end? Do you see many percent signs, or markers like \x, \u, or &#? Compare it with the table below.
  3. Check the length. A complete sequence of Hex bytes has an even number of digits. Padded Base64 has a length divisible by four.
  4. Check the prefix. Strings beginning with TVqQ, H4sI, aHR0c, or 4d5a can suggest what is inside.
  5. Read the surrounding code. Functions such as atob, getUrl, and FromBase64String can show how a value is decoded.
  6. Decode one layer and inspect the output.
    • If you get readable text, stop or check for another pattern such as %xx.
    • If the output resembles another encoding, such as Base64 or Hex, use the character-set check again.
    • If you see a recognizable file signature, such as MZ, PK, or 1f8b, identify the file type. Decompress recognized compressed data in your analysis environment. Stop if you find an executable.
    • If you get unrecognizable bytes, consider XOR, compression, or encryption.
  7. Try Magic when you get stuck. It tests common operations and suggests candidate outputs for you to inspect.
  8. Know when to stop. Entropy close to 8 bits per byte and an absence of obvious repetition can suggest compression or encryption. Entropy is a clue. If you cannot identify the format or obtain the key for confirmed encryption, document what you observed and escalate for malware analysis.

판단 순서

알아볼 수 없는 글자를 만나면 아래 순서대로 확인해요. 한 단계를 풀 때마다 결과를 다시 1번부터 봐요. 악성코드 트래픽에는 여러 겹이 겹칠 수 있어요(예: Hex → XOR → URL 인코딩).

  1. 앞뒤를 다듬어요. 따옴표, a= 같은 이름 부분, 공백, 줄바꿈을 빼고 데이터만 Input에 넣어요. CyberChef 아래의 ABC 글자 수가 예상과 맞는지 봐요.
  2. 쓰인 글자의 종류(문자 집합)를 봐요. 0-9a-f뿐인가? A-Z a-z 0-9 + /에 끝이 =인가? %가 많은가? \x, \u, &#가 보이는가? → 다음 섹션의 표에서 찾아요.
  3. 길이를 봐요. 완전한 바이트를 나타내는 Hex는 짝수, 패딩을 포함한 Base64는 4의 배수예요.
  4. 시작 글자를 봐요. TVqQ, H4sI, aHR0c, 4d5a처럼 자주 나오는 접두어가 있어요(시작 글자 섹션).
  5. 주변 코드를 봐요. 글자를 감싼 함수(atob, getUrl, FromBase64String)가 있으면 그 함수가 해독 방법이에요(번역표 섹션).
  6. 한 겹 풀고 결과를 판단해요.
    • 읽을 수 있는 글자 → 끝, 또는 여전히 %xx가 있으면 URL Decode
    • 또 인코딩 모양(Base64, Hex) → 2번으로
    • 파일 시그니처(MZ, PK, 1f8b) → 파일이에요. 압축이면 풀고, 실행 파일이면 멈춰요
    • 알아볼 수 없는 바이트 → XOR이나 압축, 암호화를 의심해요(XOR 섹션)
  7. 막히면 Magic을 써요. CyberChef의 Magic 작업은 흔한 해독을 자동으로 시험해서 그럴듯한 결과를 보여 줘요(도움 기능 섹션).
  8. 멈출 때를 알아요. Entropy가 8에 가깝고 반복 무늬가 없으면 압축이나 암호화를 의심할 수 있어요. Entropy만으로 둘을 구분할 수는 없어요. 형식을 확인하기 어렵거나 암호화가 확인됐는데 키가 없다면, 관찰한 내용을 티켓에 적고 악성코드 분석 담당에게 넘겨요.

Recognizing common encodings

The characters used are often your best starting clue. The Base64 alphabet includes the letters and digits used by Hex. If a string consists entirely of Hex digits and has an even length, try Hex first.

Points that often cause confusion

  • Hex vs. Base64. Letters beyond A–F or a–f rule out plain Hex. An odd number of digits cannot represent complete Hex byte pairs.
  • Base64 padding is sometimes absent. Some values need no padding, and some formats omit it. When present, = padding belongs at the end. An internal = can separate a field name from its value.
  • Interpret URL escapes in context. For form-encoded data, + can represent a space. Decode the outermost layer first. In the POST example below, URL escapes only appeared after removing Hex and XOR.

헷갈리기 쉬운 점

  • Hex인지 Base64인지: A–F나 a–f 범위를 벗어난 알파벳이 섞여 있으면 순수한 Hex가 아니에요. 길이가 홀수여도 Hex가 아니에요(앞뒤에 다른 글자가 붙었는지도 확인).
  • Base64에 =가 없을 수도 있어요. 길이가 딱 맞으면 =가 필요 없어요. 패딩인 =는 끝에만 와요. 중간의 =는 이름=값을 나누는 구분자일 수 있어요.
  • URL 인코딩은 데이터가 오간 맥락을 보고 풀어요. 웹 폼 인코딩의 +는 공백을 뜻할 수 있어요. 바깥쪽부터 풀고, 아래 POST 사례처럼 Hex와 XOR을 푼 뒤에 %xx가 보이면 그때 URL Decode를 적용해요.

Common prefixes and file signatures

Many file formats start with recognizable bytes called signatures or magic numbers. Encoded prefixes can help you choose a next step. Check the decoded bytes before drawing a conclusion.

Likely content Initial bytes or text Hex prefix Common Base64 prefix Next step
Windows executable or DLL MZ 4d5a TVqQ is common Verify the format and hash the file without executing it
gzip 1f 8b 08 1f8b08 H4sI Gunzip
zlib 78 9c, 78 01, or 78 da 789c for one common header eJ for that header Zlib Inflate
ZIP, DOCX, XLSX, or JAR PK\x03\x04 504b0304 UEsDB Unzip
PDF %PDF- 255044462d JVBERi0 Analyze as a PDF
Legacy Office document (DOC, XLS) D0 CF 11 E0 d0cf11e0 0M8R4 Inspect with document or macro-analysis tools
Linux executable (ELF) \x7fELF 7f454c46 f0VMR Stop and hash the file
PNG image \x89PNG 89504e47 iVBORw0KGgo Render Image
JPEG image FF D8 FF ffd8ff /9j/ Render Image
HTTP URL http:// 687474703a2f2f aHR0cDovL Read the text
HTTPS URL https:// 68747470733a2f2f aHR0cHM6Ly Read the text
XML declaration <?xml 3c3f786d6c PD94bWw Read the text
PowerShell command in UTF-16LE $ followed by NUL 2400 JAB when the next character has a matching prefix Decode text (UTF-16LE)
PowerShell IEX in UTF-16LE I\0E\0X\0 490045005800 SQBFAFgA Decode text (UTF-16LE)

How to use these clues

  • TVqQ suggests a payload with an MZ header. H4sI suggests using From Base64 followed by Gunzip.
  • Windows PowerShell expects UTF-16LE text for -EncodedCommand. The NUL bytes in ASCII-range UTF-16LE commands often produce repeated A characters in Base64. Use From Base64 → Decode text (UTF-16LE (1200)).
  • If you identify an executable, stop at static triage. Compute SHA-256 or MD5 with SHA2 or MD5, record it in the ticket, and hand the sample to the malware analysis team. Keep it out of your normal working environment.
  • Detect File Type can use the decoded bytes to suggest a file type.

자주 보는 시작 글자와 파일 시그니처

파일은 종류마다 정해진 첫 바이트(매직 넘버, 시그니처)로 시작해요. 그래서 인코딩된 글자의 처음 몇 글자만 봐도 안에 무엇이 들었는지 짐작할 수 있어요. 아래 값을 외워 두면 풀기 전에 방향이 보여요.

안에 든 것 원래 첫 바이트 (글자) Hex로 보면 Base64로 보면 다음 작업
윈도우 실행 파일(EXE, DLL) MZ 4d5a 흔한 예는 TVqQ 형식을 확인하고 실행 없이 해시 구하기
gzip 압축 1f 8b 08 1f8b08 H4sI Gunzip
zlib 압축 78 9c (또는 78 01, 78 da) 789c eJ Zlib Inflate
ZIP, DOCX, XLSX, JAR PK\x03\x04 504b0304 UEsDB Unzip

PowerShell IEX(UTF-16LE) I\0E\0X\0 490045005800 SQBFAFgA Decode text (UTF-16LE)

쓰는 법

  • Base64 글자가 TVqQ로 시작하면 MZ 헤더가 있을 수 있으니 풀린 바이트에서 형식을 확인해요. H4sI면 From Base64 다음에 Gunzip을 붙여요.
  • PowerShell의 -enc/-EncodedCommand 뒤의 글자는 UTF-16LE 텍스트를 Base64로 바꾼 거예요. 그래서 JAB, SQBFAFgA처럼 A가 반복되는 모양이 자주 나와요. 레시피는 From Base64 → Decode text(UTF-16LE (1200))예요.
  • 실행 파일(MZ, ELF)이 나오면 거기서 멈춰요. SHA256 / MD5만 구해서(CyberChef SHA2, MD5) 티켓에 적고, 파일은 악성코드 분석 담당에게 넘겨요. 풀린 파일을 열거나 실행하지 않아요.
  • Detect File Type 작업을 마지막에 붙이면 CyberChef가 시그니처를 보고 파일 종류를 알려 줘요.

When to suspect XOR

XOR is often used to obscure data. Applying the same XOR key again recovers the original bytes. With a one-byte key there are 256 possibilities.

Look for these clues

  • Hex or Base64 decoding produces unreadable bytes without an obvious compression signature such as 1f8b or 789c.
  • A particular byte appears unusually often. Plaintext spaces or zero bytes can map to one frequently occurring value when XORed with a fixed byte.
  • Blocks recur at regular intervals. This can suggest a repeating key. Treat the interval as a candidate key length and verify it with other evidence.
  • The code contains ^, xor, or Xor.

Use entropy as a clue. CyberChef’s Entropy operation reports a value from 0 to 8 bits per byte.

Approximate entropy Possible interpretation What to check
3.5–5 Text, code, or form data If unreadable, consider fixed-byte XOR or a character substitution. Fixed-byte XOR preserves byte entropy.
5–7 Executable or mixed data Look for frequency patterns and file signatures before drawing a conclusion.
7.5 or higher Compressed or encrypted data Check for a format or context clue. Document the result and escalate if you cannot identify it.

Estimate the key from byte frequency. Use Frequency distribution to see which bytes occur most often.

  • If the original was text and space was the most frequent character, try most frequent byte XOR 0x20 as a candidate key.
  • If the original file had many zero bytes, the most frequent byte can be the key itself because zero XOR the key equals the key.

XOR Brute Force settings

Option Value What it does
Key length 1 to start, or 2 when supported by the evidence Sets the number of key bytes. Two bytes means 65,536 candidates.
Sample length Start with 100 bytes Sets how many bytes to test. Increase it if your crib may occur later.
Sample offset 0 to start Sets the starting byte.
Crib See the next section Keeps candidate results that contain the expected text.
Print key On Shows the key beside the result.
Output as hex Off for text Displays text for inspection.

Once you have a candidate that you can verify, switch to XOR, enter the key in HEX, and continue with the next layer.

Repeating keys. Repeated structure can point to a candidate period. If you know the original contains a run of zero bytes, that run can expose part or all of the key in the corresponding output. For a longer key, record “repeating-key XOR suspected” and escalate if appropriate. Use the Null preserving setting only when it matches the behavior you observe in the sample.

XOR — 언제 의심하고 어떻게 푸나

XOR은 악성코드가 가장 흔하게 쓰는 간단한 숨기기예요. 바이트마다 키를 XOR하고, 같은 키로 한 번 더 XOR하면 원래대로 돌아와요. 키가 1바이트면 가능한 키가 256개뿐이라 다 시험해 볼 수 있어요.

이럴 때 XOR을 의심해요

  • Hex나 Base64를 풀었는데 알아볼 수 없는 바이트가 나왔고, 압축 시그니처(1f8b, 789c)도 없어요.
  • 풀린 바이트에 같은 값이 유난히 자주 나와요. 원래 글의 공백이나 0 바이트가 키와 XOR돼서 같은 값이 됐기 때문이에요.
  • 같은 덩어리가 일정한 간격으로 반복돼요. 여러 바이트 키를 반복해서 쓴 신호예요. 반복 간격을 키 길이 후보로 보고 다른 단서와 대조해요.
  • 코드에 ^, xor, Xor가 보여요.

Entropy로 먼저 가르기 — CyberChef Entropy 작업은 데이터가 얼마나 무작위인지 0~8로 보여 줘요(바이트당 비트).

Entropy 보통 뜻 할 일
약 3.5~5 글자(영어, 코드, 폼 데이터) 읽을 수 없다면 1바이트 XOR이나 ROT류를 의심해 볼 수 있어요. 1바이트 XOR은 Entropy를 바꾸지 않아요
약 5~7 실행 파일, 여러 종류가 섞인 데이터 XOR된 실행 파일일 수 있어요. 빈도 분석으로 키를 찾아요
7.5 이상 압축 또는 암호화 가능성 형식과 주변 단서를 확인해요. 구별하기 어렵다면 관찰한 내용을 티켓에 적고 넘겨요

빈도로 키 찾기 (crib 없이) — CyberChef Frequency distribution 작업으로 가장 많이 나오는 바이트를 봐요.

  • 원래가 글자였다면 가장 흔한 글자는 보통 공백(0x20)이에요. 그래서 키 = 가장 많은 바이트 XOR 0x20일 가능성이 높아요.
  • 원래가 실행 파일이었다면 0 바이트가 가장 많아요. 그래서 가장 많은 바이트 = 키 그 자체예요(0 XOR 키 = 키).

XOR Brute Force 설정

옵션 값 뜻
Key length 1 (안 되면 2) 시험할 키의 바이트 수. 2는 65,536개라 느려요
Sample length 기본값(100) 앞부분 몇 바이트만 시험할지. crib이 뒤쪽에 있을 것 같으면 늘려요
Sample offset 0 몇 번째 바이트부터 시험할지
Crib 아래 crib 섹션 이 글자가 나오는 키만 보여 줘요
Print key 켜기 결과 옆에 키를 보여 줘요
Output as hex 끄기 글자로 보여 줘요

키를 찾으면 XOR Brute Force를 XOR로 바꾸고(Key = 찾은 값, HEX) 다음 작업을 이어 붙여요.

여러 바이트 키일 때 — 반복 간격(키 길이)이 보이고, 원래 데이터에 0 바이트가 많으면 그 부분에서 키가 그대로 드러나요. 하지만 키가 길면 티켓 단계에서 풀려고 하지 말고, "repeating-key XOR suspected"라고 적고 악성코드 분석으로 넘겨요. Null preserving은 분석 중인 코드가 그 방식으로 처리하는 것이 확인될 때 켜요.

Choosing a crib

A crib is a short string you expect to find in the decoded output. In XOR Brute Force, it filters the candidate results. Choose one based on where the data came from.

Context Expected content Possible crib
POST with Content-Type: application/x-www-form-urlencoded name=value&name=value &1=, &id=, or =, informed by the surrounding fields such as a= and b=
POST with Content-Type: application/json {"name":"value"} {" or ":"
Check-in that may contain endpoint information A known host or user name A name already observed in the baseline, such as CONSERVATOR or lloyd
Windows path C:\Users\… Users, .exe, or AppData. If the current layer still contains URL escapes, try C%3A%5C.
URL in a downloader or configuration http://… http, ://, or .com
Web page or script HTML or JavaScript <html, <script, function, or var
PowerShell command Command text powershell, IEX, New-Object, or http
Embedded executable MZ followed by a DOS stub This program or the MZ bytes (4d5a in Hex)
No clues beyond probable English text English words A space or the
Known malware format A fixed field in that format For example, Hancitor GUID= or BUILD=
  1. Match the layer you are testing. If URL escapes are still present immediately after XOR, use C%3A%5C instead of an unescaped path. In the case below, &1= was present as a literal separator in the decoded form structure.
  2. Prefer a specific crib you can justify. A single = can occur by chance in many candidates. A correct three-character string such as &1= is more selective.
  3. Shorten the crib if you get no matches. For example, try &1=, then =, then a space.
  4. Check the sample range. If your crib falls outside the tested bytes, increase Sample length or adjust Sample offset.
  5. Check separate fields independently. In the sample POST, the a=, b=, and c= fields used different keys.
  6. Record your reasoning. Keep the crib, where it came from, and the recipe in your notes so another analyst can reproduce the result.

Crib 고르는 법

Crib은 "원래 글에 틀림없이 들어 있을 글자"예요. XOR Brute Force는 256개 결과 중 crib이 들어 있는 것만 보여 줘요. crib은 데이터가 어디에서 왔는지를 보고 골라요.

상황별 crib

데이터가 있던 곳 / 단서 원래 글의 모양(추측) 쓸 crib

POST, Content-Type: application/json {"이름":"값"} {", ":"
피해 PC 정보를 보냈을 것 같은 체크인 호스트 이름, 사용자 이름 베이스라이닝에서 찾은 이름 (예: CONSERVATOR, lloyd) — 가장 강력해요
윈도우 경로가 있을 것 C:\Users\… Users, .exe, AppData. URL 인코딩되기 전이면 C%3A%5C
주소가 있을 것(다운로더, 설정) http://… http, ://, .com

알려진 악성코드 그 악성코드의 고정 형식 예: Hancitor GUID=, BUILD=

규칙

  1. crib은 "그 겹에서의 모양"으로 써요. XOR 다음에 URL Decode가 남아 있다면, XOR을 푼 직후의 글에는 \가 아니라 %5C가 있어요. 그래서 crib C:\는 실패하고 C%3A%5C는 성공해요. 이번 POST에서는 필드 구분자인 &1=가 XOR을 푼 폼 구조에 그대로 들어 있었어요.
  2. 길수록 정확하지만, 확실해야 해요. = 한 글자는 여러 키에서 우연히 나와요. &1=처럼 3글자 이상이면 거의 하나만 남아요. 하지만 길게 쓴 crib이 틀리면 아무것도 안 나와요.
  3. 아무것도 안 나오면 crib을 짧게 바꿔서 다시 해요. &1= → = → 공백 순서로요.
  4. crib이 샘플 길이 안에 있어야 해요. Sample length는 기본 100바이트예요. crib이 뒤쪽에 있을 것 같으면 Sample length를 늘려요.
  5. 여러 메시지는 키가 다를 수 있어요. 이번 POST는 a=, b=, c=마다 키가 달랐어요. 메시지마다 따로 찾아요.
  6. crib을 어떻게 골랐는지 작업 노트에 적어요. 다른 사람이 같은 결과를 다시 만들 수 있어야 해요.

CyberChef tools and common mistakes

Operation When to use it What to look for
Magic When the encoding is unclear Tests common decoding recipes and suggests candidates. Depth controls how many layers it explores. Intensive mode tests more possibilities at a cost in speed. Try a crib if you expect a known string. Custom transformations like getUrl may require manual analysis.
Entropy When considering compression, encryption, or XOR Use the value alongside other evidence.
Frequency distribution When estimating a fixed XOR key without a crib Look for the most frequent byte.
Detect File Type When the decoded output may be a file Look for recognized signatures.
Strings When looking for text inside binary data Start with a minimum length of 4–6 to find URLs, paths, and commands.
Extract URLs / Extract IP addresses / Extract domains When collecting indicators Build a list of indicators of compromise.
Defang URL / Defang IP Addresses Before pasting indicators into a ticket For example, http → hxxp and . → [.].
MD5 / SHA2 When hashing a decoded file Record the hash for tracking or lookup.
From UNIX Timestamp For 10-digit seconds or 13-digit milliseconds Set Units to match the input.
Remove whitespace / Remove null bytes When extra formatting is present Remove only bytes that the expected format allows you to discard.
Save / load recipe When reusing a tested sequence For example, odd-chars-reverse or hex-xor-urldecode.

Troubleshooting

Symptom Possible cause What to check
Output looks shifted Quotes, a field prefix such as a=, or whitespace was included Compare the expected length with the input count at ABC.
Only the tail is garbled or missing A folded line in Arkime was skipped or the packet-view limit cut off the input Compare against available metadata, such as the request body length.
Find / Replace changes nothing Find and Replace were swapped, Simple string was selected, or Global match is off Put the pattern in Find and $1 or $2 in Replace. Enable Regex and Global.
XOR output looks wrong The key was interpreted as UTF-8 text, so 5d became two characters Select HEX for the key.
An otherwise plausible recipe fails The operations are in the wrong order Remove the outermost encoding first and inspect each step.
XOR Brute Force returns no matches The crib is wrong, in a different representation, or outside the sample Shorten the crib, match the current layer, or increase Sample length.
Base64 decoding stops early The input contains unexpected characters or missing data Check that all input was captured. Remove non-alphabet characters only if they are known formatting noise.

Analysis precautions

  • If a decoded result is an executable, stop after identification and hashing. Handle the sample using your malware-analysis process.
  • Leave decoded addresses as text and defang them before putting them in a ticket.
  • Keep captured scripts as data. Recreate understood transformations and escalate unfamiliar code for specialist analysis.
  • Record the recipe, key and crib in the ticket’s tool output. For example, From Hex -> XOR Brute Force (crib "&1=") -> XOR 5d -> URL Decode.

XOR Brute Force에서 아무것도 안 나옴 crib이 틀렸거나 다른 겹의 모양, 또는 샘플 길이 밖 crib을 짧게, Sample length 늘리기
Base64가 일부만 풀림 줄바꿈이나 다른 글자가 섞임 입력이 온전한지 확인하고, 섞인 문자가 단순한 서식일 때만 Remove non-alphabet chars를 켜요

안전 원칙

  • 풀린 결과가 실행 파일이면 해시만 구하고 멈춰요. 저장해서 열거나 실행하지 않아요.
  • 풀린 주소는 클릭하지 않고, 티켓에는 Defang해서 적어요.
  • 캡처에서 나온 코드는 데이터로 다뤄요. 확인된 변환만 재현하고 익숙하지 않은 코드는 전문 분석으로 넘겨요.
  • 티켓의 TOOL OUTPUT에는 레시피와 키, crib을 한 줄로 남겨요. 예: From Hex -> XOR Brute Force (crib "&1=") -> XOR 5d -> URL Decode
