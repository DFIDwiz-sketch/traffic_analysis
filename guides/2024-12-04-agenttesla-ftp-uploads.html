What shows that files were uploaded?

The publisher reports AgentTesla-related exfiltration over FTP. In the original PCAP, client 10.12.4.101 sends four STOR commands to 192.254.225.136. For each command the capture shows the server selecting a passive data port, the client sending data on a separate connection, and the server reporting completion on the control channel. This guide uses commands, ports and reply codes as evidence.

파일 업로드를 보여주는 근거는 무엇인가

공개 원문은 AgentTesla와 관련된 FTP 유출을 보고합니다. 원본 PCAP에서 클라이언트 10.12.4.101은 192.254.225.136에 STOR 명령을 네 번 보냅니다. 각 요청에 대해 서버가 수동 모드 데이터 포트를 알렸고, 클라이언트는 별도 연결로 데이터를 보냈으며, 서버는 제어 채널에서 완료를 응답했습니다. 이 가이드는 명령, 포트와 응답 코드를 근거로 사용합니다.

1 · Baseline the host pair in Splunk

Replace <CASE> with the label assigned to this capture. Set the Splunk display to UTC, cover the entire capture, and use Zeek ts as event time if _time stores ingest time. The examples use flattened Zeek fields.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

Verify that connection and FTP logs are available. If FTP logs are missing, inspect the original control packets before drawing conclusions about transfer commands.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp
    id_orig_h=10.12.4.101 id_resp_h=192.254.225.136
| sort 0 ts
| table ts uid id_orig_p id_resp_p service conn_state orig_bytes resp_bytes

Read the connection table by time, source port and responder port. The control sessions go to TCP/21. Nearby connections to higher ports are candidates for passive FTP data. Compare originator and responder bytes to assess direction. A high port alone leaves the application and purpose open.

1단계 · Splunk에서 두 호스트의 베이스라인 확인

<CASE>에 캡처를 가져올 때 지정한 값을 넣습니다. Splunk 표시 시간대를 UTC로 설정하고 전체 캡처 구간을 포함합니다. _time이 수집 시각이면 Zeek ts를 사건 시각으로 사용합니다. 예제는 평탄화된 Zeek 필드를 기준으로 합니다.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

연결과 FTP 로그가 조회되는지 확인합니다. FTP 로그가 빠졌다면 원본 제어 패킷을 확인한 뒤 전송 명령을 판단합니다.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp
    id_orig_h=10.12.4.101 id_resp_h=192.254.225.136
| sort 0 ts
| table ts uid id_orig_p id_resp_p service conn_state orig_bytes resp_bytes

연결을 시각, 출발지 포트, 응답자 포트 기준으로 읽습니다. 제어 세션은 TCP/21이고, 인접 시각의 높은 번호 포트는 수동 FTP 데이터 채널 후보입니다. 송수신 바이트를 비교해 방향을 살핍니다. 포트만으로는 응용 프로토콜과 목적을 확인하기 어렵습니다.

2 · Match transfers across separate connections

SPL 
index=zeek sourcetype=zeek:ftp pcap_case="<CASE>" id_orig_h=10.12.4.101 id_resp_h=192.254.225.136 id_resp_p=21
    command IN ("PASV","STOR")
| sort 0 ts
| table ts uid id_orig_p command reply_code data_channel_passive data_channel_resp_h data_channel_resp_p

Use the FTP control UID to locate the TCP/21 record from the same Zeek processing run. Where available, use the passive flag and advertised IP and port in the data_channel fields. Map the dotted Zeek field names to your parser's flattened representation. A Zeek row may summarize the command and omit an intermediate reply. Use the packets to read the full ordering.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp
    id_orig_h=10.12.4.101 id_resp_h=192.254.225.136 id_resp_p IN (46489,37833,44947,48464)
| sort 0 ts
| table ts uid id_orig_p id_resp_p conn_state orig_bytes resp_bytes missed_bytes

The data channels are separate TCP connections with their own UIDs. Match the client, advertised server endpoint and time window. Then verify that the payload direction agrees with the STOR command. The server's 227 reply advertises the port after PASV. Its 150 reply precedes data, and the 226 reply indicates completion.

UTC · 4 December Original frames · 227 / STOR / first data / 226 Directly observed
21:21:03.286–21:21:03.537 41 / 46 / 49 / 54 Client sends data to server port 46489, then server reports completion
21:21:04.314–21:21:04.664 60 / 65 / 68 / 103 Same control connection, data to 37833
21:21:04.741–21:21:05.036 108 / 113 / 116 / 135 Same control connection, data to 44947
21:41:08.360–21:41:08.636 166 / 171 / 174 / 180 Later control connection, data to 48464

The selection separates four uploads from the number of control sessions. These observations support successful FTP transfers at the protocol level. An approved export or backup can produce the same sequence. The identity of the process, authorization, retained server copy and sensitivity of the transferred data require separate evidence.

2단계 · 별도 연결에 걸친 전송 대조

SPL 
index=zeek sourcetype=zeek:ftp pcap_case="<CASE>" id_orig_h=10.12.4.101 id_resp_h=192.254.225.136 id_resp_p=21
    command IN ("PASV","STOR")
| sort 0 ts
| table ts uid id_orig_p command reply_code data_channel_passive data_channel_resp_h data_channel_resp_p

FTP 제어 UID로 같은 Zeek 처리 실행의 TCP/21 연결을 찾습니다. 로그에 있다면 data_channel의 수동 모드 여부, 서버 IP와 포트를 읽습니다. 점으로 구분된 Zeek 필드 이름을 수집기의 평탄화 형태에 맞춥니다. Zeek에서 명령이나 응답 일부가 요약될 수 있으므로 전체 순서는 패킷으로 확인합니다.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp
    id_orig_h=10.12.4.101 id_resp_h=192.254.225.136 id_resp_p IN (46489,37833,44947,48464)
| sort 0 ts
| table ts uid id_orig_p id_resp_p conn_state orig_bytes resp_bytes missed_bytes

데이터 채널은 별개의 TCP 연결이므로 UID도 각각 다릅니다. 클라이언트, 서버가 알린 주소·포트와 시각을 기준으로 연결합니다. 페이로드 방향이 STOR 명령과 맞는지 비교합니다. PASV 뒤의 227 응답이 포트를 알려주고, 150 응답이 데이터 전송에 앞서며, 226 응답이 완료를 나타냅니다.

12월 4일 UTC 원본 프레임 · 227 / STOR / 첫 데이터 / 226 직접 확인한 근거
21:21:03.286–21:21:03.537 41 / 46 / 49 / 54 클라이언트가 서버 포트 46489로 데이터를 보내고 서버가 완료 응답
21:21:04.314–21:21:04.664 60 / 65 / 68 / 103 같은 제어 연결에서 37833으로 전송
21:21:04.741–21:21:05.036 108 / 113 / 116 / 135 같은 제어 연결에서 44947로 전송
21:41:08.360–21:41:08.636 166 / 171 / 174 / 180 이후 제어 연결에서 48464로 전송

전송 건수는 제어 세션 수와 따로 셉니다. 이 근거는 FTP 프로토콜 수준에서 업로드 성공을 뒷받침합니다. 승인된 내보내기나 백업도 같은 순서를 보일 수 있습니다. 프로세스, 권한, 서버의 파일 보존과 데이터의 민감도는 별도로 확인합니다.

4 · Read the control reply metadata offline if needed

TShark 
tshark -n -r "2024-12-04-AgentTesla-variant-using-FTP.pcap" \
  -Y '(frame.number == 41 || frame.number == 48 || frame.number == 54)' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e ftp.response.code -e ftp.passive.port

If Arkime leaves the advertised port unclear, read the three original server replies for the first transfer. Compare the 227, 150 and 226 codes. The passive-port field should be populated on the 227 reply. This filter returns only selected reply metadata.

5 · Document the uploads and scope potential exposure

Include the hash, two endpoints, control and data tuples, and the completed transfer frames in the ticket. Check the FTP destination and source process against approved jobs. Ask for endpoint process and file-access records, firewall telemetry and server-side transfer logs if available. Restrict handling of sensitive capture data and use endpoint or server evidence to scope any exposure.
