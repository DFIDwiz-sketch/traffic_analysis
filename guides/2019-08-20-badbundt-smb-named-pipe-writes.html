What did the later SMB writes target?

The public Badbundt exercise investigates an infected workstation in an Active Directory network. The publisher’s answer identifies Ursnif and Trickbot. In the original capture, workstation 10.8.20.101 first reads a policy file from domain controller 10.8.20.8 over SMB2. Later the same pair exchanges repeated SMB1 traffic. Several accepted write requests point to named pipes on IPC$. Investigate the burst as possible lateral activity and establish which objects the selected writes actually reached.

이후의 SMB 쓰기는 어떤 대상을 향했는가?

공개 실습 Badbundt는 Active Directory 환경에서 감염된 워크스테이션을 조사하는 사례입니다. 저자의 해설은 Ursnif와 Trickbot을 지목합니다. 원본에서 워크스테이션 10.8.20.101은 먼저 도메인 컨트롤러 10.8.20.8의 정책 파일을 SMB2로 읽습니다. 이후 같은 주소 쌍에서 SMB1 트래픽이 반복되고, 성공 응답이 돌아온 쓰기 중 여러 건은 IPC$의 네임드 파이프를 향합니다. 이 구간을 횡적 이동 가능성이 있는 활동으로 조사하고, 선택한 쓰기가 어떤 객체에 도달했는지 확인합니다.

1 · Baseline TCP/445 by minute and responder

Use the case tag for <CASE>. Display the full capture in UTC and use Zeek's numeric ts for capture time. If Splunk filters on ingest time, include the corresponding import interval. The examples use flattened field names.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

Check which connection, SMB and DCE/RPC logs are present. Some of the older SMB exchanges may have limited parser coverage.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp id_orig_h=10.8.20.101 id_resp_p=445
| eval minute=floor(ts/60)*60
| stats dc(uid) as connections sum(orig_pkts) as client_packets sum(resp_pkts) as server_packets
    values(conn_state) as states by minute id_resp_h
| sort 0 minute id_resp_h

Compare TCP/445 activity by minute and responder. Around 19:50 UTC, focus on the client’s traffic to the DC separately from the traffic to the gateway 10.8.20.1. Across the original capture, the DC flow group has 6,141 TCP/445 packets in both directions and SYNs from 44 distinct client ports. Those packet and port counts measure different things from Zeek UIDs.

1 · 분과 응답자별로 TCP/445 기준선 만들기

<CASE>에 사례 태그를 넣습니다. 전체 캡처 범위를 UTC로 표시하고 캡처 시각은 숫자형 Zeek ts를 사용합니다. Splunk가 수집 시각으로 필터링한다면 가져온 시점도 포함합니다. 예시는 평탄화된 필드명을 사용합니다.

SPL 
index=zeek pcap_case="<CASE>"
| stats count min(ts) as first max(ts) as last by sourcetype
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S %Z"), last=strftime(last,"%Y-%m-%d %H:%M:%S %Z")
| sort - count

연결, SMB, DCE/RPC 로그가 수집됐는지 확인합니다. 구형 SMB 교환은 파서가 일부만 처리할 수 있습니다.

SPL 
index=zeek sourcetype=zeek:conn pcap_case="<CASE>" proto=tcp id_orig_h=10.8.20.101 id_resp_p=445
| eval minute=floor(ts/60)*60
| stats dc(uid) as connections sum(orig_pkts) as client_packets sum(resp_pkts) as server_packets
    values(conn_state) as states by minute id_resp_h
| sort 0 minute id_resp_h

분과 응답자별 TCP/445 활동을 비교합니다. 19:50 UTC 전후에는 DC 접속과 게이트웨이 10.8.20.1 접속을 구분해서 봅니다. 원본에서 DC 방향 흐름 그룹의 양방향 TCP/445 패킷은 6,141개이며, SYN의 고유 클라이언트 포트는 44개입니다. 패킷 수, 포트 수, Zeek UID 수는 각각 다른 단위입니다.

2 · Identify the share and resolve handles before counting file writes

SPL 
index=zeek pcap_case="<CASE>" id_orig_h=10.8.20.101 id_resp_h=10.8.20.8 id_resp_p=445
    id_orig_p IN (49200,49252,49560,49561,49563)
    sourcetype IN ("zeek:conn","zeek:smb_mapping","zeek:smb_files","zeek:dce_rpc")
| sort 0 ts
| table ts sourcetype uid id_orig_p path share_type name action named_pipe endpoint operation

Review the earlier policy session from client port 49200 and the selected later IPC sessions. path and share_type identify the mapped tree when logged. Check name, action and RPC metadata for evidence about the object. For the samples below, the server reply to the open supplies the file identifier that ties the following write to its named pipe.

SPL 
index=zeek pcap_case="<CASE>" uid="<SELECTED_UID>"
    sourcetype IN ("zeek:conn","zeek:smb_mapping","zeek:smb_files","zeek:dce_rpc")
| sort 0 ts
| table ts sourcetype uid id_orig_h id_orig_p id_resp_h id_resp_p path name action named_pipe endpoint operation

Use the UID from each selected connection in the same Zeek processing run to relate connection, tree mappings, file and RPC records. Repeat for each client port. Use the tree ID and handle in packet evidence when IPC$ and a disk share use the same TCP connection. An SMB write acknowledgement on a pipe establishes transport of bytes to that pipe. Account actions and remote execution need separate evidence.

2 · 파일 쓰기로 집계하기 전에 공유와 핸들 확인하기

SPL 
index=zeek pcap_case="<CASE>" id_orig_h=10.8.20.101 id_resp_h=10.8.20.8 id_resp_p=445
    id_orig_p IN (49200,49252,49560,49561,49563)
    sourcetype IN ("zeek:conn","zeek:smb_mapping","zeek:smb_files","zeek:dce_rpc")
| sort 0 ts
| table ts sourcetype uid id_orig_p path share_type name action named_pipe endpoint operation

클라이언트 포트 49200의 앞선 정책 세션과 이후의 선택한 IPC 세션들을 봅니다. 로그에 있으면 path와 share_type으로 연결된 공유를 식별합니다. name, action, RPC 메타데이터로 어떤 객체를 다뤘는지 확인합니다. 아래 예에서는 열기에 대한 서버 응답의 파일 식별자로 후속 쓰기를 네임드 파이프에 연결합니다.

SPL 
index=zeek pcap_case="<CASE>" uid="<SELECTED_UID>"
    sourcetype IN ("zeek:conn","zeek:smb_mapping","zeek:smb_files","zeek:dce_rpc")
| sort 0 ts
| table ts sourcetype uid id_orig_h id_orig_p id_resp_h id_resp_p path name action named_pipe endpoint operation

선택한 연결마다 동일한 Zeek 처리 실행의 UID를 사용해 연결, 공유 매핑, 파일, RPC 로그를 연계합니다. 클라이언트 포트별로 반복합니다. IPC$와 디스크 공유가 같은 TCP 연결에 있으면 패킷의 트리 ID와 핸들로 구분합니다. SMB 쓰기 성공 응답은 바이트가 해당 파이프로 전달됐다는 근거입니다. 계정 작업과 원격 실행 여부는 별도 근거로 확인합니다.

정상적인 도메인 관리에도 이 네임드 파이프가 쓰입니다. 워크스테이션에서 반복된 SMB1 활동은 감염 근거와 함께 검토할 가치가 있습니다. 확인한 응답은 캡처 안의 파이프 쓰기 성공을 보여 줍니다. 송신 프로세스, 상위 호출의 결과, DC 침해 여부는 추가 확인이 필요합니다.

3 · Compare the IPC and policy sessions in Arkime

Arkime 
tags == "<CASE>" && ip.src == 10.8.20.101 && ip.dst == 10.8.20.8 && port.src == 49252 && port.dst == 445

Open the session around 19:50:30 UTC. Follow the tree and handle through the samr open, then verify direction and response status for the selected write. Preserve the tuple and time in your notes because Arkime export can change the frame numbering.

Arkime 
tags == "<CASE>" && ip.src == 10.8.20.101 && ip.dst == 10.8.20.8 && port.src == 49200 && port.dst == 445

Open the earlier session and follow the policy read on SYSVOL. Compare its read reply with the pipe write acknowledgement. Keep the interpretation tied to the share and object in each session.

3 · Arkime에서 IPC 세션과 정책 세션 비교하기

Arkime 
tags == "<CASE>" && ip.src == 10.8.20.101 && ip.dst == 10.8.20.8 && port.src == 49252 && port.dst == 445

19:50:30 UTC 전후의 세션을 엽니다. 트리와 핸들을 따라 samr 열기를 확인한 다음, 선택한 쓰기의 방향과 응답 상태를 확인합니다. 내보내면 프레임 번호가 바뀔 수 있으므로 전체 주소·포트와 시각도 남깁니다.

Arkime 
tags == "<CASE>" && ip.src == 10.8.20.101 && ip.dst == 10.8.20.8 && port.src == 49200 && port.dst == 445

앞선 세션에서 SYSVOL 정책 파일 읽기를 따라갑니다. 정책 읽기 응답과 파이프 쓰기 응답을 비교합니다. 세션마다 공유 이름과 대상 객체를 확인한 뒤 해석합니다.

4 · Confirm one write’s response status offline if needed

TShark 
tshark -n -r "2019-08-20-traffic-analysis-exercise.pcap" \
  -Y 'frame.number == 8804 || frame.number == 8810' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e ip.src -e tcp.stream \
  -e smb.mid -e smb.cmd -e smb.nt_status

If Arkime leaves the acknowledgement unclear, display these two original frames only. Match the SMB multiplex ID inside the same TCP stream and use the responder’s status field for the outcome. The request’s header status cannot establish success.

4 · 필요할 때만 쓰기 한 건의 응답 상태를 오프라인으로 확인하기

TShark 
tshark -n -r "2019-08-20-traffic-analysis-exercise.pcap" \
  -Y 'frame.number == 8804 || frame.number == 8810' \
  -T fields -E header=y -e frame.number -e frame.time_epoch -e ip.src -e tcp.stream \
  -e smb.mid -e smb.cmd -e smb.nt_status

Arkime에서 쓰기 응답이 명확하지 않으면 원본 프레임 두 개만 출력합니다. 같은 TCP 스트림에서 SMB 멀티플렉스 ID를 대조하고 응답 측 상태 필드로 결과를 판단합니다. 요청 헤더의 상태 필드만으로 성공 여부를 판단할 수 없습니다.

5 · Record the protocol evidence and check the DC

Include the workstation and DC, capture hash, UTC window, tree and pipe names, and matched frames in the SOC ticket. Verify which endpoint process opened the SMB1 sessions, review SMB1 exposure and the approved use of legacy protocols, and compare the DC’s authentication, service creation and file-access evidence with the burst. Track disk writes and remote execution as distinct findings if corroborated.

5 · SOC 티켓에 근거를 남기고 DC 기록 확인하기

티켓에 워크스테이션과 DC, 캡처 해시, UTC 구간, 공유와 파이프 이름, 대응하는 프레임 번호를 넣습니다. SMB1 세션을 연 프로세스와 구형 프로토콜 사용 승인 여부를 확인합니다. DC의 인증, 서비스 생성, 파일 접근 기록도 해당 구간과 대조합니다. 디스크 파일 쓰기와 원격 실행이 추가로 확인되면 각각의 근거를 따로 남깁니다.
